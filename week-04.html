Lab 4.1 — Subnetting drills, by hand (2h)

Goal: Subnet on paper, fast, correctly, without a calculator. Then verify with a tool.

Setup: Paper and pen. No calculator, no phone. Kali VM open in a second window for the verification step only.

Steps:

  1. Binary conversion. Convert these to binary by hand, then check yourself with python3 -c "print(bin(192))": 192 · 168 · 10 · 130 · 255 · 224 · 0 · 127

  2. Memorise the mask table. Write it out from memory five times:

CIDR Mask Block size (256 − last octet) Usable hosts
/24 255.255.255.0 256 254
/25 255.255.255.128 128 126
/26 255.255.255.192 64 62
/27 255.255.255.224 32 30
/28 255.255.255.240 16 14
/29 255.255.255.248 8 6
/30 255.255.255.252 4 2
  1. Solve these ten by hand. For each, write the network address, the broadcast address, the first usable host, the last usable host, and the number of usable hosts:
  • 192.168.10.0/24
  • 192.168.10.0/26
  • 192.168.10.130/26
  • 192.168.1.77/30
  • 172.16.5.200/22
  • 10.10.10.10/8
  • 192.168.100.200/27
  • 10.0.0.55/12
  • 192.168.1.1/25
  • 172.20.30.40/28

  1. Verify with a tool. For each answer, check it: 

    sudo apt install sipcalc -y     # or use: ipcalc
sipcalc 192.168.10.130/26
python3 -c "import ipaddress; n=ipaddress.ip_network('192.168.10.130/26', strict=False); print(n.network_address, n.broadcast_address, list(n.hosts())[0], list(n.hosts())[-1], n.num_addresses-2)"

  2. Drill to speed. Go to subnettingpractice.com and do 25 questions. Target: under 20 seconds each. Do not move on until you hit that.

  3. Reverse direction. Given "I need a subnet with at least 50 hosts", what is the smallest CIDR that fits? Do five of these.

Deliverable: Your handwritten working for all ten problems, plus your subnettingpractice.com score and time.

If you see this → it means:

Symptom Cause
Network address lands on an odd number like .10.64 for a /26 Correct — block size 64 means subnets start at 0, 64, 128, 192. You are not wrong
You get 64 usable hosts for a /26 You forgot to subtract 2 (network + broadcast). Correct answer is 62
/22 breaks your brain Work in the third octet, not the fourth. Block size = 256 − 252 = 4, so subnets are 0, 4, 8, 12…
Your answer is right but takes 3 minutes Not yet at professional speed. Drill more; speed here is muscle memory, nothing else

Lab 4.2 — Map your own lab network (1.5h)

Goal: Read the network your own machine lives on, from the command line only.

Setup: Both VMs running, adapter on NAT Network (from Week 1).

Steps:

  1. ip a — write down for each interface: name, state, MAC address, IP, prefix length.
  2. ip r — identify your default gateway. What does default via mean?
  3. ip n — this is the ARP cache: IP → MAC mappings your machine already knows. Why is it already populated?
  4. ping -c 3 <ubuntu-ip> from Kali. Does the ARP cache change? Check ip n again.
  5. ping -c 3 1.1.1.1 — a public address. Then traceroute 1.1.1.1. How many hops before you leave your lab? Where does the path go?
  6. traceroute -I 1.1.1.1 (ICMP mode) vs plain traceroute (UDP mode). Do the paths differ? Why might that be?
  7. Deliberately break the gateway: sudo ip route del default. Try to ping 1.1.1.1. Now try to ping your Ubuntu VM. Explain the difference. Restore with sudo ip route add default via <gateway>.

Deliverable: A hand-drawn diagram of your lab: interfaces, IPs, MACs, the gateway, and where the lab ends and the internet begins.

If you see this → it means:

Symptom Cause
ip a shows 192.168.56.x on one interface That's a host-only adapter, not a NAT Network adapter — check VirtualBox settings
traceroute prints only * * * ICMP/UDP is filtered on the path. Try traceroute -T -p 443 1.1.1.1 (TCP mode)
Ping to the local VM works but internet fails after deleting the route Exactly the point: the gateway is the door out of your subnet. Same-subnet traffic never needs it
ip n shows FAILED or INCOMPLETE Nothing answered the ARP request — host down, wrong subnet, or firewall dropping ARP

Lab 4.3 — Build a three-machine network on an Internal Network (2h)

Goal: Build a switched network with no router and no DHCP. You assign every address by hand. This is where addressing stops being theory.

Setup: 16GB host. RAM budget: Kali 3GB, Ubuntu 3GB, third node 1.5GB. Do not run all three with a GUI at 4GB each — you will swap and hate your life.

The third node: clone your Ubuntu VM and switch it to a server install with no desktop, or build a minimal Debian/Alpine VM. It only needs a shell.

Steps:

  1. Snapshot all three first.
  2. In VirtualBox, give each VM a second adapter (Adapter 2) set to Internal Network, name labnet. Leave Adapter 1 on NAT Network so you keep internet through a different path.
  3. Boot all three. Find the new interface name (ip a — usually enp0s8 or eth1).
  4. Assign static addresses by hand — no DHCP exists on labnet:
VM Address Prefix Role
Kali 192.168.50.10 /24 attacker
Ubuntu 192.168.50.20 /24 target
Node-3 192.168.50.30 /24 third host

Ubuntu (netplan): 

# /etc/netplan/99-labnet.yaml
network:
  version: 2
  ethernets:
    enp0s8:
      addresses: [192.168.50.20/24]

sudo netplan apply
Kali and Node-3: 
sudo ip link set enp0s8 up
sudo ip addr add 192.168.50.10/24 dev enp0s8

  1. Prove the switch works. From Kali: ping -c3 192.168.50.20 and ping -c3 192.168.50.30. Both must work — this proves layer 2 connectivity with zero routing involved.
  2. Prove there is no gateway. ip r on any VM — there must be no default via line for labnet. Confirm: ping -c2 1.1.1.1 fails, ping -c2 192.168.50.20 succeeds.
  3. Break it on purpose. Change Kali to 192.168.60.10/24 (wrong subnet). Try to ping Ubuntu. It fails — but the cable is fine. Explain in your notes why, using the words subnet and layer 3.
  4. Now add a router role. Turn the Ubuntu VM into a router for the other two: sudo sysctl -w net.ipv4.ip_forward=1, then reach the Kali-to-Ubuntu subnet from Node-3. Note: this is a rabbit hole. Timebox it to 20 minutes; you'll do it properly in Week 6.

Deliverable: A diagram of the labnet with all three IPs and MACs, plus a written explanation of why two hosts on the same switch but different subnets cannot talk.

If you see this → it means:

Symptom Cause
Interface is DOWN with no address You added the address but not ip link set <if> up, or netplan YAML indentation is wrong
Address disappears after reboot ip addr add is temporary by design. Make it permanent in netplan / NetworkManager
Ping fails though addressing is correct VirtualBox Internal Network name must match exactly on all three VMs, including capitalisation
All three get the same IP You're looking at Adapter 1 (NAT Network), not Adapter 2. Check ip a for which interface holds which address

Lab 4.4 — Enumerate the lab with arp-scan (1.5h)

Goal: Discover every host on a network without asking a single one of them for permission — using only ARP.

Steps:

  1. From Kali (attached to labnet): 

    sudo apt install arp-scan -y     # preinstalled on Kali, may need install on Ubuntu
sudo arp-scan -I eth1 -l
    (Replace eth1 with your labnet interface name — -I picks the interface, -l means "my local network".)

  2. Record the output: IP, MAC, and vendor (OUI). Where does the vendor name come from if nobody asked the device?

  3. Add a fourth device. Boot a phone or a second lightweight VM onto labnet. Re-run the scan. Did it appear? How fast?
  4. Turn one VM off. Re-run. Does it still appear? Check ip n — how long did the stale entry persist?
  5. Compare tools. This time scan with nmap -sn 192.168.50.0/24. Both find the hosts — but which one is faster, and which one is stealthier? Why? (Hint: ARP is layer 2; nmap -sn uses ARP on local networks too, but ICMP further away.)
  6. The defender's view. On the Ubuntu target, run sudo tcpdump -i enp0s8 arp -n and re-run arp-scan from Kali. Read what Ubuntu sees. Write down: is there any way for Ubuntu to tell this scan apart from a normal ARP request?

Deliverable: The full arp-scan output for labnet, plus a written answer to step 6 — this is the first time you will realise some scanning is invisible.

⚠️ Authorization check. arp-scan on a network you do not own is a hostile act, even though it's "only ARP". Run it only on labnet and your own devices. The university Wi-Fi, the café, the family router — all off limits, permanently.

المختبر 4.2 — ارسم خريطة شبكة مختبرك (1.5 ساعات)

الهدف: أن تقرأ الشبكة التي يعيش عليها جهازك، من سطر الأوامر فقط.

الإعداد: الآلتان الافتراضيتان تعملان، والمحوّل (adapter) على NAT Network (من الأسبوع 1).

الخطوات:

  1. ip a — اكتب لكل واجهة (interface): الاسم، والحالة، وعنوان MAC، وعنوان IP، وطول البادئة (prefix length).
  2. ip r — حدّد بوابتك الافتراضية. ماذا يعني default via؟
  3. ip n — هذا هو ذاكرة ARP المؤقتة (ARP cache): خرائط IP → MAC التي يعرفها جهازك بالفعل. لماذا هي ممتلئة أصلاً؟
  4. ping -c 3 <ubuntu-ip> من Kali. هل تتغيّر ذاكرة ARP؟ افحص ip n مرة أخرى.
  5. ping -c 3 1.1.1.1 — عنوان عام. ثم traceroute 1.1.1.1. كم قفزة (hop) قبل أن تغادر مختبرك؟ إلى أين يمضي المسار؟
  6. traceroute -I 1.1.1.1 (وضع ICMP) مقابل traceroute المجرّد (وضع UDP). هل يختلف المساران؟ ولماذا قد يحدث ذلك؟
  7. اكسر البوابة عمداً: sudo ip route del default. جرّب أن تـ ping 1.1.1.1. ثم جرّب أن تـ ping آلة Ubuntu. اشرح الفرق. أعد الوضع بـ sudo ip route add default via <gateway>.

التسليم المطلوب: رسم يدوي لمختبرك: الواجهات، وعناوين IP، وعناوين MAC، والبوابة، وأين ينتهي المختبر ويبدأ الإنترنت.

إن رأيت هذا → فمعناه:

العَرَض السبب
ip a يُظهر 192.168.56.x على إحدى الواجهات هذا محوّل host-only، لا محوّل NAT Network — افحص إعدادات VirtualBox
traceroute يطبع * * * فقط حركة ICMP/UDP مُرشَّحة على المسار. جرّب traceroute -T -p 443 1.1.1.1 (وضع TCP)
الـ ping إلى الآلة المحلية ينجح لكن الإنترنت يفشل بعد حذف المسار هذا هو المقصود بالضبط: البوابة هي باب الخروج من شبكتك الفرعية. وحركة نفس الشبكة الفرعية لا تحتاجها أبداً
ip n يُظهر FAILED أو INCOMPLETE لا شيء أجاب على طلب ARP — الجهاز متوقف، أو الشبكة الفرعية خاطئة، أو جدار ناري يُسقط ARP

المختبر 4.3 — ابنِ شبكة من ثلاثة أجهزة على Internal Network (2 ساعات)

الهدف: ابنِ شبكة مُبدَّلة (switched) بلا موجّه وبلا DHCP. أنت تعيّن كل عنوان بيدك. هنا تتوقف العنونة عن كونها نظرية.

الإعداد: مضيف بذاكرة 16GB. ميزانية الذاكرة: Kali بـ 3GB، و Ubuntu بـ 3GB، والعقدة الثالثة بـ 1.5GB. لا تشغّل الثلاث بواجهة رسومية وبذاكرة 4GB لكل واحدة — ستستخدم swap وستكره حياتك.

العقدة الثالثة: استنسخ آلة Ubuntu وحوّلها إلى تثبيت سيرفر بلا سطح مكتب، أو ابنِ آلة Debian/Alpine مصغّرة. لا تحتاج سوى shell.

الخطوات:

  1. خُذ لقطة (snapshot) للثلاث أولاً.
  2. في VirtualBox، أعطِ كل آلة محوّلاً ثانياً (Adapter 2) مضبوطاً على Internal Network بالاسم labnet. واترك Adapter 1 على NAT Network لتحتفظ بالإنترنت عبر مسار مختلف.
  3. أقلع الثلاث. اعرف اسم الواجهة الجديدة (ip a — عادةً enp0s8 أو eth1).
  4. عيّن العناوين الساكنة يدوياً — لا وجود لـ DHCP على labnet:

  2. أثبت أنه لا توجد بوابة. ip r على أي آلة — يجب أن لا يوجد سطر default via من أجل labnet. أكّد: ping -c2 1.1.1.1 يفشل، و ping -c2 192.168.50.20 ينجح.

المختبر 4.4 — تعداد المختبر بـ arp-scan (1.5 ساعات)

الهدف: اكتشف كل جهاز على الشبكة دون أن تطلب الإذن من أي منها — باستخدام ARP فقط.

الخطوات:

  1. من Kali (المتّصلة بـ labnet): 

    sudo apt install arp-scan -y     # preinstalled on Kali, may need install on Ubuntu
sudo arp-scan -I eth1 -l
    (استبدل eth1 باسم واجهة labnet عندك — -I يختار الواجهة، و -l تعني "شبكتي المحلية".)

  2. سجّل المخرجات: IP، و MAC، والشركة المصنّعة (OUI). من أين يأتي اسم الشركة إن لم يسأل أحدٌ الجهاز؟

  3. أضف جهازاً رابعاً. أقلع هاتفاً أو آلة افتراضية خفيفة ثانية على labnet. أعد تشغيل الفحص. هل ظهر؟ وبأي سرعة؟
  4. أطفئ إحدى الآلات. أعد الفحص. هل ما زال يظهر؟ افحص ip n — كم بقي المدخل القديم (stale entry)؟
  5. قارن الأدوات. هذه المرة افحص بـ nmap -sn 192.168.50.0/24. كلتاهما تجد الأجهزة — لكن أيّهما أسرع، وأيّهما أكثر تخفّياً؟ لماذا؟ (تلميح: ARP في الطبقة 2؛ و nmap -sn يستخدم ARP أيضاً على الشبكات المحلية، لكن ICMP على الشبكات الأبعد.)
  6. من منظور المدافع. على هدف Ubuntu، شغّل sudo tcpdump -i enp0s8 arp -n وأعد تشغيل arp-scan من Kali. اقرأ ما تراه Ubuntu. واكتب: هل توجد أي طريقة تستطيع بها Ubuntu أن تميّز هذا الفحص عن طلب ARP عادي؟

التسليم المطلوب: مخرجات arp-scan الكاملة لـ labnet، مع إجابة مكتوبة على الخطوة 6 — هذه أول مرة تدرك فيها أن بعض الفحص غير مرئي.

⚠️ تحقّق من التصريح. تشغيل arp-scan على شبكة لا تملكها فعل عدائي، حتى لو كان "ARP فقط". شغّله فقط على labnet وعلى أجهزتك أنت. شبكة الواي فاي في الجامعة، والمقهى، وراوتر البيت — كلها خارج الحدود، بشكل دائم.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

Networking is not a prerequisite for security. Networking is security.

Everything an attacker does travels over a network. Everything a defender sees arrives as network traffic. If you cannot reason about addressing, subnets, and layer 2, you cannot understand a single attack you will study in the next nine weeks.

Three things worth internalizing:

  1. ARP has no authentication — and that is a design flaw, not a bug. When your machine asks "who has 192.168.50.1?", any host on the segment may answer, and your machine will believe it. There is no signature, no challenge, no verification. An attacker on the same segment simply answers first and claims to be the gateway. Now every packet you send to the internet goes through them. That is ARP spoofing, and it is the front door to a man-in-the-middle attack — the attacker reads, and can silently modify, your traffic. This is why you will spend Week 5 watching a real credential cross the wire. ARP spoofing is not exotic; it is the default behaviour of a fundamentally trusting protocol, and it works because you are on the same broadcast domain.

  2. This is why network segmentation exists, and why flat networks are dangerous. In Lab 4.3 you built a flat /24 where all three machines can see each other directly. In a real company, that flat network can mean the intern's laptop shares a broadcast domain with the payroll server. One compromised machine, and the attacker can ARP-spoof every neighbour. Segmentation — VLANs, subnets, firewalls between them — is a direct response to exactly the problem you just demonstrated with arp-scan. When you read "lateral movement" in an incident report, this is the mechanism.

  3. A single IP address tells an attacker more than you think. From one address they can determine: which ISP or hosting provider owns it (ASN), the likely country and city, its reverse DNS hostname (which frequently leaks role and environment — jenkins-dev-01.corp.example.com names the service, the environment, and the company), whether it is residential/dynamic or a static business range, and whether it appears in public internet-wide scan datasets. None of that requires touching the target. It is all passive. This is called OSINT, and it is the first phase of every real engagement. The defensive lesson is equally sharp: your hostnames and your exposed services leak your internal structure, and that is why naming conventions and outbound service exposure are security decisions, not IT housekeeping.

الشبكات ليست متطلباً سابقاً للأمن. الشبكات هي الأمن.

كل ما يفعله المهاجم ينتقل عبر شبكة. وكل ما يراه المدافع يصل في صورة حركة شبكة. إن لم تستطع التفكير المنطقي في العنونة والشبكات الفرعية والطبقة 2، فلن تفهم هجمة واحدة من التي ستدرسها في الأسابيع التسعة القادمة.

ثلاثة أمور تستحق أن تستوعبها:

  1. ARP بلا أي مصادقة — وهذا عيب في التصميم، لا خطأ برمجي. عندما يسأل جهازك "من يملك 192.168.50.1؟"، يجوز لأي جهاز على نفس القطاع أن يجيب، وسيصدّقه جهازك. لا توقيع، ولا تحدٍّ، ولا تحقّق. والمهاجم على نفس القطاع يجيب ببساطة أولاً ويدّعي أنه البوابة. عندها تمر كل حزمة ترسلها إلى الإنترنت عبره. هذا هو انتحال ARP (ARP spoofing)، وهو الباب الأمامي لهجوم الرجل في المنتصف (MITM) — يقرأ المهاجم حركتك، ويستطيع تعديلها بصمت. لهذا ستقضي الأسبوع 5 في مشاهدة بيانات اعتماد حقيقية تعبر السلك. انتحال ARP ليس شيئاً نادراً؛ إنه السلوك الافتراضي لبروتوكول يثق بكل شيء، وينجح لأنك على نفس نطاق البث (broadcast domain).

  2. لهذا توجد تجزئة الشبكة، ولهذا الشبكات المسطحة خطرة. في المختبر 4.3 بنيت شبكة مسطحة /24 ترى فيها الآلات الثلاث بعضها مباشرة. وفي شركة حقيقية، تلك الشبكة المسطحة قد تعني أن حاسوب المتدرّب يشارك نطاق البث مع سيرفر الرواتب. جهاز واحد مخترق، ويستطيع المهاجم انتحال ARP لكل جيرانه. التجزئة (segmentation) — VLANs، وشبكات فرعية، وجدران نارية بينها — ردّ مباشر على المشكلة نفسها التي عرضتها للتو بـ arp-scan. وعندما تقرأ "الحركة الجانبية (lateral movement)" في تقرير حادث، فهذا هو الميكانيزم.

  3. عنوان IP واحد يخبر المهاجم بأكثر مما تظن. من عنوان واحد يستطيع تحديد: أي مزوّد خدمة إنترنت أو استضافة يملكه (ASN)، والدولة والمدينة المحتملة، واسمه العكسي في DNS (reverse DNS) — الذي كثيراً ما يسرّب الدور والبيئة: jenkins-dev-01.corp.example.com يسمّي الخدمة، والبيئة، والشركة — وهل هو عنوان منزلي/ديناميكي أم نطاق أعمال ساكن، وهل يظهر في مجموعات بيانات المسح العامة على مستوى الإنترنت. لا شيء من ذلك يتطلب لمس الهدف. كله سلبي. هذا يُسمى OSINT، وهو المرحلة الأولى في كل عملية حقيقية. والدرس الدفاعي بنفس الحدّة: أسماء أجهزتك وخدماتك المكشوفة تسرّب بنيتك الداخلية، ولهذا فإن اصطلاحات التسمية وكشف الخدمات للخارج قرارات أمنية، لا أعمال صيانة تقنية.

نموذج OSI — لماذا نحتاج طبقات أصلاً؟

تخيّل أنك تريد إرسال رسالة لصديق في مدينة أخرى. أنت لا تفكر في: أي طريق تسلك الشاحنة، ولا كيف تُعبّأ الصناديق، ولا كيف تعمل إشارات المرور. أنت فقط تكتب الرسالة وتضعها في صندوق البريد.

هذا بالضبط ما يفعله نموذج الطبقات: يقسّم عملية الاتصال المعقدة إلى طبقات مستقلة، كل طبقة لها مهمة واحدة واضحة، وتقدّم خدمتها للطبقة التي فوقها دون أن تعرف هي كيف تعمل الطبقة التي تحتها.

الفائدة العملية: عندما يتعطل شيء، تعرف أين تبحث. لا إنترنت؟ ابدأ من الطبقة 1. يفتح الموقع بالاسم لكن لا يعمل برقم IP؟ المشكلة في طبقة التطبيق (DNS).

ملاحظة مهمة: الطبقات 5 و 6 و 7 في OSI لا وجود لها كطبقات مستقلة في TCP/IP — كلها مدمجة في طبقة التطبيق. لهذا الواقع العملي يستخدم TCP/IP، بينما OSI يبقى لغة مشتركة للوصف: عندما يقول مهندس "هذه مشكلة طبقة 2"، يفهم الجميع المقصود فوراً.

التغليف (Encapsulation) — الفكرة التي تشرح كل شيء

عندما ترسل رسالة، لا تُرسل كما هي. تُغلَّف طبقة فوق طبقة، مثل الظرف داخل ظرف داخل ظرف:

الطبقة الوحدة (PDU) ما يُضاف
Application Data رسالتك: GET /login
Transport Segment رأس TCP: منفذ المصدر، منفذ الوجهة، رقم التسلسل
Network Packet رأس IP: عنوان IP المصدر والوجهة
Data Link Frame رأس Ethernet: MAC المصدر والوجهة
Physical Bits تُحوَّل إلى إشارات كهربائية أو ضوئية

القاعدة: كل طبقة تضيف رأسها (header) فقط، ولا تنظر داخل ما فوقها. جهاز التوجيه (Router) يقرأ رأس IP ويرميه، ثم يقرأ التالي. المُبدّل (Switch) يقرأ رأس Ethernet فقط ولا يعرف شيئاً عن IP.

لماذا يهمنا هذا أمنياً؟ لأن كل طبقة لها هجماتها الخاصة. الهجوم على ARP هو طبقة 2. انتحال IP هو طبقة 3. اختطاف الجلسة هو طبقة 4. XSS هو طبقة 7. عندما تفهم الطبقات، تصبح كل ثغرة تقرأ عنها في مكانها الصحيح.

العنونة IPv4 — الأساس الرياضي

عنوان IPv4 = 32 بت، تُكتب كأربعة أرقام (كل رقم من 0 إلى 255) تفصلها نقاط.

لماذا 255؟ لأن كل رقم يمثل 8 بتات، و 2⁸ = 256 احتمالاً (من 0 إلى 255).

التحويل من عشري إلى ثنائي — الطريقة:

قيم البتات الثمانية من اليسار لليمين:

128 64 32 16 8 4 2 1

مثال: حوّل 192 إلى ثنائي

192 = 128 + 64  →  128 نعم(1)  64 نعم(1)  32 لا(0)  16 لا(0)  8 لا(0)  4 لا(0)  2 لا(0)  1 لا(0)
192 = 1 1 0 0 0 0 0 0

مثال كامل: 192.168.10.130

192  →  11000000
168  →  10101000     (168 = 128 + 32 + 8)
 10  →  00001010     (10  = 8 + 2)
130  →  10000010     (130 = 128 + 2)

المدى القناع عدد العناوين
10.0.0.0 – 10.255.255.255 /8 ~16.7 مليون
172.16.0.0 – 172.31.255.255 /12 ~1 مليون
192.168.0.0 – 192.168.255.255 /16 65,536

عناوين خاصة أخرى يجب حفظها:

  • 127.0.0.0/8 → العنوان المحلي (localhost) — جهازك نفسه.
  • 169.254.0.0/16 → APIPA — يظهر عندما يفشل الحصول على عنوان من DHCP. رؤيته علامة مشكلة، لا حل.

لماذا هذا مهم أمنياً؟ لأن رؤية عنوان 10.x أو 192.168.x في سجل تخبرك أن النشاط داخلي — أي أن المهاجم إما موجود داخل الشبكة فعلاً، أو أنه يستخدم برنامجاً يزوّر العناوين. العنوان الخاص في سجل هجوم على سيرفر عام = علامة تفشيل (tunneling) أو وسيط. أما عنوان 127.0.0.1 في السجلات فهو إما خدمة داخلية أو تزوير متعمّد لإخفاء المصدر الحقيقي.

التقسيم الفرعي (Subnetting) — بالمثال العملي

الفكرة: بدلاً من شبكة واحدة كبيرة، نقسمها إلى شبكات أصغر. لماذا؟ للأمان (عزل) وللتنظيم (تقليل حركة البث).

الخطوة الحاسمة: حساب حجم الكتلة

الصيغة الذهبية: حجم الكتلة = 256 − آخر رقم في القناع

مثال 1: 192.168.10.0/26

  1. القناع /26 = 255.255.255.192
  2. حجم الكتلة = 256 − 192 = 64
  3. الشبكات الفرعية تبدأ عند: .0 · .64 · .128 · .192
  4. عدد الأجهزة القابلة للاستخدام = 2⁶ − 2 = 62
الشبكة عنوان الشبكة أول جهاز آخر جهاز عنوان البث
1 192.168.10.0 .1 .62 .63
2 192.168.10.64 .65 .126 .127
3 192.168.10.128 .129 .190 .191
4 192.168.10.192 .193 .254 .255

مثال 2: أين يقع 192.168.10.130/26؟

  • الكتل: 0، 64، 128، 192 → العدد 130 يقع بين 128 و 191
  • عنوان الشبكة: 192.168.10.128
  • أول جهاز: 192.168.10.129
  • آخر جهاز: 192.168.10.190
  • عنوان البث: 192.168.10.191

مثال 3: القناع في الأوكتيت الثالث — 172.16.5.200/22

هنا الكتلة ليست في الأوكتيت الرابع بل الثالث:

  1. القناع /22 = 255.255.252.0
  2. حجم الكتلة في الأوكتيت الثالث = 256 − 252 = 4
  3. الشبكات: 0، 4، 8، 12 … → العدد 5 يقع بين 4 و 7
  4. الشبكة: 172.16.4.0 · البث: 172.16.7.255

القاعدة عند اللبس: اكتب القناع بالثنائي وضع خطاً تحت بتات الشبكة. ما تبقّى أصفاراً هو الجزء الذي يتغير (الأجهزة). لا تحفظ — ارسم.

لماذا نطرح 2؟ لأن أول عنوان في كل شبكة هو عنوان الشبكة نفسه (يُستخدم لتعريف الشبكة)، وآخر عنوان هو عنوان البث (Broadcast) الذي يذهب لكل الأجهزة. لا يجوز إعطاؤهما لجهاز.

ARP — الثغرة المدمجة في التصميم

المشكلة: الجهاز يعرف عنوان IP الوجهة، لكنه يحتاج MAC ليبني إطار Ethernet. كيف يربط بينهما؟ عبر ARP.

آلية العمل في خطوتين:

  1. طلب (Request): يُرسل بثاً (Broadcast) لكل الشبكة: "من يملك 192.168.50.20؟ أخبر 192.168.50.10"
  2. رد (Reply): الجهاز صاحب العنوان يرد مباشرة (Unicast): "أنا 192.168.50.20، وهذا MAC الخاص بي"

النتيجة: جدول مؤقت في ذاكرتك يربط IP بـ MAC. تراه بأمر ip n.

الثغرة: لا يوجد في ARP أي مصادقة. الرسالة تقول ببساطة "ثق بي". لذلك:

انتحال ARP (ARP Spoofing): المهاجم يرسل ردود ARP كاذبة باستمرار: "أنا البوابة 192.168.50.1، وهذا MAC الخاص بي". فتحدّث ضحاياه جدول ARP عندهم، ويصبح كل خروجهم للإنترنت ماراً عبر جهاز المهاجم. هذه هي هجمة الرجل في المنتصف (MITM)، وهي ممكنة فقط لأن ARP بلا أي مصادقة.

كيف تدافع؟

  • التقسيم (Segmentation): المهاجم يحتاج أن يكون على نفس الشبكة المحلية. عزل الشبكات يقطع الطريق.
  • Dynamic ARP Inspection (DAI): ميزة على المُبدّلات المُدارة تتحقق من صحة ردود ARP.
  • المراقبة: أدوات مثل arpwatch تنبّهك عند تغيّر ربط IP-MAC.
