Lab 10.1 — Hashing is not encryption (2h)

Goal: Feel, not read, the difference between a hash and a cipher. Setup: Kali VM, terminal only.

  1. Avalanche effect — change one character, watch everything change: 

    echo -n "password"  | sha256sum
echo -n "Password"  | sha256sum
echo -n "password " | sha256sum
    Roughly half the output bits change for a one-bit input change. This is what makes hashes useful for integrity.

  2. Determinism — the property that makes unsalted hashes dangerous. Run echo -n "password" | sha256sum twice: identical both times. Now think about a password database: every user with the password password has the identical stored hash.

  3. Hashing is one-way. Run echo -n "correct horse battery staple" | sha256sum, then try to reverse it. You cannot — not because the tool lacks an option, but because the information is genuinely destroyed. A 60-character input and a 3-character input both produce 64 hex characters: 

    echo -n "a" | sha256sum        # 64 hex chars
echo -n "a" | md5sum           # 32 hex chars

  4. Integrity in practice. Download a file from a site that publishes checksums, then: 

    sha256sum downloaded-file.iso
echo "<published-hash>  downloaded-file.iso" > check.txt   # exactly TWO spaces
sha256sum -c check.txt      # prints: OK
    Copy the file, corrupt one byte with dd, verify again — it fails. This is how package managers and your OS verify nothing was tampered with in transit.

  5. Now prove hashing is not encryption: 

    echo "password" > plain.txt
openssl enc -aes-128-cbc -nosalt -K 00112233445566778899aabbccddeeff \
  -iv 0102030405060708090a0b0c0d0e0f10 -in plain.txt -out cipher.bin
openssl enc -d -aes-128-cbc -nosalt -K 00112233445566778899aabbccddeeff \
  -iv 0102030405060708090a0b0c0d0e0f10 -in cipher.bin
    The ciphertext is reversible because a key exists. A hash has no key and no reverse. Write that sentence in your own words.

Deliverable: All three hashes from step 1, the sha256sum -c success and failure output, the decrypted text from step 5, and a three-sentence explanation of the difference between a hash and a cipher.

If you see this → it means:

Symptom Cause

Lab 10.2 — Crack your own hashes, and learn why password policy exists (1.5h)

⚠️ LEGAL BOUNDARY — READ BEFORE YOU TYPE ANYTHING. You may crack only hashes you generated yourself, on your own VM, in this lab. That is the entire scope. Cracking, or attempting to crack, password hashes you do not own, or do not have explicit written authorization to test, is a criminal offence in essentially every jurisdiction — under computer-misuse statutes in the US and EU and equivalent laws across the Arab world. "It was on a website I found" is not authorization. "It was in a dump I downloaded" is not authorization. There is no grey area here. The purpose of this lab is to make you feel, in your own hands, why password policy matters — so you can defend it with evidence instead of repeating it as a rule.

Goal: Measure how fast weak passwords die, and how much the storage algorithm changes the outcome.

Setup: Kali VM. john and hashcat are preinstalled. The rockyou wordlist ships at /usr/share/wordlists/rockyou.txt.gz — decompress with sudo gunzip /usr/share/wordlists/rockyou.txt.gz.

  1. Create three training passwords — never a real password you use anywhere: summer2024 (word plus a year: the most common real-world pattern), Tr0ub4dor (word with letter substitutions), and a long random passphrase.

  2. Generate the hashes yourself. You are the author of every hash in this lab: 

    for p in 'summer2024' 'Tr0ub4dor' 'correct-horse-battery-staple-9x'; do
  printf '%s' "$p" | sha256sum | awk '{print $1}'
done > raw-sha256.txt

  3. Crack them, and time it: 

    time john --format=raw-sha256 --wordlist=/usr/share/wordlists/rockyou.txt raw-sha256.txt
john --show --format=raw-sha256 raw-sha256.txt

  4. Change only the algorithm, not the password. bcrypt-hash the same weak password and crack that: 

    sudo apt install -y apache2-utils        # provides htpasswd
htpasswd -bnBC 10 "" 'summer2024' | tr -d ':\n' > bcrypt-pw.txt   # note the $2y$10$ prefix
time john --format=bcrypt --wordlist=/usr/share/wordlists/rockyou.txt bcrypt-pw.txt

  5. Compare and record the numbers. Same password, same wordlist, same machine — only the storage algorithm differs. The gap is not a few percent; it is orders of magnitude.

  6. Benchmark your own hardware rather than trusting a number from an article — hashcat -b -m 0 (MD5), -m 1400 (SHA-256), -m 3200 (bcrypt). This is the number that explains everything: an attacker needs no skill, only speed. When a fast hash allows billions of guesses per second, password length is the only defence left.
  7. See salting in the file itself. Run openssl passwd -6 'summer2024' twice — the outputs differ, because -6 (SHA-512 crypt) generates a random salt each time and stores it with the hash. Two users with the same password now have different stored values, so a precomputed rainbow table is useless.

Deliverable: A table of password, algorithm, time to crack, and benchmark hashes/sec. Plus one paragraph: write the password policy you would recommend to a small business, and justify each rule with your own measured data.

Lab 10.3 — Inspect a real TLS certificate and decode every field (1.5h)

Goal: Stop treating the padlock as magic. Setup: Kali VM with internet access, target example.com (www.wikipedia.org or github.com also work).

  1. Connect and dump the certificate: 
    openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

    Why -servername? It sends the hostname in the handshake (SNI — Server Name Indication). Without it, a server hosting many sites doesn't know which certificate to present and you get the wrong one. This confuses learners constantly.

  2. Decode the leaf certificate: 

    openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -text

  3. Explain every field in your notes — this is the real deliverable:

Field What it means
Version Almost always v3. X.509 is the format; v3 added extensions
Serial Number Unique per issuer — what a revocation list refers to
Signature Algorithm What the issuer used to sign this cert, e.g. sha256WithRSAEncryption
Issuer / Subject Who signed it (the CA) and who it is for. Fields C, O, CN
Validity Not Before / Not After. Outside this window the cert is invalid even if perfectly signed
Subject Public Key Info The public key being vouched for, with algorithm and size (RSA 2048/4096 or an EC curve)
Subject Alternative Name The hostnames this cert covers. Browsers ignore CN entirely and match on SAN — this is how one cert covers example.com and www.example.com
Basic Constraints: CA: TRUE means it may sign other certificates. A leaf must say FALSE
Key Usage / Extended Key Usage What the key may legally be used for, e.g. TLS Web Server Authentication
Subject / Authority Key Identifier Fingerprints of this cert's key and the issuer's key — the links in the chain
Authority Information Access / CRL Distribution Points Where to find the issuer's certificate, the OCSP responder, and the revocation list
Signature Value The issuer's actual signature over all of the above

  1. Trace the chain to the root: 

    openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null \
  | grep -E "^ *[0-9]+ s:|^ *i:"
grep -c "BEGIN CERTIFICATE" /etc/ssl/certs/ca-certificates.crt    # count your trusted roots
    You will see leaf (the site) → intermediate CA → root CA. The server usually sends the leaf and intermediates but not the root — the client already has it. That .crt file is the entire basis of trust on your machine: a certificate is only "valid" because a chain of signatures leads to one of those entries.

  2. Read the dates, subject and issuer with -noout -dates -subject -issuer, and note how short the validity window is on modern certificates — short lifetimes limit the damage of a stolen key.

  3. Force a verification failure and read the error. Save a cert with openssl x509 > site.pem, then run openssl verify -CAfile /dev/null site.pem. unable to get local issuer certificate means: I cannot trace this to anyone I trust. That is precisely the message a browser turns into a warning page — and precisely the message users click past.

Deliverable: Your notes explaining every field in step 3 in your own words, the chain output with the root identified, the count of trusted roots on your system, and the step 6 error with a one-sentence explanation for a non-technical user.

Lab 10.4 — Generate a keypair, sign a file, and break the signature (1h)

Goal: Prove a digital signature is bound to a specific file. Setup: Kali VM, work in ~/lab/week10/.

  1. Generate an RSA private key and inspect it: 

    mkdir -p ~/lab/week10 && cd ~/lab/week10
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.pem
chmod 600 private.pem                            # a key readable by anyone is not private
openssl pkey -in private.pem -text -noout        # see what you made
    You will see modulus, publicExponent, then prime1, prime2, exponent1… RSA's security rests on the fact that multiplying two large primes is easy, but factoring the product back into them is not. Everything else is derived from those two numbers. This is maths, not magic.

  2. Extract the public key: openssl rsa -in private.pem -pubout -out public.pem. It is the modulus plus the public exponent — safe to publish, and that is the point.

  3. Sign a file. Note what happened: OpenSSL hashed the file with SHA-256, then signed the hash. Signing the whole file would be slow and, for large files, impractical: 

    echo "Transfer 100 SAR to account 12345" > message.txt
openssl dgst -sha256 -sign private.pem -out message.sig message.txt
openssl dgst -sha256 -verify public.pem -signature message.sig message.txt   # Verified OK

  4. Now tamper — this is the moment the lab exists for: 

    echo "Transfer 100000 SAR to account 12345" > message.txt     # one extra digit
openssl dgst -sha256 -verify public.pem -signature message.sig message.txt   # Verification Failure
    A signature is bound to the exact bytes of the file. Because the hash has the avalanche property from Lab 10.1, any modification at all is detected.

  5. Try to forge a signature with only the public key. You cannot — signing requires private.pem. This is what non-repudiation means in practice.

Be precise, because this is where people overclaim. Non-repudiation is a property of the key, not the person. If the private key was stolen, shared, or generated on a compromised machine, non-repudiation collapses. Cryptography proves possession of a key — it does not prove who was sitting at the keyboard.

Deliverable: The Verified OK and Verification Failure outputs, and a paragraph answering: what does a valid signature actually prove, and what does it not prove?

Lab 10.5 — Watch ECB mode leak a picture (1h)

Goal: See why ECB is the textbook example of a mode you must never use. Setup: sudo apt install -y imagemagick. Work in ~/lab/week10/.

  1. Prepare an uncompressed image. ECB's weakness is visible in raw data, so you need an uncompressed format (BMP) — JPEG and PNG compress the data and destroy the pattern. Use dimensions that are multiples of 16 (like 512×512) so the demonstration is clean: 

    convert /usr/share/backgrounds/*.jpg -resize 512x512 -depth 8 -type TrueColor -colorspace sRGB flat.bmp
xxd flat.bmp | head -4      # a 24-bit BMP: 54-byte header, then raw pixel bytes
    We preserve the header and encrypt only the pixels — otherwise the image viewer refuses to open the result at all.

  2. Encrypt the pixels with ECB, then with CBC on the same data: 

    head -c 54 flat.bmp > header.bin
tail -c +55 flat.bmp | openssl enc -aes-128-ecb -nosalt \
  -K 00112233445566778899aabbccddeeff -out body-ecb.bin
cat header.bin body-ecb.bin > encrypted-ecb.bmp
tail -c +55 flat.bmp | openssl enc -aes-128-cbc -nosalt \
  -K 00112233445566778899aabbccddeeff \
  -iv 0102030405060708090a0b0c0d0e0f10 -out body-cbc.bin
cat header.bin body-cbc.bin > encrypted-cbc.bmp

  3. Open both. encrypted-cbc.bmp is visual noise. encrypted-ecb.bmp still shows the shape of the original image. Put the screenshot beside the original in your notes.

  4. Explain why, and write it down. ECB encrypts every 16-byte block independently with the same key, so two identical plaintext blocks produce two identical ciphertext blocks — the encryption is deterministic, any repetition in the plaintext survives, and that is what your eye picks up. CBC XORs each plaintext block with the previous ciphertext block before encrypting, so identical plaintext blocks encrypt differently and the pattern is destroyed. Neither provides integrity: an attacker can flip bits in a CBC ciphertext and predictably corrupt the next block. That is why modern systems use AEAD modes — AES-GCM, ChaCha20-Poly1305 — which encrypt and authenticate.
  5. Write the rule: ECB is not a "weaker option." It is a broken option for any data with structure — which is essentially all data.

⚠️ openssl enc is not your file-encryption tool. It is perfect for a demonstration, but its password-based mode uses a weak key-derivation function. For real file encryption use age, gpg, or full-disk encryption (LUKS) — a live example of this week's rule: use vetted tools the way they were designed to be used.

Deliverable: The three images side by side, your written explanation of why ECB leaks and CBC does not, and one sentence naming the mode class you would use in production and why.

الهدف: أن تلمس الفرق بين دالة التجزئة والشيفرة، لا أن تقرأ عنه. التهيئة: آلة Kali وهمية، Terminal فقط.

  1. تأثير الانهيار (Avalanche) — غيّر حرفاً واحداً وراقب كيف يتغيّر كل شيء: 

    echo -n "password"  | sha256sum
echo -n "Password"  | sha256sum
echo -n "password " | sha256sum
    يتغيّر ما يقارب نصف بتات المخرج مقابل تغيير بت واحد في المدخل. هذا ما يجعل دوال التجزئة مفيدة للتحقق من السلامة.

  2. الحتمية — الخاصية التي تجعل التجزئة بلا ملح خطرة. شغّل echo -n "password" | sha256sum مرتين: النتيجة متطابقة في المرتين. الآن فكّر في قاعدة بيانات كلمات مرور: كل مستخدم كلمة مروره password لديه نفس البصمة تماماً.

  3. التجزئة اتجاه واحد. شغّل echo -n "correct horse battery staple" | sha256sum، ثم حاول عكسها. لن تستطيع — لا لأن الأداة تفتقر إلى خيار، بل لأن المعلومة دُمِّرت فعلاً. مدخل من 60 حرفاً ومدخل من حرف واحد ينتجان 64 حرفاً سادس عشرياً في الحالتين: 

    echo -n "a" | sha256sum        # 64 hex chars
echo -n "a" | md5sum           # 32 hex chars

  4. السلامة عملياً. نزّل ملفاً من موقع ينشر بصماته، ثم: 

    sha256sum downloaded-file.iso
echo "<published-hash>  downloaded-file.iso" > check.txt   # exactly TWO spaces
sha256sum -c check.txt      # prints: OK
    انسخ الملف، وأفسد بايتاً واحداً بـ dd، ثم تحقّق مرة أخرى — سيفشل التحقق. هكذا تتحقق مديريات الحزم ونظام تشغيلك من أن شيئاً لم يُعدَّل أثناء النقل.

  5. الآن أثبت أن التجزئة ليست تشفيراً: 

    echo "password" > plain.txt
openssl enc -aes-128-cbc -nosalt -K 00112233445566778899aabbccddeeff \
  -iv 0102030405060708090a0b0c0d0e0f10 -in plain.txt -out cipher.bin

المختبر 10.2 — اكسر بصماتك أنت، وافهم لماذا توجد سياسة كلمات المرور (1.5 ساعة)

⚠️ حدّ قانوني — اقرأ هذا قبل أن تكتب أي شيء. يُسمح لك بكسر البصمات التي ولّدتها بنفسك فقط، على آلتك الوهمية، في هذا المختبر. هذا هو النطاق كاملاً. كسر بصمات كلمات مرور لا تملكها، أو لا تملك تصريحاً كتابياً صريحاً باختبارها، أو محاولة كسرها، جريمة جنائية في كل دولة تقريباً — بموجب قوانين إساءة استخدام الحاسوب في الولايات المتحدة والاتحاد الأوروبي والقوانين المكافئة في العالم العربي. عبارة "كانت على موقع وجدته" ليست تصريحاً. وعبارة "كانت في تسريب نزّلته" ليست تصريحاً. لا توجد منطقة رمادية هنا. الغرض من هذا المختبر أن تشعر بيديك لماذا تهم سياسة كلمات المرور — لتتمكن من الدفاع عنها بالدليل بدل ترديدها كقاعدة.

الهدف: قِس كم تموت كلمات المرور الضعيفة بسرعة، وكم تغيّر خوارزمية التخزين النتيجة.

التهيئة: آلة Kali وهمية. john و hashcat مثبَّتان مسبقاً. تأتي قائمة الكلمات rockyou في /usr/share/wordlists/rockyou.txt.gz — فُكّ ضغطها بـ sudo gunzip /usr/share/wordlists/rockyou.txt.gz.

  1. أنشئ ثلاث كلمات مرور تدريبية — لا كلمة مرور حقيقية تستخدمها في أي مكان: summer2024 (كلمة + سنة: أكثر نمط واقعي شيوعاً)، و Tr0ub4dor (كلمة باستبدال حروف)، وعبارة مرور طويلة عشوائية.

  2. ولّد البصمات بنفسك. أنت مؤلف كل بصمة في هذا المختبر: 

    for p in 'summer2024' 'Tr0ub4dor' 'correct-horse-battery-staple-9x'; do
  printf '%s' "$p" | sha256sum | awk '{print $1}'
done > raw-sha256.txt

  3. اكسرها، وقِس الزمن: 

    time john --format=raw-sha256 --wordlist=/usr/share/wordlists/rockyou.txt raw-sha256.txt
john --show --format=raw-sha256 raw-sha256.txt

  4. غيّر الخوارزمية وحدها، لا كلمة المرور. جزّئ نفس كلمة المرور الضعيفة بـ bcrypt واكسرها: 

    sudo apt install -y apache2-utils        # provides htpasswd
htpasswd -bnBC 10 "" 'summer2024' | tr -d ':\n' > bcrypt-pw.txt   # note the $2y$10$ prefix
time john --format=bcrypt --wordlist=/usr/share/wordlists/rockyou.txt bcrypt-pw.txt

  5. قارن وسجّل الأرقام. نفس كلمة المرور، نفس قائمة الكلمات، نفس الجهاز — والخوارزمية وحدها هي المختلفة. الفارق ليس بضعة في المئة؛ بل هو مراتب كاملة من القدر.

  6. قِس أداء عتادك أنت بدل أن تثق برقم من مقال — hashcat -b -m 0 (MD5)، و -m 1400 (SHA-256)، و -m 3200 (bcrypt). هذا هو الرقم الذي يفسّر كل شيء: المهاجم لا يحتاج مهارة، بل يحتاج سرعة فقط. وعندما تسمح دالة تجزئة سريعة بمليارات التخمينات في الثانية، يبقى طول كلمة المرور هو الدفاع الوحيد المتبقي.
  7. شاهد الملح في الملف نفسه. شغّل openssl passwd -6 'summer2024' مرتين — المخرجات تختلف، لأن -6 (SHA-512 crypt) يولّد ملحاً عشوائياً في كل مرة ويخزّنه مع البصمة. مستخدمان بنفس كلمة المرور لديهما الآن قيمتان مخزَّنتان مختلفتان، فصار جدول قوس المطر المحسوب مسبقاً عديم الفائدة.

المخرج المطلوب: جدول يضم كلمة المرور، والخوارزمية، وزمن الكسر، وعدد البصمات في الثانية في القياس. بالإضافة إلى فقرة واحدة: اكتب سياسة كلمات المرور التي ستنصح بها منشأة صغيرة، وبرّر كل قاعدة ببياناتك المقيسة أنت.

المختبر 10.3 — افحص شهادة TLS حقيقية وفُكّ ترميز كل حقل فيها (1.5 ساعة)

الهدف: توقّف عن التعامل مع القفل (padlock) كأنه سحر. التهيئة: آلة Kali وهمية متصلة بالإنترنت، والهدف example.com (و www.wikipedia.org أو github.com يعملان أيضاً).

  1. اتصل واستخرج الشهادة: 
    openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

    لماذا -servername؟ لأنه يرسل اسم المضيف داخل المصافحة (SNI — Server Name Indication). بدونه، لا يعرف الخادم الذي يستضيف مواقع كثيرة أي شهادة يقدّم، فتحصل على الشهادة الخطأ. هذا الأمر يربك المتعلمين باستمرار.

  2. فُكّ ترميز الشهادة الطرفية: 

    openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -text

  3. اشرح كل حقل في ملاحظاتك — وهذا هو المخرج الحقيقي:

الحقل ما يعنيه
Version دائماً تقريباً v3. الصيغة هي X.509؛ و v3 أضافت الإضافات (extensions)
Serial Number فريد لكل جهة إصدار — وهو ما تشير إليه قائمة الإبطال
Signature Algorithm ما استخدمته جهة الإصدار لتوقيع هذه الشهادة، مثل sha256WithRSAEncryption
Issuer / Subject من وقّعها (جهة الإصدار CA) ولمن هي. الحقول C و O و CN
Validity Not Before / Not After. خارج هذه النافذة تكون الشهادة غير صالحة حتى لو كانت موقَّعة بإتقان
Subject Public Key Info المفتاح العام الذي تُشهد له، مع الخوارزمية والحجم (RSA 2048/4096 أو منحنى EC)
Subject Alternative Name أسماء المضيفين التي تغطيها هذه الشهادة. المتصفحات تتجاهل CN تماماً وتطابق على SAN — وهكذا تغطي شهادة واحدة example.com و www.example.com
Basic Constraints: CA: TRUE تعني أنها قد توقّع شهادات أخرى. ويجب أن تقول الشهادة الطرفية FALSE
Key Usage / Extended Key Usage ما يُسمح باستخدام المفتاح له، مثل TLS Web Server Authentication
Subject / Authority Key Identifier بصمتان: بصمة مفتاح هذه الشهادة وبصمة مفتاح جهة الإصدار — وهما حلقتا السلسلة
Authority Information Access / CRL Distribution Points أين تجد شهادة جهة الإصدار، ومستجيب OCSP، وقائمة الإبطال
Signature Value توقيع جهة الإصدار الفعلي على كل ما سبق

  1. تتبّع السلسلة إلى الجذر: 

    openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null \
  | grep -E "^ *[0-9]+ s:|^ *i:"
grep -c "BEGIN CERTIFICATE" /etc/ssl/certs/ca-certificates.crt    # count your trusted roots
    سترى الشهادة الطرفية (الموقع) → الشهادة الوسيطة → الشهادة الجذرية. يرسل الخادم عادةً الشهادة الطرفية والوسيطة لكن لا يرسل الجذرية — فالعميل يملكها أصلاً. ملف .crt هذا هو أساس الثقة كله على جهازك: الشهادة ليست "صالحة" إلا لأن سلسلة توقيعات تؤدي إلى أحد مدخلات ذلك الملف.

  2. اقرأ التواريخ والموضوع وجهة الإصدار بـ -noout -dates -subject -issuer، ولاحظ كم صار نافذة الصلاحية قصيرة في الشهادات الحديثة — فالعمر القصير يحدّ من ضرر مفتاح مسروق.

  3. افرض فشل التحقق واقرأ الخطأ. احفظ شهادة بـ openssl x509 > site.pem، ثم شغّل openssl verify -CAfile /dev/null site.pem. رسالة unable to get local issuer certificate تعني: لا أستطيع تتبّع هذه الشهادة إلى أي طرف أثق به. وهذه بالضبط هي الرسالة التي يحوّلها المتصفح إلى صفحة تحذير — وبالضبط هي الرسالة التي ينقر المستخدمون عليها ويتجاوزونها.

المخرج المطلوب: ملاحظاتك تشرح كل حقل في الخطوة 3 بأسلوبك، ومخرجات السلسلة مع تحديد الجذر، وعدد الجذور الموثوقة على نظامك، وخطأ الخطوة 6 مع شرح من جملة واحدة لمستخدم غير تقني.

المختبر 10.4 — ولّد زوج مفاتيح، وقّع ملفاً، ثم اكسر التوقيع (1 ساعة)

الهدف: أثبت أن التوقيع الرقمي مرتبط بملف بعينه. التهيئة: آلة Kali وهمية، واعمل داخل ~/lab/week10/.

  1. ولّد مفتاحاً خاصاً RSA وافحصه: 

    mkdir -p ~/lab/week10 && cd ~/lab/week10
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.pem
chmod 600 private.pem                            # a key readable by anyone is not private
openssl pkey -in private.pem -text -noout        # see what you made
    سترى modulus و publicExponent، ثم prime1 و prime2 و exponent1… أمن RSA يقوم على أن ضرب عددين أوليين كبيرين سهل، لكن تحليل الناتج عائداً إلى العددين الأوليين ليس سهلاً. وكل ما عداهما مشتق منهما. هذه رياضيات، لا سحر.

  2. استخرج المفتاح العام: openssl rsa -in private.pem -pubout -out public.pem. إنه المعامل (modulus) زائد الأس العام — يُنشر بأمان، وهذا هو المقصود.

  3. وقّع ملفاً. لاحظ ما حدث: قام OpenSSL بـ تجزئة الملف بـ SHA-256، ثم وقّع البصمة. أما توقيع الملف كاملاً فسيكون بطيئاً، وغير عملي مع الملفات الكبيرة: 

    echo "Transfer 100 SAR to account 12345" > message.txt
openssl dgst -sha256 -sign private.pem -out message.sig message.txt
openssl dgst -sha256 -verify public.pem -signature message.sig message.txt   # Verified OK

  4. الآن عبث بالمحتوى — هذه هي اللحظة التي وُجد المختبر من أجلها: 

    echo "Transfer 100000 SAR to account 12345" > message.txt     # one extra digit
openssl dgst -sha256 -verify public.pem -signature message.sig message.txt   # Verification Failure
    التوقيع مرتبط بالبايتات المحددة للملف. ولأن البصمة تملك خاصية الانهيار من المختبر 10.1، فأي تعديل مهما كان صغيراً يُكتشف.

  5. حاول تزوير توقيع بالمفتاح العام وحده. لن تستطيع — فالتوقيع يتطلب private.pem. وهذا هو معنى عدم الإنكار عملياً.

كن دقيقاً، لأن هنا يتجاوز الناس حدود الدقة. عدم الإنكار خاصية المفتاح، لا خاصية الشخص. فإن سُرِق المفتاح الخاص أو شُورِك أو وُلِّد على جهاز مخترَق — ينهار عدم الإنكار بالكامل. التشفير يثبت حيازة مفتاح — ولا يثبت من كان يجلس أمام لوحة المفاتيح.

المخرج المطلوب: مخرجات Verified OK و Verification Failure، وفقرة تجيب عن: ما الذي يثبته التوقيع الصالح فعلاً، وما الذي لا يثبته؟

المختبر 10.5 — شاهد نمط ECB يسرّب صورة (1 ساعة)

الهدف: افهم لماذا ECB هو المثال النموذجي لنمط يجب ألا تستخدمه أبداً. التهيئة: sudo apt install -y imagemagick. واعمل داخل ~/lab/week10/.

  1. جهّز صورة غير مضغوطة. ضعف ECB يظهر في البيانات الخام، لذا تحتاج صيغة غير مضغوطة (BMP) — فـ JPEG و PNG يضغطان البيانات ويدمّران النمط. استخدم أبعاداً من مضاعفات 16 (مثل 512×512) ليكون العرض نظيفاً: 

    convert /usr/share/backgrounds/*.jpg -resize 512x512 -depth 8 -type TrueColor -colorspace sRGB flat.bmp
xxd flat.bmp | head -4      # a 24-bit BMP: 54-byte header, then raw pixel bytes
    نحتفظ بالترويسة ونشفّر البكسلات وحدها — وإلا رفض عارض الصور فتح الناتج أصلاً.

  2. شفّر البكسلات بـ ECB، ثم بـ CBC على نفس البيانات: 

    head -c 54 flat.bmp > header.bin
tail -c +55 flat.bmp | openssl enc -aes-128-ecb -nosalt \
  -K 00112233445566778899aabbccddeeff -out body-ecb.bin
cat header.bin body-ecb.bin > encrypted-ecb.bmp
tail -c +55 flat.bmp | openssl enc -aes-128-cbc -nosalt \
  -K 00112233445566778899aabbccddeeff \
  -iv 0102030405060708090a0b0c0d0e0f10 -out body-cbc.bin
cat header.bin body-cbc.bin > encrypted-cbc.bmp

  3. افتح الاثنتين. encrypted-cbc.bmp تشويش بصري. أما encrypted-ecb.bmp فـ لا تزال تُظهر شكل الصورة الأصلية. ضع لقطة الشاشة بجانب الأصل في ملاحظاتك.

  4. اشرح السبب، واكتبه. ECB يشفّر كل كتلة من 16 بايت باستقلال وبنفس المفتاح، فكتلتان متطابقتان من النص الصريح تنتجان كتلتين متطابقتين من النص المشفَّر — أي أن التشفير حتمي، وأي تكرار في النص الصريح يبقى ظاهراً، وهذا ما تلتقطه عينك. أما CBC فيطبّق XOR بين كل كتلة نص صريح وكتلة النص المشفَّر السابقة قبل التشفير، فتُشفَّر الكتل المتطابقة بشكل مختلف ويتدمّر النمط. ولا أحد منهما يوفر السلامة: يستطيع مهاجم قلب بتات في نص مشفَّر بـ CBC وإفساد الكتلة التالية بشكل متوقع. لهذا تستخدم الأنظمة الحديثة أنماط AEAD — AES-GCM و ChaCha20-Poly1305 — التي تشفّر وتصادق في الوقت نفسه.
  5. اكتب القاعدة: ECB ليس "خياراً أضعف". إنه خيار مكسور لأي بيانات ذات بنية — أي كل البيانات عملياً.

⚠️ openssl enc ليس أداة تشفير ملفاتك. هو ممتاز للعرض التمثيلي، لكن نمطه القائم على كلمة مرور يستخدم دالة اشتقاق مفاتيح ضعيفة. لتشفير ملفات حقيقي استخدم age أو gpg أو تشفير القرص الكامل (LUKS) — مثال حي على قاعدة هذا الأسبوع: استخدم أدوات مُدقَّقة بالطريقة التي صُمّمت لتُستخدم بها.

المخرج المطلوب: الصور الثلاث جنباً إلى جنب، وشرحك المكتوب لسبب تسريب ECB وعدم تسريب CBC، وجملة واحدة تسمّي صنف النمط الذي ستستخدمه في بيئة الإنتاج ولماذا.

  • اشرح TLS لشخص غير تقني في 200 كلمة. بلا مصطلحات: لا "غير متماثل"، ولا "تجزئة"، ولا "جهة إصدار الشهادات". تشبيهات فقط. وإن لم تستطع، فأنت لا تفهمه جيداً بما يكفي للدفاع عنه في اجتماع — والدفاع عن قرارات التشفير أمام مديرين غير تقنيين جزء حقيقي من هذه المهنة.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

Crypto is where security stops being a matter of opinion.

Everywhere else you can argue. Was that firewall rule necessary? Is that risk acceptable? Reasonable professionals disagree. Cryptography is different: either the maths holds or it does not. That is why sloppiness here is unforgivable — and why the same failures repeat decade after decade.

Failure 1: "We hashed the passwords." — the sentence that means nothing

The most common false sense of security in the industry. Hashing passwords is table stakes; it is also the beginning of the question, not the answer. Ask three follow-ups, in this order:

  1. Which hash? If the answer is MD5 or SHA-1, the passwords are effectively plaintext — not because someone can reverse the hash (they cannot, and that nuance matters) but because these algorithms are designed to be fast. Lab 10.2 gave you the number yourself: billions of guesses per second.
  2. Is it salted? Unsalted hashes mean every user with the same password has an identical stored value. Crack one, own them all — and a precomputed rainbow table lets you crack them before you even start. Salting does not make a weak password strong. It makes precomputation useless and makes cracking a database as expensive as cracking each password individually.
  3. Is it slow? The correct algorithms — Argon2id, scrypt, bcrypt — are deliberately, tunably slow, and (for Argon2 and scrypt) memory-hungry. A legitimate login takes ~100 milliseconds and nobody notices; an attacker making billions of guesses takes centuries instead of seconds. OWASP currently ranks Argon2id first, scrypt second, and bcrypt as a legacy option.

The counter-intuitive lesson that takes people years to absorb: a good hash function is not a good password hash. SHA-256 is an excellent hash and a terrible password storage algorithm. Speed is a virtue for integrity checking and a catastrophe for password storage. Algorithms are not "strong" or "weak" in the abstract — they are appropriate or inappropriate for a purpose.

Failure 2: "We encrypted it." — the sentence with a missing half

Encryption without integrity is a trap. A ciphertext that can be silently modified is worse than useless, because it produces confident wrong answers instead of errors — exactly what Lab 10.5 showed you with CBC. The modern answer is authenticated encryption (AEAD): AES-GCM and ChaCha20-Poly1305 encrypt and attach a tag proving the data was not altered; if the tag fails, decryption is refused. Never use a mode without authentication on data you care about — and never invent your own way of combining encryption and authentication. Experts have gotten that combination wrong repeatedly; it is not a place for improvisation.

Failure 3: the certificate error — and why everyone clicks through

Lab 10.3 had you read unable to get local issuer certificate and translate it. That error means one thing: the chain of trust broke — the certificate is not signed by anyone your machine trusts, or it expired, or the name does not match. In a well-run environment that means something is genuinely wrong: an expired certificate on a load balancer, a misconfiguration, or an attacker intercepting your traffic with a forged certificate.

But users click through certificate warnings because warnings are noise. They have clicked through a hundred expired-certificate warnings caused by lazy server administration, so the one time it matters looks identical to the ninety-nine that did not. That is a security usability failure, not a user intelligence failure — and understanding the distinction is a mark of a professional. The defence is not "train users better"; it is HSTS (making browsers refuse plain HTTP entirely, so downgrade attacks fail) and certificate pinning in applications. When you design a system, your job is to make the secure path the easy path — because the insecure path is always the one people take at 5pm on a Friday.

Failure 4: weak randomness — the failure nobody sees coming

Every key, session token, password-reset link, and nonce depends on randomness. If the randomness is predictable, everything built on it collapses — and it collapses silently. The encryption is mathematically perfect; the key was just guessable. The pattern is always the same: someone uses a general-purpose random function, or a timestamp, or a counter, because it "looks random" and is convenient. This has caused real, high-profile breaks, including session tokens predictable by observing a previous one.

The rule is absolute: use a cryptographically secure random number generator (/dev/urandom, or the CSPRNG in your language's crypto library — secrets in Python, crypto.randomBytes in Node). Never a general-purpose random function for anything security-related. Never a timestamp. Never a counter. This is why the picoCTF challenge Timestamped Secrets exists: the lesson is not about the cipher at all — a perfect cipher with a predictable key is not encryption, it is obfuscation.

Failure 5: rolling your own

Every failure above happened to teams with good engineers under real deadlines. That is the entire argument.

Cryptography is the one area of this field where the expert consensus is that you should not build, modify, or hand-assemble primitives — and you should be suspicious of anyone who wants to. Not because writing code that produces encrypted output is hard; that part is easy, and that is the trap. It is hard because the failures are invisible. Broken crypto looks exactly like working crypto. It passes every test where you encrypt, decrypt, and see your data. It only fails when an attacker who knows what they are doing shows up — and by then the data is gone.

The professional rule, which you should be able to recite: use a well-maintained, widely-audited library. Use it the way its documentation tells you to. Use it for the purpose it was designed for. Do not implement a primitive from a description. Do not invent a combination of primitives. Do not "improve" an algorithm. And if you ever think "I'll just do my own version of this" — stop, and read the documentation again.

At rest and in transit — both, not either

  • In transit protects data moving across a network. That is TLS, and it is why HTTPS matters. Without it, anyone on the same Wi-Fi — a café, an airport, a hotel — can read and modify your traffic.
  • At rest protects data sitting on a disk. That is full-disk encryption, encrypted database columns, or encrypted backups. Without it, a stolen laptop, a discarded drive, or a misconfigured backup bucket is a full data breach.

A system can be encrypted in transit and completely exposed at rest, or vice versa, and both count as breaches. When you assess a system, ask about both — then ask the third question most people miss: where do the keys live? Encryption with the key stored next to the data protects you from exactly nothing.

التشفير هو النقطة التي يتوقف عندها الأمن عن كونه مسألة رأي.

في كل مجال آخر يمكنك أن تجادل. هل كانت قاعدة الجدار الناري تلك ضرورية؟ هل هذا الخطر مقبول؟ مهنيون عقلاء يختلفون. أما التشفير فمختلف: إما أن تصمد الرياضيات أو لا تصمد. لهذا لا يُغتفر الإهمال هنا — ولهذا تتكرر الإخفاقات نفسها عقداً بعد عقد.

الإخفاق 1: "جزّأنا كلمات المرور." — الجملة التي لا تعني شيئاً

أكثر شعور زائف بالأمان شيوعاً في المجال. تجزئة كلمات المرور هي الحد الأدنى؛ وهي أيضاً بداية السؤال لا جوابه. اسأل ثلاثة أسئلة متابعة، بهذا الترتيب:

  1. أي دالة تجزئة؟ إن كان الجواب MD5 أو SHA-1، فكلمات المرور عملياً نص صريح — لا لأن أحداً يستطيع عكس البصمة (لا يستطيع، وهذه الدقة مهمة) بل لأن هذه الخوارزميات مصمَّمة لتكون سريعة. المختبر 10.2 أعطاك الرقم بنفسك: مليارات التخمينات في الثانية.
  2. هل هي مملَّحة؟ التجزئة بلا ملح تعني أن كل مستخدم بنفس كلمة المرور لديه قيمة مخزَّنة متطابقة. اكسر واحدة تملك الجميع — وجدول قوس المطر المحسوب مسبقاً يتيح كسرها قبل أن تبدأ أصلاً. الملح لا يجعل كلمة المرور الضعيفة قوية. إنه يُبطل الحساب المسبق، ويجعل كسر قاعدة بيانات مكلفاً بقدر كسر كل كلمة مرور على حدة.
  3. هل هي بطيئة؟ الخوارزميات الصحيحة — Argon2id و scrypt و bcrypt — بطيئة عمداً وبشكل قابل للضبط، وشرهة للذاكرة (في Argon2 و scrypt). تسجيل دخول شرعي يستغرق ~100 مللي ثانية ولا يلاحظه أحد؛ أما مهاجم يجرّب مليارات التخمينات فيستغرق قروناً بدل ثوانٍ. وتصنّف OWASP حالياً Argon2id أولاً، و scrypt ثانياً، و bcrypt كخيار قديم.

الدرس المخالف للحدس الذي يستغرق الناس سنوات لاستيعابه: دالة التجزئة الجيدة ليست دالة تجزئة كلمات مرور جيدة. SHA-256 دالة تجزئة ممتازة وخوارزمية تخزين كلمات مرور كارثية. السرعة فضيلة في التحقق من السلامة وكارثة في تخزين كلمات المرور. الخوارزميات ليست "قوية" أو "ضعيفة" في المطلق — إنها مناسبة لغرض أو غير مناسبة له.

الإخفاق 2: "شفّرناها." — الجملة الناقصة النصف

التشفير بلا سلامة فخ. فالنص المشفَّر القابل للتعديل بصمت أسوأ من عديم الفائدة، لأنه ينتج أجوبة خاطئة واثقة بدل أن ينتج أخطاء — وهذا بالضبط ما أظهره لك المختبر 10.5 مع CBC. والجواب الحديث هو التشفير الموثَّق (AEAD): AES-GCM و ChaCha20-Poly1305 يشفّران ويرفقان وسمة (tag) تثبت أن البيانات لم تُعدَّل؛ فإن فشلت الوسمة رُفض فك التشفير. لا تستخدم نمطاً بلا مصادقة على بيانات تهمك — ولا تخترع طريقتك الخاصة في الجمع بين التشفير والمصادقة. أخطأ الخبراء في هذه التركيبة مراراً؛ فهي ليست موضعاً للارتجال.

الإخفاق 3: خطأ الشهادة — ولماذا ينقر الجميع ويتجاوزونه

طلب منك المختبر 10.3 أن تقرأ unable to get local issuer certificate وتترجمها. هذا الخطأ يعني شيئاً واحداً: انكسرت سلسلة الثقة — فالشهادة ليست موقَّعة من طرف يثق به جهازك، أو انتهت صلاحيتها، أو أن الاسم لا يطابق. وفي بيئة مُدارة جيداً يعني ذلك أن هناك خللاً حقيقياً: شهادة منتهية على موازن تحميل (load balancer)، أو خطأ إعداد، أو مهاجم يعترض حركتك بشهادة مزوَّرة.

لكن المستخدمين ينقرون على تحذيرات الشهادات ويتجاوزونها لأن التحذيرات صارت ضجيجاً. فقد تجاوزوا مئة تحذير شهادة منتهية سببها إهمال إداري، فباتت المرة الوحيدة التي تهم مطابقة بصرياً للتسع والتسعين التي لم تهم. هذا فشل في قابلية الاستخدام، لا فشل في ذكاء المستخدم — وإدراك هذا الفرق علامة على المهنية. والدفاع ليس "درّب المستخدمين أفضل"؛ إنه HSTS (بجعل المتصفحات ترفض HTTP الصريح تماماً فتفشل هجمات التخفيض) والتثبيت (certificate pinning) في التطبيقات. وعندما تصمّم نظاماً، فمهمتك أن تجعل المسار الآمن هو المسار السهل — لأن المسار غير الآمن هو الذي سيسلكه الناس دائماً في الخامسة مساء يوم جمعة.

الإخفاق 4: عشوائية ضعيفة — الإخفاق الذي لا يتوقعه أحد

كل مفتاح، ورمز جلسة، ورابط إعادة تعيين كلمة المرور، و nonce يعتمد على العشوائية. فإن كانت العشوائية قابلة للتوقع انهار كل ما بُني عليها — وينهار بصمت. التشفير سليم رياضياً؛ المفتاح وحده هو الذي كان قابلاً للتخمين. والنمط دائماً واحد: يستخدم أحدهم دالة عشوائية عامة الغرض، أو طابعاً زمنياً (timestamp)، أو عدّاداً، لأنها "تبدو عشوائية" ومريحة. وقد سبّبت هذه إخفاقات حقيقية بارزة، منها رموز جلسة صار يمكن توقعها بمراقبة رمز سابق.

والقاعدة مطلقة: استخدم مولّد أرقام عشوائية آمناً تشفيرياً (/dev/urandom، أو الـ CSPRNG في مكتبة التشفير الخاصة بلغتك — secrets في Python، و crypto.randomBytes في Node). ولا تستخدم دالة عشوائية عامة الغرض لأي شيء أمني أبداً. ولا طابعاً زمنياً. ولا عدّاداً. ولهذا يوجد تحدي picoCTF المسمى Timestamped Secrets: الدرس ليس عن الشيفرة إطلاقاً — فشيفرة مثالية بمفتاح قابل للتوقع ليست تشفيراً، بل تمويهاً.

الإخفاق 5: كتابة التشفير بنفسك

كل إخفاق سبق حدث لفرق تضم مهندسين جيدين تحت مواعيد تسليم حقيقية. وهذه هي الحجة كاملة.

التشفير هو المجال الوحيد في هذا الميدان الذي يكون فيه إجماع الخبراء على أنك لا تبني العناصر التشفيرية ولا تعدّلها ولا تجمعها يدوياً — وأن تشك في كل من يريد ذلك. لا لأن كتابة كود يُنتج مخرجات مشفَّرة صعبة؛ فهذا الجزء سهل، وهنا يكمن الفخ. بل لأن الإخفاقات غير مرئية. فالتشفير المكسور يبدو تماماً كالتشفير العامل. ينجح في كل اختبار تشفّر فيه وتفكّ التشفير فترى بياناتك. ولا يفشل إلا عندما يظهر مهاجم يعرف ما يفعله — وعندها تكون البيانات قد ذهبت.

والقاعدة المهنية، التي يجب أن تكون قادراً على ترديدها: استخدم مكتبة مُصانة جيداً ومُدقَّقة على نطاق واسع. واستخدمها بالطريقة التي تقولها وثائقها. واستخدمها للغرض الذي صُمّمت له. لا تُنفّذ عنصراً تشفيرياً من وصف. لا تخترع تركيبة من العناصر. لا "تحسّن" خوارزمية. وإن خطر لك يوماً "سأعمل نسختي الخاصة من هذا" — فتوقف، واقرأ الوثائق مرة أخرى.

في التخزين وأثناء النقل — كلاهما، لا أحدهما

  • أثناء النقل يحمي البيانات المنتقلة عبر الشبكة. وذلك هو TLS، ولهذا يهم HTTPS. وبدونه، يستطيع أي شخص على نفس شبكة Wi-Fi — مقهى، مطار، فندق — قراءة حركتك وتعديلها.
  • في التخزين يحمي البيانات الجاثمة على القرص. وذلك هو تشفير القرص الكامل، أو أعمدة قاعدة بيانات مشفّرة، أو نسخ احتياطية مشفّرة. وبدونه، حاسوب محمول مسروق أو قرص مُهمَل أو دلو نسخ احتياطي سيئ الإعداد يساوي اختراقاً كاملاً للبيانات.

يمكن أن يكون النظام مشفَّراً أثناء النقل ومكشوفاً تماماً في التخزين، أو العكس، وكلاهما يُحتسب اختراقاً. وعندما تقيّم نظاماً، اسأل عن الاثنين — ثم اسأل السؤال الثالث الذي ينساه معظم الناس: أين تُخزَّن المفاتيح؟ تشفير مع تخزين المفتاح بجانب البيانات = لا حماية على الإطلاق.

أخطر التباس في المجال كله. المبتدئ يرى نصاً مشوّهاً فيظنه "مشفّراً"، بينما هو مجرد ترميز لا يحمي شيئاً:

التشبيهات التي تحسم الأمر:

1. الترميز = كتابة العربية بحروف إنجليزية (Arabizi). لو كتبت "مرحبا" هكذا marhaba — هل أخفيت المعنى؟ لا. غيّرت طريقة الكتابة فقط، وأي شخص يعرف القاعدة يقرؤها فوراً. الترميز ليس أماناً، بل وسيلة لنقل البيانات عبر أنظمة لا تقبل بعض الرموز. عندما ترى SGVsbG8= وتظن أنك "شفّرت" شيئاً — فأنت لم تفعل. هذه Base64، وعكسها متاح للجميع.

2. التجزئة = بصمة الإصبع أو عصر الفاكهة. لو أعطيتك بصمة إصبع، هل تستطيع إعادة بناء الشخص منها؟ لا. هذه هي التجزئة: اتجاه واحد.

  • عصير الفاكهة: لا يمكنك استرجاع التفاحة من العصير. لكن نفس التفاحة تُنتج دائماً نفس العصير — وهذا بالضبط ما يجعل التجزئة بلا "ملح" خطيرة.
  • بصمة الإصبع: ثابتة للشخص نفسه، وقصيرة جداً مقارنة بحجمه. كذلك التجزئة: ثابتة الطول (64 حرفاً في SHA-256) مهما كان حجم المدخل.

3. التشفير = خزنة بمفتاح. المحتوى موجود بالكامل لكنه مقفل. من يملك المفتاح يراه، ومن لا يملكه لا يراه. وهو الإجراء الوحيد من الثلاثة الذي يحقق السرية.

قاعدة تذكّرها دائماً: إذا استطاع أي شخص عكس العملية بدون مفتاح — فهو ترميز وليس تشفيراً. وإذا لم يكن هناك عكس إطلاقاً — فهي تجزئة. وإذا تطلّب العكس مفتاحاً — فهذا تشفير.

التشفير المتماثل وغير المتماثل — مفتاح واحد أم مفتاحان؟

المتماثل (Symmetric) غير المتماثل (Asymmetric)
عدد المفاتيح مفتاح واحد مفتاحان: عام وخاص
السرعة سريع جداً بطيء (أبطأ بمئات المرات)
أمثلة AES · ChaCha20 RSA · ECC
المشكلة الأساسية توزيع المفتاح بطء شديد للبيانات الكبيرة
الاستخدام الفعلي تشفير البيانات نفسها تبادل المفاتيح · التوقيعات · الشهادات

مشكلة توزيع المفتاح، بمثال ملموس: أنت وأحمد تريدان التواصل سراً. التشفير المتماثل يحتاج أن كليكما يملك نفس المفتاح. حسناً — كيف تُوصل المفتاح لأحمد؟ إن أرسلته في رسالة فقد يقرؤه من يعترضها، وعندها انتهى كل شيء. وإن كان لديكما قناة آمنة أصلاً لتوصيل المفتاح — فلماذا تحتاج التشفير من الأساس؟ هذه حلقة مفرغة حقيقية.

الحل — تشبيه صندوق البريد: أي شخص في المدينة يستطيع إلقاء رسالة في الفتحة (المفتاح العام — منشور للجميع). لكن مفتاح فتح الصندوق لا يملكه إلا صاحب الصندوق (المفتاح الخاص — سرّي دائماً). الآن يستطيع أحمد أن يرسل لك سراً دون أن تلتقيا مسبقاً ودون تبادل أي سر. هذا هو حل مشكلة توزيع المفتاح.

كيف يعمل TLS بالاثنين معاً؟ أهم نقطة في الأسبوع: (1) غير المتماثل في البداية فقط — للتحقق من هوية الخادم عبر الشهادة وتبادل مفتاح جلسة جديد. (2) المتماثل (AES) لتشفير كل البيانات الفعلية — لأنه أسرع بمئات المرات.

الخلاصة: غير المتماثل يحل توزيع المفتاح لكنه بطيء؛ المتماثل سريع لكنه يحتاج مفتاحاً مشتركاً. TLS يجمع الاثنين: غير متماثل مرة واحدة في البداية، ثم متماثل لكل ما بعده. هذا التصميم الذكي هو ما يجعل الإنترنت ممكناً.

التجزئة بعمق: SHA-256 و MD5 وكيف "تُكسر" الدوال

الخاصية المعنى
أحادية الاتجاه لا يمكن استرجاع المدخل من المخرج
ثابتة الطول أي مدخل → مخرج بطول ثابت (SHA-256 = 256 بت)
حساسية فائقة (Avalanche) تغيير حرف واحد يغيّر نصف البتات
حتمية نفس المدخل → نفس المخرج دائماً

ما معنى أن MD5 "مكسورة" بالضبط؟ هنا دقة ضرورية:

المفهوم المعنى حالة MD5
مقاومة ما قبل الصورة (Preimage) إيجاد مدخل من مخرجه ⚠️ لم تُكسر عملياً
مقاومة التصادم (Collision) إيجاد مدخلين مختلفين بنفس المخرج ❌ مكسورة تماماً

الترجمة العملية: لا تستطيع أن تأخذ بصمة MD5 وتستعيد كلمة المرور منها. لكن تستطيع أن تصنع ملفين مختلفين تماماً لهما نفس البصمة — وقد حدث هذا فعلاً واستُخدم في هجمات حقيقية. لماذا لا تزال MD5 في كل مكان؟ التوافق مع أنظمة قديمة عمرها 20 سنة · استخدامات غير أمنية (كشف تلف قرص عارض، حيث MD5 كافٍ) · الجهل — وهو السبب الأكثر شيوعاً.

لكن السبب الأهم لتجنّب MD5 و SHA-1 في كلمات المرور ليس التصادم — بل السرعة. فهما مصمَّمتان لتكونا سريعتين، والسرعة عدوّ كلمات المرور. لهذا نستخدم دوال مصمَّمة لتكون بطيئة: bcrypt · scrypt · Argon2.

الملح (Salt) — لماذا التجزئة بلا ملح كارثة

الملح = قيمة عشوائية فريدة تُضاف لكل كلمة مرور قبل تجزئتها، وتُخزَّن بجانب البصمة. الملح ليس سراً — وظيفته ليست السرية. بدونه، أحمد وسارة بكلمة المرور password123 لهما نفس البصمة تماماً: اكسر واحدة تكسر الاثنتين. ماذا يمنع الملح؟ جداول قوس المطر (Rainbow Tables) — جداول جاهزة بملايين البصمات المحسوبة مسبقاً تصبح كلها بلا قيمة — والهجمات الجماعية، إذ يصبح كسر كل كلمة مرور جهداً مستقلاً.

⚠️ وماذا لا يمنع؟ الملح لا يجعل كلمة مرور ضعيفة قوية. إذا كانت كلمة المرور 123456 فستُكسر حتى مع الملح. الملح يمنع إعادة الاستخدام، ولا يعوّض عن ضعف كلمة المرور ولا عن خوارزمية بطيئة.

تخزين كلمات المرور: الصواب مقابل الخطأ

❌ خطأ فادح ⚠️ مقبول بشروط ✅ الصحيح
نص صريح (plaintext) SHA-256/SHA-512 + ملح Argon2id (الخيار الأول)
MD5 (بملح أو بدونه) PBKDF2 (عند اشتراط FIPS) scrypt (البديل الأول)
SHA-1 · SHA-256 بلا ملح bcrypt (للأنظمة القديمة، بمعامل عمل ≥ 10) bcrypt

لماذا هذه الثلاثة بالذات؟ لأنها مصمَّمة لتكون بطيئة ومكلفة، وبطؤها قابل للضبط: Argon2 تستهلك ذاكرة كبيرة + تمريرات + توازٍ (فائزة مسابقة تجزئة كلمات المرور 2015) · scrypt ذاكرة (N) + حجم كتلة (r) + توازٍ (p) · bcrypt معامل العمل، وكل زيادة تضاعف الزمن (أقصى طول مدخل 72 بايت).

النتيجة: تسجيل دخول شرعي يأخذ 100 مللي ثانية — لا يلاحظه أحد. المهاجم يحاول مليارات التخمينات — فيستغرق قروناً بدل ثوانٍ. البطء هنا ليس عيباً، بل هو الميزة كلها.

التوقيعات الرقمية وشهادات PKI

التوقيع الرقمي = تجزئة الملف + تشفير تلك التجزئة بالمفتاح الخاص. للتحقق يفكّ الجميع التجزئة بالمفتاح العام ويقارنونها. يثبت: ✅ السلامة (لم يُعدَّل الملف بحرف) · ✅ الأصالة (صادر من مالك المفتاح الخاص) · ✅ عدم الإنكار.

دقة ضرورية: عدم الإنكار خاصية المفتاح، لا الشخص. إذا سُرِق المفتاح الخاص أو شاركه صاحبه أو وُلِّد على جهاز مخترَق — ينهار عدم الإنكار بالكامل. التشفير يثبت حيازة مفتاح، لا من كان أمام الشاشة.

سلسلة الثقة: الشهادة الجذرية (Root CA) — مخزّنة مسبقاً في نظامك وموثوقة ضمنياً → توقّع → الشهادة الوسيطة (Intermediate CA) → توقّع → شهادة الموقع (Leaf).

كيف يتحقق المتصفح؟ يصعد في السلسلة حتى يصل إلى شهادة جذرية موجودة في مخزنه. إن وصل ✅، وإن لم يصل → تحذير. ويسأل أربعة أسئلة: (1) هل تنتهي السلسلة إلى جذر موثوق؟ → وإلا unable to get local issuer certificate · (2) هل التاريخ داخل فترة الصلاحية؟ → وإلا "الشهادة منتهية" · (3) هل اسم النطاق مطابق لـ SAN؟ (المتصفحات الحديثة تتجاهل CN تماماً) → وإلا "عدم تطابق الاسم" · (4) هل الشهادة مُبطَلة (OCSP / CRL)؟

لماذا ينقر المستخدمون على التحذير ويتجاوزونه؟ لأن التحذيرات صارت ضجيجاً: شهادات منتهية بسبب إهمال إداري تتكرر مئات المرات، فيصبح التحذير الذي يهم فعلاً مطابقاً بصرياً لمئة تحذير لا تهم. هذا فشل في تصميم قابلية الاستخدام، لا فشل في ذكاء المستخدم. والحلول الحقيقية هي HSTS (يمنع المتصفح من الاتصال بـ HTTP أصلاً فتفشل هجمات التخفيض) والتثبيت (Pinning).

الأخطاء الشائعة، والتشفير أثناء النقل مقابل في التخزين

أثناء النقل (In Transit) في التخزين (At Rest)
يحمي من اعتراض الشبكة (واي فاي عام، مهاجم على نفس الشبكة) سرقة الجهاز، قرص مُهمَل، نسخة احتياطية مكشوفة
التقنية TLS تشفير القرص الكامل · أعمدة قاعدة بيانات مشفّرة · نسخ احتياطية مشفّرة

سؤال ثالث ينساه الجميع: أين تُخزَّن المفاتيح؟ تشفير مع تخزين المفتاح بجانب البيانات = لا حماية على الإطلاق.

القانون المقدّس: استخدم مكتبة موثوقة ومُدقَّقة، بالطريقة التي تقولها وثائقها، للغرض الذي صُمّمت له. لا تُنفّذ خوارزمية من وصف قرأته. لا تخترع تركيبة. لا "تحسّن" خوارزمية. ولا تقل أبداً: "سأعمل نسختي الخاصة".
