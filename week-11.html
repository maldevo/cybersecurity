Lab 11.1 — Harden your Ubuntu VM (2h)

Goal: Take a machine from default-install to a documented, defensible baseline.

Setup: Your Ubuntu VM from Week 1. Snapshot it first (Ubuntu-Pre-Hardening) — you will break things.

Steps:

  1. Establish the "before". Install Lynis (sudo apt install lynis) and run sudo lynis audit system. Save the output: sudo lynis audit system | tee ~/lab/week11/lynis-before.txt. Note the Hardening index number.

  2. Inventory the attack surface. Record it: 

    ss -tulnp                     # what is listening, and on which interface
systemctl list-units --type=service --state=running
dpkg --get-selections | wc -l # package count

  3. Close what you don't need. Pick at least three running services you do not use, and for each: stop it, disable it, and document why it was running at all. Do not disable SSH — you need it for the labs.

  4. Reduce the listening surface. Find anything bound to 0.0.0.0 that only needs 127.0.0.1 and change it. Restart, re-verify with ss -tulnp.
  5. Patch. sudo apt update && sudo apt full-upgrade, then sudo apt autoremove. Record the count of upgraded packages. Explain in your notes what full-upgrade does differently from upgrade.
  6. Accounts and access. Disable any account you don't use (sudo usermod -L <user>). Check awk -F: '($3 == 0) {print $1}' /etc/passwd — there must be exactly one UID-0 account. Enable the firewall: sudo ufw enable, sudo ufw default deny incoming, sudo ufw allow from <kali-ip> to any port 22. Verify.
  7. Re-audit. Run Lynis again into lynis-after.txt. Compare the two Hardening index values.

Deliverable: ~/lab/week11/hardening-report.md — a table with three columns: Control, Before, After, plus the Lynis index delta and one paragraph on which change gave the most improvement and why.

If you see this → it means:

Symptom Cause
ss shows a port you can't identify Use sudo ss -tulnp — without sudo you don't see the process name
You locked yourself out of SSH ufw default-deny ran before your allow rule. Fix from the VM console, not SSH
Lynis score barely moved Lynis counts many categories; hardening index improves slowly. That's realistic — note it
apt full-upgrade removes a package you wanted It resolved a dependency conflict. Read the prompt before typing y

Lab 11.2 — Stand up a SIEM and ship logs into it (2h)

Goal: A working Wazuh deployment receiving logs from your Ubuntu VM.

Setup — RAM plan (16GB host). This is the tightest part of the whole 13 weeks. Budget it deliberately:

VM RAM Notes
Wazuh server (Ubuntu Server, no GUI) 6 GB All-in-one needs ~4 GB for the indexer + ~2 GB for the manager
Ubuntu target (monitored) 3 GB The VM you hardened in Lab 11.1
Kali (attacker) 3 GB Already built
Host ~4 GB VirtualBox + browser

Do not run all three with a desktop browser open. If your machine struggles, use the prebuilt Wazuh virtual machine instead of building the all-in-one manually, and shut down Kali while the SIEM is indexing.

Steps:

  1. Create a third VM: Ubuntu Server, 6 GB RAM, 2 vCPU, 40 GB disk, on the same NAT Network as the other two.
  2. Install Wazuh all-in-one following the official installation guide. Do not improvise — follow it exactly, and install the indexer, server, and dashboard.
  3. Verify: browse to https://<wazuh-ip> from the Ubuntu desktop VM. Log in. You are looking at a SIEM.
  4. Enroll the Ubuntu target as an agent: Wazuh agent installation. Point it at the Wazuh manager's IP.
  5. Confirm the agent shows Active in the dashboard, and that auth.log events from the target are arriving under Security events.
  6. Generate a little traffic: SSH into the target, run sudo -l, fail a login once. Find each event in the dashboard. Write down the rule description the SIEM attached to it.

Deliverable: A screenshot of the agent as Active plus a list of five events you generated, each with the rule description Wazuh assigned and the log source it came from.

If you see this → it means:

Symptom Cause
Dashboard unreachable The indexer service isn't up yet — it takes minutes on first boot and needs its full RAM
Agent shows "Never connected" Wrong manager IP, or the agent service isn't running — systemctl status wazuh-agent
No events at all The agent's ossec.conf isn't watching /var/log/auth.log, or the firewall blocks port 1514
Everything is slow You are under the RAM budget. Shut down Kali while the SIEM runs

Lab 11.3 — The full loop: attack it, then detect it (1.5h)

Goal: Generate a real brute-force against your own target and catch it in the SIEM. This is the single most important lab of the week.

⚠️ Target is 192.168.x.x — your own Ubuntu VM, on your own NAT Network. Attacking anything else is a criminal offence. No exceptions, no "just one host to see if it works."

Steps:

  1. Snapshot the target.
  2. From Kali, run a password brute-force against your own Ubuntu VM's SSH with hydra (pre-installed in Kali). Keep it to a small wordlist — this is a demonstration, not a real attack.
  3. Watch the target: sudo tail -f /var/log/auth.log while it runs. Watch the shape of the attack — the rate, the usernames tried, whether usernames alternate.
  4. Now open the Wazuh dashboard and find the alerts. Open one alert and read every field: rule.id, rule.level, rule.description, data.srcip, full_log.
  5. Answer in your notes: did Wazuh already have a rule for this, or would I have had to write one? What level did it assign? Was it escalated once the attempts crossed a threshold?
  6. Add a response: research Wazuh active response and explain in your notes how you would automatically block the source IP — and one reason auto-blocking is dangerous.

Deliverable: A written walkthrough of the loop: the command you ran → the log line it produced → the alert it raised → the rule that fired. Four links in one chain. If you can explain that chain, you understand detection.

Lab 11.4 — Write a Sigma rule (1h)

Goal: Describe a behaviour in a vendor-neutral way.

Setup: Read Sigma rule basics and look at real examples in the Sigma rule repository.

Steps:

  1. Choose a behaviour you can actually produce in your lab. Good options: a new user added to a privileged group; a new systemd service created in a directory that isn't a package directory; authorized_keys modified; a shell spawned by a web server user.
  2. Write the rule in YAML with: title, id (a random UUID), status: experimental, description, references, author, date, logsource, detection (with a selection and a condition), falsepositives, level, and tags (including the ATT&CK technique).
  3. Produce the behaviour on your target VM and confirm the log line your detection block describes actually exists in auth.log or the journal. Most rules fail here — the log line isn't shaped how you assumed.
  4. Convert it to a SIEM query with Uncoder.io and paste the output into your notes. Explain what the conversion lost.

Deliverable: Your rule (valid YAML — check it parses), the log line that proves it would match, and the converted query.

The lesson: a detection rule is a hypothesis about logs. Writing it is easy; verifying the log actually looks like that is the job.

Lab 11.5 — Incident timeline and ATT&CK mapping (0.5h)

Goal: Turn scattered alerts into a story.

Steps:

  1. From Lab 11.3, export the alerts (or use the dashboard's timeline view). Build a chronological table: timestamp | host | source IP | event | rule id | what it means.
  2. Mark the phases: when did the attack start, when did it peak, when did it stop, was there any success?
  3. Using ATT&CK, map each event in your timeline to a tactic and a technique. Start from T1110 Brute Force and its sub-techniques.
  4. Write the one-paragraph executive summary a manager would read: what happened, how bad, what you did, what you recommend.

Deliverable: The timeline table, the ATT&CK mapping, and the executive summary.

المختبر 11.1 — حصّن آلة Ubuntu الوهمية (ساعتان)

الهدف: نقل آلة من التثبيت الافتراضي إلى خط أساس موثّق وقابل للدفاع عنه.

التهيئة: آلة Ubuntu الوهمية من الأسبوع 1. خذ لقطة أولاً (Ubuntu-Pre-Hardening) — ستكسر أشياء.

الخطوات:

  1. أنشئ حالة "قبل". ثبّت Lynis (sudo apt install lynis) وشغّل sudo lynis audit system. احفظ المخرجات: sudo lynis audit system | tee ~/lab/week11/lynis-before.txt. سجّل رقم مؤشر التحصين (Hardening index).

  2. احصر سطح الهجوم. سجّله: 

    ss -tulnp                     # what is listening, and on which interface
systemctl list-units --type=service --state=running
dpkg --get-selections | wc -l # package count

  3. أغلق ما لا تحتاجه. اختر ثلاثة من الخدمات العاملة على الأقل لا تستخدمها، ولكل واحدة: أوقفها، وعطّلها، ووثّق لماذا كانت تعمل أصلاً. لا تعطّل SSH — تحتاجه للمختبرات.

  4. قلّل سطح الاستماع. اعثر على أي شيء مربوط بـ 0.0.0.0 وهو لا يحتاج إلا 127.0.0.1 وغيّره. أعد التشغيل، وأعد التحقق بـ ss -tulnp.
  5. حدّث. sudo apt update && sudo apt full-upgrade، ثم sudo apt autoremove. سجّل عدد الحزم المُحدَّثة. واشرح في ملاحظاتك ما الذي يفعله full-upgrade مختلفاً عن upgrade.
  6. الحسابات والوصول. عطّل أي حساب لا تستخدمه (sudo usermod -L <user>). افحص awk -F: '($3 == 0) {print $1}' /etc/passwd — يجب أن يكون هناك حساب واحد فقط بمعرّف UID صفر. فعّل الجدار الناري: sudo ufw enable، sudo ufw default deny incoming، sudo ufw allow from <kali-ip> to any port 22. وتحقّق.
  7. أعد التدقيق. شغّل Lynis مرة أخرى إلى lynis-after.txt. قارن قيمتَي مؤشر التحصين.

المطلوب تسليمه: ~/lab/week11/hardening-report.md — جدول بثلاثة أعمدة: الضابط، قبل، بعد، مع فرق مؤشر Lynis وفقرة واحدة عن أي تغيير أعطى أكبر تحسّن ولماذا.

ss يُظهر منفذاً لا تستطيع تحديده استخدم sudo ss -tulnp — بدون sudo لا ترى اسم العملية
حجبت نفسك خارج SSH قاعدة المنع الافتراضي في ufw عملت قبل قاعدة السماح. أصلح الأمر من طرفية الآلة الوهمية، لا من SSH
نتيجة Lynis لم تتحرّك إلا قليلاً Lynis تحسب فئات كثيرة؛ ومؤشر التحصين يتحسّن ببطء. هذا واقعي — سجّله

المختبر 11.2 — أنشئ نظام SIEM واشحن السجلات إليه (ساعتان)

الهدف: تنصيب Wazuh عامل يستقبل السجلات من آلة Ubuntu الوهمية.

التهيئة — خطة الذاكرة (مضيف 16GB). هذا أضيق جزء في الأسابيع الـ 13 كلها. وزّعها بحساب متعمّد:

الآلة الوهمية الذاكرة ملاحظات
خادم Wazuh (Ubuntu Server، بلا واجهة رسومية) 6 GB التنصيب الشامل (all-in-one) يحتاج ~4 GB للـ indexer + ~2 GB للـ manager
هدف Ubuntu (المُراقَب) 3 GB الآلة التي حصّنتها في المختبر 11.1
Kali (المهاجم) 3 GB مبنية بالفعل
المضيف ~4 GB VirtualBox + المتصفح

لا تشغّل الآلات الثلاث مع فتح متصفح سطح مكتب. إن كان جهازك يعاني، استخدم آلة Wazuh الوهمية الجاهزة بدلاً من بناء التنصيب الشامل يدوياً، وأوقف Kali أثناء فهرسة الـ SIEM.

الخطوات:

  1. أنشئ آلة وهمية ثالثة: Ubuntu Server، ذاكرة 6 GB، معالجان افتراضيان (2 vCPU)، قرص 40 GB، على نفس شبكة NAT Network التي عليها الآلتان الأخريان.
  2. ثبّت Wazuh بالتنصيب الشامل وفق دليل التثبيت الرسمي. لا ترتجل — اتبعه حرفياً، وثبّت المكوّنات الثلاثة: indexer و server و dashboard.
  3. تحقّق: افتح https://<wazuh-ip> من آلة Ubuntu Desktop. سجّل الدخول. أنت تنظر الآن إلى نظام SIEM.
  4. سجّل هدف Ubuntu كعميل (agent): تثبيت عميل Wazuh. ووجّهه إلى عنوان IP الخاص بمدير Wazuh.
  5. تأكّد أن العميل يظهر Active في اللوحة، وأن أحداث auth.log من الهدف تصل تحت Security events.
  6. أنشئ قليلاً من الحركة: اتصل بـ SSH على الهدف، وشغّل sudo -l، وفشّل محاولة تسجيل دخول واحدة. اعثر على كل حدث في اللوحة. واكتب وصف القاعدة (rule description) التي ألصقها الـ SIEM بالحدث.

المطلوب تسليمه: صورة شاشة للعميل وهو Active، مع قائمة بخمسة أحداث ولّدتها، ولكل حدث وصف القاعدة التي أسندها Wazuh ومصدر السجل الذي جاء منه.

إذا رأيت هذا → فمعناه:

العرض السبب
اللوحة لا تُفتح خدمة الـ indexer لم تعمل بعد — تحتاج دقائق في أول إقلاع وتحتاج كامل ذاكرتها
العميل يظهر "Never connected" عنوان IP خاطئ للمدير، أو خدمة العميل لا تعمل — systemctl status wazuh-agent
لا توجد أي أحداث ملف ossec.conf في العميل لا يراقب /var/log/auth.log، أو الجدار الناري يحجب المنفذ 1514
كل شيء بطيء أنت تحت ميزانية الذاكرة. أوقف Kali أثناء عمل الـ SIEM

المختبر 11.3 — الحلقة الكاملة: اهجم عليه، ثم اكتشف الهجوم (1.5 ساعة)

الهدف: ولّد هجوماً حقيقياً بالقوة الغاشمة (brute-force) على هدفك أنت، واقبض عليه في الـ SIEM. هذا أهم مختبر منفرد في الأسبوع.

⚠️ الهدف هو 192.168.x.x — آلة Ubuntu الوهمية الخاصة بك، على شبكة NAT Network الخاصة بك. مهاجمة أي شيء آخر جريمة جنائية. لا استثناءات، ولا "جهاز واحد فقط لأرى هل ينجح الأمر".

الخطوات:

  1. خذ لقطة للهدف.
  2. من Kali، شغّل هجوم قوة غاشمة على كلمات المرور ضد SSH في آلة Ubuntu الوهمية الخاصة بك باستخدام hydra (مثبّتة مسبقاً في Kali). التزم بقائمة كلمات صغيرة — هذا عرض توضيحي، لا هجوم حقيقي.
  3. راقب الهدف: sudo tail -f /var/log/auth.log أثناء تشغيله. راقب شكل الهجوم — المعدّل، وأسماء المستخدمين المُجرَّبة، وهل تتناوب أسماء المستخدمين.
  4. الآن افتح لوحة Wazuh واعثر على التنبيهات. افتح تنبيهاً واحداً واقرأ كل حقل: rule.id، وrule.level، وrule.description، وdata.srcip، وfull_log.
  5. أجب في ملاحظاتك: هل كان لدى Wazuh قاعدة لهذا أصلاً، أم كان عليّ كتابة واحدة؟ ما المستوى الذي أسندته؟ هل تصاعد التنبيه بعد تجاوز المحاولات حداً معيناً؟
  6. أضف استجابة: ابحث في الاستجابة النشطة في Wazuh واشرح في ملاحظاتك كيف ستحجب عنوان IP المصدر تلقائياً — وسبباً واحداً يجعل الحجب التلقائي خطيراً.

المطلوب تسليمه: شرح مكتوب للحلقة: الأمر الذي شغّلته → سطر السجل الذي أنتجه → التنبيه الذي أطلقه → القاعدة التي اشتعلت. أربع حلقات في سلسلة واحدة. إن استطعت شرح هذه السلسلة، فأنت تفهم الكشف.

المختبر 11.4 — اكتب قاعدة Sigma (ساعة)

الهدف: وصف سلوك بطريقة محايدة تجاه المنتج.

التهيئة: اقرأ أساسيات قواعد Sigma وانظر إلى أمثلة حقيقية في مستودع قواعد Sigma.

الخطوات:

  1. اختر سلوكاً تستطيع فعلاً إنتاجه في مختبرك. خيارات جيدة: مستخدم جديد يُضاف إلى مجموعة مميّزة الصلاحيات؛ خدمة systemd جديدة تُنشأ في مجلد ليس مجلد حزم؛ تعديل authorized_keys؛ صدفة (shell) يُشغّلها مستخدم خادم ويب.
  2. اكتب القاعدة بلغة YAML مع: title، وid (UUID عشوائي)، وstatus: experimental، وdescription، وreferences، وauthor، وdate، وlogsource، وdetection (مع selection وcondition)، وfalsepositives، وlevel، وtags (بما فيها تقنية ATT&CK).
  3. أنتج السلوك على آلة الهدف الوهمية وتأكّد أن سطر السجل الذي تصفه كتلة detection موجود فعلاً في auth.log أو في سجل النظام (journal). معظم القواعد تفشل هنا — سطر السجل ليس بالشكل الذي افترضته.
  4. حوّلها إلى استعلام SIEM بـ Uncoder.io والصق الناتج في ملاحظاتك. واشرح ما الذي فقدته عملية التحويل.

المطلوب تسليمه: قاعدتك (YAML صحيحة — تحقّق من أنها تُحلَّل بلا أخطاء)، وسطر السجل الذي يثبت أنها ستطابق، والاستعلام المحوَّل.

الدرس: قاعدة الكشف هي فرضية عن السجلات. كتابتها سهلة؛ أما التحقق من أن السجل يبدو هكذا فعلاً فهو العمل الحقيقي.

المختبر 11.5 — الخط الزمني للحادث وربطه بـ ATT&CK (0.5 ساعة)

الهدف: حوّل التنبيهات المتناثرة إلى قصة.

الخطوات:

  1. من المختبر 11.3، صدّر التنبيهات (أو استخدم عرض الخط الزمني في اللوحة). ابنِ جدولاً زمنياً: timestamp | host | source IP | event | rule id | what it means.
  2. حدّد المراحل: متى بدأ الهجوم، ومتى بلغ ذروته، ومتى توقّف، وهل نجح في شيء؟
  3. باستخدام ATT&CK، اربط كل حدث في خطك الزمني بتكتيك وتقنية. ابدأ من T1110 Brute Force وتقنياتها الفرعية.
  4. اكتب الملخّص التنفيذي في فقرة واحدة كما سيقرؤه مدير: ماذا حدث، وما مدى سوءه، وماذا فعلت، وبماذا توصي.

المطلوب تسليمه: جدول الخط الزمني، وربط ATT&CK، والملخّص التنفيذي.

Challengeالتحدّي

  • ابنِ خريطة تغطية ATT&CK. أنشئ طبقة (layer) في ATT&CK Navigator ولوّن كل تقنية تستطيع كشفها فعلاً اليوم في مختبرك. كن صادقاً. الخلايا غير الملوّنة هي تحليل الفجوات عندك — اكتب فقرة واحدة عن أكبر فجوة وما يتطلّبه سدّها.
  • أنجز تمريناً مجانياً للفريق الأزرق. أكمل تحدياً مجانياً على Blue Team Labs Online أو وحدة مجانية على LetsDefend. واكتب ما فعلته وأين تعطّلت.
  • اكتب دليل إجراءات (runbook) للاستجابة للحوادث لسيناريو القوة الغاشمة على SSH: صفحة واحدة، if X then Y، مع ذِكر من ستُبلغه، وما ستحافظ عليه، وما لن تفعله (مثلاً لا تُعد تشغيل الجهاز — ستفقد دليل الذاكرة).

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

This is the week you find out if you're a defender.

Be honest with yourself about what attracts you. Defensive work is not the consolation prize — it is a genuinely different craft, and it suits different people:

  1. You own the environment, not the engagement. A pentester borrows a network for two weeks and leaves. A defender owns that network for years. They know the strange server nobody documented, the one subnet that behaves oddly on Fridays, the account that always locks out on payroll day. That accumulated, deep familiarity is a real kind of power — and it's the thing attackers can't buy.

  2. You see the whole picture. An attacker sees the one path they took. A defender sees all the paths — the ones taken, the ones attempted, and the ones that nearly worked. The detection mindset is systems thinking: everything connects to everything.

  3. "Right slowly" beats "wrong once." An attacker who is wrong once is caught and the engagement ends. A defender is allowed to be uncertain, to iterate, to say "I don't know yet, give me the logs." The job rewards patience, curiosity, and the willingness to keep pulling a thread — not the ability to produce a shell in thirty seconds.

  4. The failure mode is different. In offense, the bad day is "I didn't find it." In defense, the bad day is "it happened and I didn't see it." Being honest about which of those two keeps you up at night is the single best signal about which lane you belong in.

And one thing you now know for certain, because you built it: prevention alone always fails. You hardened that Ubuntu box for two hours and it still had a brute-forceable SSH service at the end, because it had to — it's a useful service and it must be reachable. Every organization that has ever been breached had a firewall. Detection is not what you do when prevention fails; it's what makes prevention honest.

هذا هو الأسبوع الذي تكتشف فيه هل أنت مدافع.

كن صادقاً مع نفسك بشأن ما يجذبك. العمل الدفاعي ليس جائزة ترضية — إنه حرفة مختلفة بحق، وهو يناسب أناساً مختلفين:

  1. أنت تملك البيئة، لا المهمة. مختبر الاختراق يستعير شبكة أسبوعين ثم يرحل. أما المدافع فيملك تلك الشبكة سنوات. يعرف الخادم الغريب الذي لم يوثّقه أحد، والشبكة الفرعية الوحيدة التي تتصرف بغرابة أيام الجمعة، والحساب الذي يُقفل دائماً يوم صرف الرواتب. هذه المعرفة العميقة المتراكمة نوع حقيقي من القوة — وهي الشيء الذي لا يستطيع المهاجمون شراءه.

  2. أنت ترى الصورة كاملة. المهاجم يرى المسار الواحد الذي سلكه. والمدافع يرى كل المسارات — التي سُلكت، والتي جُرّبت، والتي كادت تنجح. عقلية الكشف هي تفكير منظومي: كل شيء متصل بكل شيء.

  3. "أن تكون مصيباً ببطء" أفضل من "أن تخطئ مرة". المهاجم الذي يخطئ مرة واحدة يُكشف وتنتهي المهمة. أما المدافع فيُسمح له أن يكون غير متأكد، وأن يكرّر المحاولة، وأن يقول "لا أعرف بعد، أعطني السجلات". الوظيفة تكافئ الصبر والفضول والاستعداد لمواصلة شدّ الخيط — لا القدرة على إنتاج صدفة (shell) في ثلاثين ثانية.

  4. نمط الفشل مختلف. في الهجوم، اليوم السيئ هو "لم أعثر عليه". وفي الدفاع، اليوم السيئ هو "حدث ولم أره". والصدق مع نفسك بشأن أيّهما يحرمك النوم هو أفضل مؤشر منفرد على المسار الذي تنتمي إليه.

وشيء واحد تعرفه الآن بيقين، لأنك بنيته بيدك: المنع وحده يفشل دائماً. حصّنت آلة Ubuntu تلك ساعتين، ومع ذلك بقي فيها في النهاية منفذ SSH قابل للهجوم بالقوة الغاشمة، لأنها مضطرة لذلك — إنها خدمة نافعة ويجب أن تكون قابلة للوصول. وكل منظمة اختُرقت يوماً كان لديها جدار ناري. الكشف ليس ما تفعله عندما يفشل المنع؛ بل هو ما يجعل المنع صادقاً.

ملاحظات مفاهيمية موسّعة

شرح إضافي موسّع

لماذا لا يكفي المنع (Prevention) وحده؟

هذا أهم مفهوم في الأسبوع كله، وهو الذي يفسّر وجود مهنة الدفاع أصلاً.

المنع (Prevention) = منع الهجوم من النجاح. جدار ناري، كلمة مرور قوية، تحديثات، إغلاق المنافذ.

الكشف (Detection) = معرفة أن هجوماً يحدث، الآن أو حدث بالأمس.

الاستجابة (Response) = فعل شيء حيال ما اكتشفته.

لماذا يفشل المنع دائماً؟ ليس لأن المهندسين أغبياء، بل لأسباب بنيوية:

السبب الشرح
الخدمة موجودة لسبب لو أغلقت SSH تماماً، لن يستطيع أحد إدارتها. كل خدمة نافعة = نقطة هجوم
الخطأ البشري إعداد خاطئ واحد يكفي، والأنظمة تتغير كل يوم
الهندسة الاجتماعية لا يوجد جدار ناري يمنع موظفاً من إدخال كلمة مروره في صفحة مزيفة
الثغرات الجديدة (0-day) تُنتشر ثغرة في برنامج لم يسمع به أحد الأسبوع الماضي
المهاجم يحتاج ثغرة واحدة أنت تحتاج إغلاق كل الثغرات. هو يحتاج واحدة فقط

القاعدة الذهبية: إدارة الأمن الحديثة تفترض أن الاختراق سيحدث، وتبني قدرتها على أنه سيكون هناك وقت بين الاختراق واكتشافه. تقليص هذا الوقت هو هدف الدفاع كله.

السجلات وتجميعها (Logging & Aggregation)

المشكلة: كل جهاز يكتب سجلاته محلياً. عشرة أجهزة = عشرة ملفات لا يقرؤها أحد.

لماذا هذا خطر؟

  • المهاجم الذي يخترق جهازاً يملك سجلاته. أول ما يفعله هو حذف الأثر.
  • لا يمكنك ربط حدث على الجهاز "أ" بحدث على الجهاز "ب".
  • لا يوجد وقت بشري لقراءة سجلات 500 جهاز يدوياً.

الحل: التجميع المركزي (Centralized Logging) — كل جهاز يرسل سجلاته إلى مكان واحد. إذا فُقد الجهاز، تبقى سجلاته عندك. هذا وحده يبرّر كل الجهد.

مبدأ جنائي مهم: سجلات الجهاز نفسه ليست دليلاً موثوقاً، لأن المهاجم قد يعدّلها. السجل المرسل خارج الجهاز وقت الحدث هو الدليل الحقيقي.

نظام SIEM — ما هو فعلاً؟

SIEM اختصار Security Information and Event Management. والاسم يشرح وظيفته:

الجزء الوظيفة
Information يجمع السجلات من كل مكان ويخزّنها
Event يحلّل الأحداث ويكتشف الشاذ
Management يربط الأحداث ببعضها ويُنبّه ويساعد في الاستجابة

ماذا يفعل عملياً؟ ثلاث وظائف فقط، لكنها ضخمة:

1. التجميع (Collection): كل السجلات في مكان واحد، بصيغة موحّدة، مع بحث فوري.

2. الربط (Correlation): وهذه هي القيمة الحقيقية. حدث واحد لا يعني شيئاً. حدثان مترابطان قد يعنيان اختراقاً:

مثال حقيقي: فشل تسجيل دخول واحد = لا شيء. فشل تسجيل دخول واحد ثم إنشاء مستخدم جديد من نفس الجهاز بعد دقيقتين = هجوم يحتاج تحقيقاً فورياً.

لا يمكن لأي أداة أخرى فعل هذا الربط، لأنها تحتاج مصدرين مختلفين في نفس اللحظة.

3. التنبيه (Alerting): عندما تتحقق قاعدة معينة، يُرسل تنبيه. القاعدة (Rule) هي "إذا رأيت X فيجب أن أنبّه".

كل أنظمة SIEM الكبرى — Splunk، Sentinel، QRadar، Elastic، Wazuh — تفعل هذه الثلاثة نفسها. الاختلاف في الحجم والواجهة والسعر، لا في المبدأ. Wazuh مفتوحة المصدر بالكامل ولذلك هي خيارنا.

MITRE ATT&CK — خريطة سلوك المهاجم

هذه أشهر قاعدة معرفية في مجال الأمن، وفهمها يفصلك عن المبتدئين.

المشكلة التي حلها ATT&CK: كان كل فريق يسمّي الهجمات بمسميات مختلفة فيصعب تبادل المعرفة. ATT&CK وحّد اللغة.

الفرق الجوهري بين التكتيك والتقنية:

المفهوم المعنى السؤال الذي يجيب عنه
التكتيك (Tactic) الهدف — لماذا يفعل المهاجم هذا؟ "ماذا يريد أن يحقق؟"
التقنية (Technique) الطريقة — كيف حققه؟ "كيف حققه بالضبط؟"

مثال موحّد يوضّح الفرق:

  • التكتيك: الوصول الأولي (Initial Access) — الهدف: الدخول إلى الشبكة.
  • التقنية: T1190 / استغلال تطبيق متاح للعامة أو T1078 / حسابات صحيحة — الطريقة: استغل ثغرة في خدمة مكشوفة، أو استخدم حساباً مسروقاً ولم يكسر شيئاً أصلاً.

نفس الهدف، طرق مختلفة. مهاجم آخر حقق نفس التكتيك بطريقة أخرى تماماً. لهذا ATT&CK مرتب بشجرتين: تكتيكات، وتحتها تقنيات، وتحتها تقنيات فرعية (Sub-techniques).

التكتيكات الأربعة عشر في نسخة Enterprise — وهي تشكّل قصة الهجوم بالترتيب المنطقي:

# التكتيك (English) بالعربية ماذا يريد المهاجم هنا؟
1 Reconnaissance الاستطلاع جمع معلومات عن الضحية دون لمسها
2 Resource Development تطوير الموارد تجهيز بنيته: نطاق، سيرفر، أدوات
3 Initial Access الوصول الأولي الدخول إلى الشبكة من أول مرة
4 Execution التنفيذ تشغيل كوده داخل الجهاز
5 Persistence الاستمرارية ضمان عودته بعد إعادة التشغيل
6 Privilege Escalation تصعيد الصلاحيات الانتقال من مستخدم عادي إلى مدير
7 Defense Evasion التهرب من الدفاعات إخفاء نفسه وتجنّب الكشف
8 Credential Access الوصول لبيانات الاعتماد سرقة كلمات المرور والجلسات
9 Discovery الاستكشاف معرفة ما يوجد على الشبكة
10 Lateral Movement الحركة الجانبية الانتقال من جهاز إلى آخر
11 Collection الجمع تجميع البيانات المهمة قبل سرقتها
12 Command and Control التحكم والقيادة قناة اتصال بينه وبين الجهاز المخترق
13 Exfiltration تسريب البيانات إخراج البيانات من الشبكة
14 Impact التأثير التدمير أو التشفير أو التعطيل

كيف تستخدمها كمدافع؟ لكل تقنية في القائمة اسأل: "ما السجل الذي ستتركه هذه التقنية؟" إن كانت الإجابة "لا شيء"، فأنت أعمى عن هذه التقنية. هذه هي طريقة التفكير الدفاعية كلها، وهي أساس تمرين Gap Analysis في هذا الأسبوع.

خطأ شائع: ATT&CK ليست قائمة ثغرات ولا قائمة أدوات. إنها خريطة سلوك. المهاجم قد يغيّر أدواته غداً، لكن سلوكه سيبقى ضمن هذه الخريطة.

هندسة الكشف و Sigma

هندسة الكشف (Detection Engineering) = كتابة القواعد التي تحوّل السجلات الخام إلى تنبيهات ذات معنى.

المشكلة: قاعدة مكتوبة لـ Splunk لا تعمل على Wazuh. كل نظام له صيغة استعلام مختلفة. فكيف نتبادل القواعد؟

الحل: Sigma — لغة محايدة لوصف الكشف، بصيغة YAML. تكتب القاعدة مرة واحدة، ثم تُترجم إلى أي نظام.

العنصر معناه
logsource من أين تأتي البيانات (نظام لينكس؟ خدمة sshd؟ سجل ويندوز؟)
detection.selection الشرط: ماذا نبحث عنه؟
detection.condition كيف نجمع الشروط (واحد؟ كلها؟ عدد معين؟)
level خطورة القاعدة: low / medium / high / critical
tags ربط القاعدة بتقنية ATT&CK — مثل attack.t1110.001

القاعدة الذهبية في كتابة القواعد: اكتب الكشف عن السلوك، لا عن الأداة.

❌ سيئ:  "تحذير إذا شغّل المهاجم أداة hydra"
✅ جيد:  "تحذير إذا فشلت أكثر من 10 محاولات دخول من نفس العنوان خلال دقيقة"

الأول يخترقه المهاجم بتغيير الأداة. الثاني يصف نمطاً لا يمكن تجنّبه — لأن العشرين محاولة فاشلة تبدو نفسها مهما كانت الأداة. هذا هو الفرق بين مبتدئ ومحترف.

دورة حياة الاستجابة للحوادث (نداء NIST)

الاستجابة للحادث (Incident Response) ليست ردة فعل عشوائية، بل عملية بمراحل.

مراحل NIST الأربع (من NIST SP 800-61):

المرحلة ماذا يحدث
1. التحضير (Preparation) قبل أي حادث: أدوات جاهزة، أدوار محددة، سجلات مفعّلة، خطة مكتوبة
2. الكشف والتحليل (Detection & Analysis) هل حدث شيء؟ ما هو؟ إلى أي مدى وصل؟
3. الاحتواء والمعالجة والاستعادة (Containment, Eradication & Recovery) أوقف الانتشار، أزل السبب، أعد الخدمة
4. أنشطة ما بعد الحادث (Post-Incident Activity) ماذا تعلمنا؟ ما الذي نصلحه؟

وفي الصيغة الموسّعة الأكثر شيوعاً في العمل اليومي (تُعرف بـ PICERL):

# المرحلة بالعربية الهدف العملي
1 Preparation التحضير جهّز قبل أن تحتاج
2 Identification التحديد هل هذا حادث فعلاً؟
3 Containment الاحتواء أوقف النزيف — اعزل الجهاز
4 Eradication الاستئصال أزل سبب الحادث (البرمجية، الحساب، الثغرة)
5 Recovery الاستعادة أعد الأنظمة للعمل بثقة
6 Lessons Learned الدروس المستفادة امنع تكراره

التمييز الذي يسأل عنه كل مُقابل عمل: ما الفرق بين الاحتواء والاستئصال؟

  • الاحتواء = منع الانتشار. قد يكون مؤقتاً وقبيحاً (افصل كابل الشبكة!). لا يزيل السبب.
  • الاستئصال = إزالة السبب الجذري. لا يبدأ قبل أن ينتهي الاحتواء، وإلا عدت إلى نقطة الصفر.

الترتيب غير قابل للتفاوض. من يستعجل إلى الاستئصال قبل الاحتواء يجد أن المشكلة انتشرت إلى عشرة أجهزة أثناء عمله على الأول.

خطأ متكرر وخطير: إعادة تشغيل الجهاز المصاب فوراً. هذا يمحو الذاكرة (RAM) — أفضل مصدر للدليل — وأحياناً يزيل البرمجيات التي تعمل في الذاكرة فقط. اعزل، لا تُطفئ.

الصيد الاستباقي مقابل التنبيه (Threat Hunting vs Alerting)

التنبيه (Alerting) الصيد (Hunting)
من يبدأ؟ النظام يبدأ: "انظر، هذا!" أنت تبدأ: "أتساءل إن كان هناك شيء لم نره؟"
الأساس قاعدة معروفة مسبقاً فرضية (Hypothesis)
السؤال "هل تحققت هذه القاعدة؟" "لو كنت مهاجماً، كيف أتجاوز قواعدنا؟"
يكشف ما يُعرف مسبقاً ما لم يُعرف بعد
النتيجة تنبيه إما حادث مخفي، أو قاعدة جديدة تُضاف

لماذا نحتاج الصيد؟ لأن القواعد تكشف فقط ما كتبناه. المهاجم الذي يعرف قواعدنا سيتجنبها. الصيد هو الطريقة الوحيدة لاكتشاف "المجهول غير المعروف".

النتيجة الجانبية الأهم للصيد: كل صيد ينتهي بلا نتيجة قاعدة جديدة. هكذا تنمو قدرة الكشف. الصيد الذي لا ينتج عنه قاعدة هو وقت مهدور.

محلل مركز العمليات الأمنية (SOC Analyst) — المستويات

المستوى ماذا يفعل فعلاً يومياً
Tier 1 — التنبيهات يراقب طابور التنبيهات، يقيّم كل تنبيه: حقيقي أم إيجابية كاذبة؟ يوثّق ويصعّد. أكثر وظيفة دفاعية مطلوبة للمبتدئين
Tier 2 — التحقيق يحقق في التنبيهات المصعّدة، يربط الأدلة، يحدد المدى، ينفّذ الاحتواء
Tier 3 — الصيد والهندسة يبحث استباقياً، يكتب قواعد الكشف، يحسّن قدرة الفريق، يقود الحوادث الكبرى

الإيجابية الكاذبة (False Positive) = تنبيه على شيء مشروع. الإيجابية الكاذبة هي العدو الأول لمحلل Tier 1 — لأن كثرتها تجعل الفريق يتجاهل التنبيهات، وهنا ينجح المهاجم. تقليلها بلا تفريط بالكشف هو مهارة حقيقية.
