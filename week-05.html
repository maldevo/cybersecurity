Lab 5.1 — Dissect a TCP handshake (1.5h)

Goal: Stop reading about the handshake and watch it happen.

Setup: Kali and Ubuntu on the same NAT Network (from Week 4). Wireshark installed on Kali (sudo apt install wireshark -y; choose "yes" when it asks about non-root capture, or just run with sudo).

Steps:

  1. Start the capture on Kali: sudo wireshark, pick the interface facing labnet, start.
  2. From Kali, open a TCP connection to Ubuntu: nc -v <ubuntu-ip> 22 (SSH port — it will answer with a banner). Leave it open.
  3. Stop the capture. Filter: tcp.port == 22
  4. Find the handshake. It is exactly three packets:
  • Packet 1 — SYN, flags 0x002, Seq=0
  • Packet 2 — SYN, ACK, flags 0x012, Seq=0 Ack=1
  • Packet 3 — ACK, flags 0x010, Seq=1 Ack=1
  1. Click each packet and expand the TCP header. Write down, for each: source port, destination port, sequence number, acknowledgement number, and the flag bits.

  2. Display filters drill. Write and record the result of each: 

    tcp.flags.syn == 1 and tcp.flags.ack == 0     # only initial SYNs
tcp.flags.reset == 1                          # only resets
tcp.port == 22                                # anything on port 22
tcp.stream eq 0                               # one complete conversation

  3. The teardown. In the capture, the FIN packets appear after you close your connection. Find them. Count how many packets the teardown took. Why four and not three?

  4. See a RST. From Kali: nc -v <ubuntu-ip> 9999 (a closed port). Capture it. What did Ubuntu send back? A RST is the network saying "nothing is listening here" — and it is the single most valuable packet for a port scanner. Remember this going into Week 6.

Deliverable: A screenshot or text export of the three handshake packets with every field annotated by hand, plus your filter results.

If you see this → it means:

Symptom Cause
No packets captured at all Wrong interface selected in Wireshark — check ip a for the labnet interface
You see the handshake but no data Correct — SSH is encrypted. Nothing readable is expected here. That's the point of Week 6
Connection goes to SYN then RST Nothing is listening on that port on the target, or a firewall rejected it
tcp.stream eq 0 shows nothing Stream indices are per-capture; find the real index via right-click → Follow → TCP Stream

Lab 5.2 — Capture a login in plaintext (2h)

Goal: Watch credentials cross the wire in readable ASCII. This is the lab learners remember for years.

Setup: A deliberately insecure HTTP login page on the Ubuntu VM. Zero budget, no downloads — a 20-line Python server.

Steps:

  1. On Ubuntu, create ~/insecure-login.py: 

    #!/usr/bin/env python3
from http.server import BaseHTTPRequestHandler, HTTPServer

PAGE = b"""<html><body><h3>Lab Login</h3>
<form method="POST" action="/login">
  User: <input name="username"><br>
  Pass: <input name="password" type="password"><br>
  <input type="submit" value="Log in">
</form></body></html>"""

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.end_headers()
        self.wfile.write(PAGE)
    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        body = self.rfile.read(n)
        print("CREDS RECEIVED:", body.decode(errors="replace"), flush=True)
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok")

HTTPServer(("0.0.0.0", 8080), H).serve_forever()

  2. Run it: python3 ~/insecure-login.py

  3. On Kali, start a capture filtered to tcp.port == 8080.
  4. In Kali's browser, visit http://<ubuntu-ip>:8080, type username student and password SuperSecret123, submit.

  5. Stop the capture and find your password. Use these filters in order: 

    http.request.method == "POST"
http contains "SuperSecret123"

  6. Right-click the POST packet → Follow → HTTP Stream. Read the raw request. The password is sitting in plain ASCII.

  7. Now do it over HTTPS. Browse to any real HTTPS site, log in somewhere with a throwaway account, capture it, and try the same filter. You will see TLS records and nothing readable. Write down what changed and why.
  8. Repeat on the same network from the target's perspective. Run sudo tcpdump -i <iface> -A 'tcp port 8080' on Ubuntu while you log in from Kali. Where else did the credential appear?

Deliverable: The base64-free, plain-text credential extracted from your own capture, plus a one-paragraph explanation of what a passive attacker on the same Wi-Fi network would have obtained.

⚠️ This is your own lab and your own throwaway password. Never do this on a network you don't own — capturing another person's traffic is a criminal offence in most jurisdictions, regardless of intent.

Lab 5.3 — Follow a DNS resolution (1.5h)

Goal: See the exact packets behind "typing a name into a browser".

Steps:

  1. On Kali, start a capture with filter udp.port == 53.

  2. Clear the cache and look up a domain: 

    sudo resolvectl flush-caches     # or: sudo systemd-resolve --flush-caches
dig www.wikipedia.org

  3. In Wireshark, find the query packet. Expand DNS. Record: transaction ID, flags, question name, query type (A), and the response's answer records with their TTL.

  4. Now query each record type deliberately and capture each: 

    dig A wikipedia.org
dig AAAA wikipedia.org
dig MX gmail.com
dig NS wikipedia.org
dig TXT google.com
dig CNAME www.github.com
dig +trace www.wikipedia.org      # watch iterative resolution from the root

  5. dig +trace is the whole lesson. Read its output top to bottom. You will see the query go to a root server, then to the .org TLD server, then to Wikipedia's authoritative server. That is iterative resolution.

  6. Recursive vs iterative. Your machine asks the resolver one question and expects one final answer — that is recursive. The resolver does the walking itself — that is iterative. Write both definitions in your notes with the actors named.
  7. Over TCP? Run dig +tcp wikipedia.org with the same filter but change it to tcp.port == 53. Why does DNS sometimes use TCP? (Hint: what happens when an answer is too big for a UDP datagram?)

Deliverable: Screenshots of a DNS query and its response with the answer record and TTL annotated, plus the dig +trace output with each of the three server tiers labelled.

Lab 5.4 — Capture DHCP DORA and analyse a pcap (2h)

Goal: See how a machine gets an address, then analyse traffic you did not generate.

Setup: The DHCP exchange needs a DHCP server. Your labnet (Week 4) has none — that is the point of part 1.

Part A — DORA (45m):

  1. On Kali, put an interface on the host's NAT Network (which does have DHCP) and start a capture with filter udp.port == 67 or udp.port == 68.
  2. Release and renew: sudo dhclient -r <iface> then sudo dhclient -v <iface> (or bounce the adapter in NetworkManager).
  3. Find the four packets and label them: Discover (broadcast, client → 255.255.255.255) · Offer (server → client) · Request (broadcast — why broadcast?) · ACK.
  4. Expand the Offer and record: offered IP, subnet mask, router (option 3), DNS servers (option 6), lease time (option 51).
  5. The security question: the Discover and Request are broadcast — everyone on the segment sees them. What could a malicious host do with that? Write your answer before reading Week 5's Security Payoff.

Part B — Analyse a stranger's pcap (75m):

  1. Download a capture from a source that did not come from your lab:
  • Wireshark SampleCaptures — curated, safe, legal
  • malware-traffic-analysis.net — real captured malware traffic, with exercises
  1. Answer these from the pcap alone, using only Wireshark filters:
  • How many hosts are involved? (Statistics → Conversations)
  • Which ports are being contacted? (Statistics → Endpoints)
  • Is there any cleartext protocol? Filter http, then ftp, then telnet.
  • What are the top talkers by bytes? (Statistics → Protocol Hierarchy)
  • Is there a DNS query for something suspicious — a long random-looking name, or a TXT record to a domain you don't recognise?

  1. Then do the same with the command line: 

    tshark -r capture.pcap -q -z conv,tcp
tshark -r capture.pcap -Y "dns" -T fields -e dns.qry.name | sort -u
tshark -r capture.pcap -Y "http.request" -T fields -e http.host -e http.request.uri

  2. Write a one-page incident note: what happened, between whom, over which protocols, and what you would investigate next.

Deliverable: The four DHCP packets identified and annotated, plus the one-page incident note on the downloaded pcap.

If you see this → it means:

Symptom Cause
No DHCP packets captured The interface has a static address, or the adapter is on Internal Network (no DHCP server there)
dig +trace output is short and goes nowhere A local resolver is answering before the trace starts. Point dig at a public resolver: dig +trace @1.1.1.1 www.wikipedia.org
Credentials don't appear in the Wireshark filter The site used HTTPS, or the form submitted via JavaScript in a way that changed the encoding — check Follow HTTP Stream
tshark says "no such field" Typo in the display filter field name. Look it up in the Display Filter Reference
Pcap opens but shows thousands of packets you can't read That's normal. Use Statistics → Protocol Hierarchy first, then narrow with filters. Never read a pcap top-to-bottom

المختبر 5.1 — تفكيك مصافحة TCP (1.5 ساعة)

الهدف: توقّف عن القراءة عن المصافحة وشاهدها تحدث أمامك.

التهيئة: Kali و Ubuntu على نفس شبكة NAT Network (من الأسبوع 4). Wireshark مثبَّت على Kali (sudo apt install wireshark -y؛ اختر "yes" عندما يسألك عن الالتقاط بدون root، أو شغّله بـ sudo مباشرة).

الخطوات:

  1. ابدأ الالتقاط على Kali: sudo wireshark، اختر الواجهة المتصلة بـ labnet، ثم ابدأ.
  2. من Kali، افتح اتصال TCP إلى Ubuntu: nc -v <ubuntu-ip> 22 (منفذ SSH — سيرد بـ banner). اتركه مفتوحاً.
  3. أوقف الالتقاط. الفلتر: tcp.port == 22
  4. جد المصافحة. إنها ثلاث حزم بالضبط:
  • الحزمة 1 — SYN، الأعلام 0x002، Seq=0
  • الحزمة 2 — SYN, ACK، الأعلام 0x012، Seq=0 Ack=1
  • الحزمة 3 — ACK، الأعلام 0x010، Seq=1 Ack=1
  1. انقر على كل حزمة ووسّع ترويسة TCP. سجّل لكل حزمة: منفذ المصدر، منفذ الوجهة، رقم التسلسل، رقم التأكيد، وبتات الأعلام.

  2. تدريب على فلاتر العرض. اكتب وسجّل نتيجة كل فلتر: 

    tcp.flags.syn == 1 and tcp.flags.ack == 0     # only initial SYNs
tcp.flags.reset == 1                          # only resets
tcp.port == 22                                # anything on port 22
tcp.stream eq 0                               # one complete conversation

  3. الإغلاق (Teardown). في الالتقاط، تظهر حزم FIN بعد أن تغلق اتصالك. جدها. عُدّ كم حزمة استغرق الإغلاق. لماذا أربع حزم وليست ثلاثاً؟

  4. شاهد RST. من Kali: nc -v <ubuntu-ip> 9999 (منفذ مغلق). التقطه. بماذا رد Ubuntu؟ حزمة RST هي الشبكة وهي تقول "لا شيء يستمع هنا" — وهي أثمن حزمة على الإطلاق بالنسبة لماسح المنافذ. تذكّر هذا عند دخولك الأسبوع 6.

المخرج المطلوب: لقطة شاشة أو تصدير نصي لحزم المصافحة الثلاث مع تعليق يدوي على كل حقل، بالإضافة إلى نتائج فلاترك.

إذا رأيت هذا → فهذا معناه:

العَرَض السبب
لم تُلتقط أي حزمة إطلاقاً واجهة خاطئة مختارة في Wireshark — تحقق من ip a للعثور على واجهة labnet
ترى المصافحة لكن لا ترى أي بيانات هذا صحيح — SSH مشفّر. لا يُتوقع أي شيء مقروء هنا. وهذا هو جوهر الأسبوع 6
الاتصال يذهب إلى SYN ثم RST لا شيء يستمع على ذلك المنفذ في الهدف، أو أن جداراً نارياً رفضه
tcp.stream eq 0 لا يعرض شيئاً فهارس المجرى خاصة بكل عملية التقاط؛ جد الفهرس الحقيقي عبر النقر بالزر الأيمن → Follow → TCP Stream

المختبر 5.2 — التقاط تسجيل دخول بنص صريح (2 ساعة)

الهدف: شاهد بيانات الاعتماد تعبر الشبكة بترميز ASCII مقروء. هذا هو المختبر الذي يتذكره المتعلمون سنوات.

التهيئة: صفحة تسجيل دخول HTTP غير آمنة عمداً على آلة Ubuntu الوهمية. ميزانية صفر، وبلا أي تنزيلات — خادم Python من 20 سطراً.

الخطوات:

  1. على Ubuntu، أنشئ ~/insecure-login.py: 

    #!/usr/bin/env python3
from http.server import BaseHTTPRequestHandler, HTTPServer

PAGE = b"""<html><body><h3>Lab Login</h3>
<form method="POST" action="/login">
  User: <input name="username"><br>
  Pass: <input name="password" type="password"><br>
  <input type="submit" value="Log in">
</form></body></html>"""

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.end_headers()
        self.wfile.write(PAGE)
    def do_POST(self):
        n = int(self.headers.get("Content-Length", 0))
        body = self.rfile.read(n)
        print("CREDS RECEIVED:", body.decode(errors="replace"), flush=True)
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok")

HTTPServer(("0.0.0.0", 8080), H).serve_forever()

  2. شغّله: python3 ~/insecure-login.py

  3. على Kali، ابدأ التقاطاً مفلتراً على tcp.port == 8080.
  4. في متصفح Kali، زُر http://<ubuntu-ip>:8080، واكتب اسم المستخدم student وكلمة المرور SuperSecret123، ثم أرسل.

  5. أوقف الالتقاط وجد كلمة مرورك. استخدم هذين الفلترين بالترتيب: 

    http.request.method == "POST"
http contains "SuperSecret123"

  6. انقر بزر الفأرة الأيمن على حزمة POST → Follow → HTTP Stream. اقرأ الطلب الخام. كلمة المرور مكشوفة بنص ASCII صريح.

  7. الآن كرّر الأمر عبر HTTPS. تصفّح أي موقع HTTPS حقيقي، وسجّل الدخول فيه بحساب مؤقت لا قيمة له، والتقط الحركة، وجرّب الفلتر نفسه. سترى سجلات TLS ولا شيء مقروء. سجّل ما الذي تغيّر ولماذا.
  8. كرّر الأمر على الشبكة نفسها من منظور الهدف. شغّل sudo tcpdump -i <iface> -A 'tcp port 8080' على Ubuntu بينما تسجّل الدخول من Kali. أين ظهرت بيانات الاعتماد مرة أخرى؟

المخرج المطلوب: بيانات الاعتماد بنص صريح ودون base64، مستخرجة من التقاطك أنت، بالإضافة إلى فقرة واحدة تشرح ما كان سيملكه مهاجم سلبي على شبكة Wi-Fi نفسها.

⚠️ هذا مختبرك أنت، وكلمة المرور هذه مؤقتة ولا قيمة لها. لا تفعل هذا أبداً على شبكة لا تملكها — التقاط حركة شخص آخر جريمة جنائية في معظم الدول، بغض النظر عن النية.

المختبر 5.3 — تتبّع تحليل DNS (1.5 ساعة)

الهدف: شاهد الحزم الفعلية التي تقف خلف عبارة "أكتب اسماً في المتصفح".

الخطوات:

  1. على Kali، ابدأ التقاطاً بفلتر udp.port == 53.

  2. امسح الذاكرة المؤقتة وابحث عن نطاق: 

    sudo resolvectl flush-caches     # or: sudo systemd-resolve --flush-caches
dig www.wikipedia.org

  3. في Wireshark، جد حزمة الاستعلام. وسّع DNS. سجّل: معرّف المعاملة (transaction ID)، الأعلام، اسم السؤال، نوع الاستعلام (A)، وسجلات الجواب في الاستجابة مع مدة صلاحيتها TTL.

  4. الآن استعلم عن كل نوع سجل بشكل مقصود والتقط كلاً منها: 

    dig A wikipedia.org
dig AAAA wikipedia.org
dig MX gmail.com
dig NS wikipedia.org
dig TXT google.com
dig CNAME www.github.com
dig +trace www.wikipedia.org      # watch iterative resolution from the root

  5. dig +trace هو الدرس كله. اقرأ مخرجاته من الأعلى إلى الأسفل. سترى الاستعلام يذهب إلى خادم الجذر (root)، ثم إلى خادم النطاق الأعلى (TLD) الخاص بـ .org، ثم إلى خادم Wikipedia المسؤول (authoritative). هذا هو التحليل التكراري (iterative).

  6. التعاودي مقابل التكراري. جهازك يسأل المحلّل سؤالاً واحداً وينتظر جواباً نهائياً واحداً — هذا تعاودي (recursive). المحلّل هو من يقوم بالتنقل بنفسه — هذا تكراري (iterative). اكتب التعريفين في ملاحظاتك مع تسمية الأطراف.
  7. عبر TCP؟ شغّل dig +tcp wikipedia.org بالفلتر نفسه لكن غيّره إلى tcp.port == 53. لماذا يستخدم DNS أحياناً TCP؟ (تلميح: ماذا يحدث عندما يكون الجواب أكبر من أن يتسع في حزمة UDP واحدة؟)

المخرج المطلوب: لقطات شاشة لاستعلام DNS واستجابته مع تعليق على سجل الجواب و TTL، بالإضافة إلى مخرجات dig +trace مع تسمية كل مستوى من مستويات الخوادم الثلاثة.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

This is the week the network stops being abstract and becomes visible. And what is visible is mostly unprotected.

Three things worth internalizing:

  1. Unencrypted protocols leak everything to anyone on the path. In Lab 5.2 you read your own password out of a packet capture. No exploit was involved. No vulnerability was exploited. HTTP simply does not encrypt anything — the username and password are bytes in a TCP payload, and anyone who can see the packets can read them. FTP, Telnet, SMTP, POP3, IMAP, SNMP v1/v2, and plain LDAP all behave the same way. The reason HTTPS matters is not that it is "more modern"; it is that without it, there is no confidentiality at all. When you study a real breach, ask about the protocol — an astonishing number of credential exposures come down to a service that was simply speaking in the clear.

  2. DNS is a control channel, and attackers use it as one. DNS was designed for resolution, not security. Three consequences:

  • DNS poisoning / spoofing: if an attacker can inject a forged response before the real one arrives — recall from Week 4 that UDP has no handshake — they can redirect you to their own server while the address bar still shows the correct name. Defences exist (DNSSEC, and resolvers that randomise source ports and transaction IDs), but the underlying protocol remains fundamentally trusting.
  • DNS tunnelling: a client can encode arbitrary data inside DNS query names, and receive data back in TXT or CNAME responses. Because DNS egress is almost always permitted through firewalls — nothing works without it — this becomes an exfiltration channel. The signature is distinctive: many queries to one domain, with long, high-entropy, base32-looking subdomains, at regular intervals. This is one of the most reliable detection opportunities in network security, and you now know exactly what to look for.
  • DNS as reconnaissance: before touching a target, an attacker enumerates subdomains, mail servers, and TXT records. Every record you publish is intelligence. dev-, staging-, jenkins- in a hostname tells them where the soft targets are.
  1. DHCP starvation and rogue servers — the attacks nobody expects. DHCP has no authentication either. A host that floods Discover messages with random MAC addresses can exhaust a server's entire address pool; legitimate clients then get nothing, and new devices cannot join the network — a denial of service delivered entirely at layer 2. Worse: an attacker who runs their own DHCP server can answer faster than the real one and hand out a malicious gateway and DNS server. Every victim then routes through the attacker, or resolves names through them. Combine that with Week 4's ARP spoofing and you have a complete local man-in-the-middle setup built entirely from unauthenticated protocols. This is why DHCP snooping and port security exist on managed switches — and precisely why a flat, unmanaged network is dangerous.

The thread connecting Weeks 4, 5, and 6: ARP trusts, DNS trusts, DHCP trusts, and TCP will happily talk to whoever answers. Almost none of the foundational internet protocols were designed with an adversary on the wire. Everything that keeps you safe today is a layer built on top — TLS, DNSSEC, DHCP snooping, 802.1X — precisely because the foundations could not be fixed without breaking the world.

هذا هو الأسبوع الذي تتوقف فيه الشبكة عن كونها مجردة وتصبح مرئية. وما هو مرئي في معظمه غير محمي.

ثلاثة أمور تستحق أن تستوعبها جيداً:

  1. البروتوكولات غير المشفّرة تسرّب كل شيء إلى أي شخص على المسار. في المختبر 5.2 قرأت كلمة مرورك بنفسك من داخل ملف التقاط حزم. لم يكن هناك أي استغلال. ولم تُستغل أي ثغرة. HTTP ببساطة لا يشفّر شيئاً — اسم المستخدم وكلمة المرور مجرد بايتات داخل حمولة TCP، وأي شخص يرى الحزم يستطيع قراءتها. و FTP و Telnet و SMTP و POP3 و IMAP و SNMP v1/v2 و LDAP غير المشفّر تسلك السلوك نفسه تماماً. سبب أهمية HTTPS ليس أنه "أحدث"، بل أنه بدونه لا توجد سرية على الإطلاق. عندما تدرس اختراقاً حقيقياً، اسأل عن البروتوكول — فعدد مذهل من حالات تسريب بيانات الاعتماد يعود إلى خدمة كانت تتحدث بالنص الصريح فقط.

  2. DNS قناة تحكم، والمهاجمون يستخدمونها كذلك. صُمّم DNS للتحليل، لا للأمان. ولهذا ثلاث نتائج:

  • تسميم / انتحال DNS: إذا استطاع مهاجم حقن استجابة مزيفة قبل وصول الاستجابة الحقيقية — تذكّر من الأسبوع 4 أن UDP بلا مصافحة — فيمكنه توجيهك إلى خادمه الخاص بينما لا يزال شريط العنوان يعرض الاسم الصحيح. توجد دفاعات (DNSSEC، ومحلّلات تعشوّش منافذ المصدر ومعرّفات المعاملات)، لكن البروتوكول الأساسي يبقى واثقاً بشكل جذري.
  • نفق DNS: يستطيع العميل ترميز بيانات اعتباطية داخل أسماء استعلامات DNS، واستقبال بيانات في ردود TXT أو CNAME. ولأن خروج DNS مسموح دائماً تقريباً عبر الجدران النارية — فلا شيء يعمل بدونه — يصبح هذا قناة تسريب. والبصمة مميزة: استعلامات كثيرة لنطاق واحد، بأسماء فرعية طويلة عالية العشوائية تشبه base32، على فترات منتظمة. هذه واحدة من أكثر فرص الكشف موثوقية في أمن الشبكات، وأنت الآن تعرف بالضبط ما الذي تبحث عنه.
  • DNS كأداة استطلاع: قبل أن يلمس الهدف، يعدّد المهاجم النطاقات الفرعية وخوادم البريد وسجلات TXT. كل سجل تنشره هو معلومة استخبارية. وجود dev- أو staging- أو jenkins- في اسم مضيف يدلّهم على مواضع الأهداف الرخوة.
  1. استنزاف DHCP والخوادم المزيّفة — الهجمات التي لا يتوقعها أحد. DHCP أيضاً بلا مصادقة. فالجهاز الذي يغرق الشبكة برسائل Discover بعناوين MAC عشوائية يستطيع استنفاد مخزون العناوين بالكامل لدى الخادم؛ فلا يحصل العملاء الشرعيون على شيء، ولا تستطيع الأجهزة الجديدة الانضمام إلى الشبكة — حرمان من الخدمة يُنفَّذ بالكامل في الطبقة الثانية. والأسوأ: المهاجم الذي يشغّل خادم DHCP خاصاً به يستطيع الرد أسرع من الخادم الحقيقي ويمنح الضحايا بوابة وخادم DNS خبيثين. فيمرّ كل ضحية عبر المهاجم، أو يحلّ الأسماء من خلاله. اجمع هذا مع تسميم ARP من الأسبوع 4 فتحصل على منظومة رجل في المنتصف محلية كاملة مبنية بكاملها من بروتوكولات بلا مصادقة. لهذا يوجد DHCP snooping و port security على المبدلات المُدارة — ولهذا تحديداً تُعدّ الشبكة المسطحة غير المُدارة خطرة.

الخيط الذي يربط الأسابيع 4 و 5 و 6: ARP يثق، و DNS يثق، و DHCP يثق، و TCP سيتحدث بارتياح مع أي طرف يرد عليه. لا يكاد أي بروتوكول من بروتوكولات الإنترنت الأساسية قد صُمّم وبيده خصم على السلك. وكل ما يحميك اليوم هو طبقة مبنية فوق ذلك — TLS و DNSSEC و DHCP snooping و 802.1X — تحديداً لأن الأساسات لم يكن ممكناً إصلاحها دون تدمير العالم كله.

TCP — المصافحة الثلاثية (Three-Way Handshake)

قبل أن يتبادل أي طرفين بيانات عبر TCP، يجب أن يتفقا على بدء الاتصال. هذا الاتفاق يحدث في ثلاث رسائل تُسمى المصافحة الثلاثية.

لماذا ثلاث رسائل وليست رسالتين؟ لأن كلاً من الطرفين يجب أن يتأكد من شيئين: أن الآخر يسمعه، وأن الآخر جاهز. رسالتان لا تكفيان لتأكيد الاتجاهين معاً.

الخطوات:

# الرسالة المُرسِل الأعلام (Flags) المعنى
1 SYN العميل SYN=1 "أريد بدء اتصال، ورقم تسلسلي الأولي هو X"
2 SYN-ACK الخادم SYN=1, ACK=1 "موافق، رقمي التسلسلي هو Y، وأتوقع منك X+1"
3 ACK العميل ACK=1 "تمام، أتوقع منك Y+1"

مثال رقمي كامل:

العميل  ──── SYN  seq=1000 ─────────────────────►  الخادم
العميل  ◄─── SYN-ACK  seq=5000  ack=1001 ────────  الخادم
العميل  ──── ACK  seq=1001  ack=5001 ───────────►  الخادم

قراءة المثال:

  • العميل بدأ برقم تسلسلي 1000.
  • الخادم رد برقمه 5000، ويؤكد استلام 1001 (أي 1000 + 1).
  • العميل أكّد 5001 (أي 5000 + 1).

رقم التسلسل (Sequence Number) ليس "رقم الرسالة" بل موضع البايت الأول في مجرى البيانات. لهذا يزيد بمقدار حجم البيانات المُرسلة، وليس بمقدار 1 دائماً.

أعلام TCP (Flags) — لغة الاتصال

العلم الاسم المعنى متى تراه
SYN Synchronize طلب بدء اتصال أول رسالة فقط
ACK Acknowledge تأكيد استلام في معظم الرسائل بعد الأولى
FIN Finish "انتهيت، أريد الإغلاق بلطف" عند إغلاق طبيعي
RST Reset "أغلق فوراً" — رفض أو خطأ عند منفذ مغلق أو اتصال غير صالح
PSH Push "سلّم هذه البيانات للتطبيق الآن" عند إرسال بيانات
URG Urgent بيانات عاجلة نادر جداً

RST أهم علم أمنياً: عندما ترسل حزمة إلى منفذ مغلق، يرد الهدف بـ RST. وعندما يُسقط جدار ناري الحزمة بصمت، لا يرد بشيء. هذا الفرق بالضبط هو ما يميّز منفذ مغلق (closed) عن منفذ مُرشَّح (filtered) — وهو أساس عمل أي ماسح منافذ. تذكّر هذا في الأسبوع السادس.

الإغلاق (Teardown) — لماذا أربع رسائل؟

TCP اتصال ثنائي الاتجاه — كل اتجاه يُغلق على حدة:

العميل  ──── FIN ──────────────────────────────►  الخادم     (1) أريد الإغلاق
العميل  ◄─── ACK ──────────────────────────────    الخادم     (2) تمام، استلمت
العميل  ◄─── FIN ──────────────────────────────    الخادم     (3) وأنا أيضاً أريد الإغلاق
العميل  ──── ACK ──────────────────────────────►  الخادم     (4) تمام

لماذا لا يكفي FIN واحد؟ لأن إغلاق اتجاه لا يعني إغلاق الآخر. الخادم قد يكون لا يزال يرسل بيانات. لهذا يُغلق كل اتجاه باستقلالية.

TCP مقابل UDP

المعيار TCP UDP
الاتصال يتطلب مصافحة لا يوجد اتصال
الموثوقية يضمن الوصول وإعادة الإرسال لا يضمن شيئاً
الترتيب مرتّب بالضرورة غير مرتّب
السرعة أبطأ (بسبب التأكيدات) أسرع بكثير
حجم الرأس 20 بايت على الأقل 8 بايت فقط
الاستخدام الويب، البريد، SSH، نقل الملفات DNS، DHCP، البث الحي، الألعاب

القاعدة العملية: استخدم TCP عندما لا يمكن تحمّل فقدان البيانات (تحميل صفحة، إرسال رسالة). استخدم UDP عندما السرعة أهم من الكمال (بث مباشر، مكالمة صوتية — لو فُقد إطار لن يلاحظه أحد).

المنافذ (Ports) — شقق في بناية واحدة

التشبيه: عنوان IP = عنوان البناية. المنفذ = رقم الشقة. الخادم قد يدير عشرات الخدمات على نفس العنوان، وكل خدمة لها شقتها (منفذها).

النطاقات الثلاثة:

النطاق المدى الاستخدام
Well-known 0 – 1023 الخدمات الأساسية (تحتاج صلاحيات root)
Registered 1024 – 49151 تطبيقات مسجّلة (MySQL مثلاً)
Dynamic / Ephemeral 49152 – 65535 منافذ مؤقتة يختارها العميل

منافذ يجب حفظها:

المنفذ البروتوكول الخدمة ملاحظة أمنية
21 TCP FTP نص صريح — بيانات الاعتماد مكشوفة
22 TCP SSH مشفّر — هدف دائم لهجمات التخمين
23 TCP Telnet نص صريح — يجب ألا يعمل أبداً
25 TCP SMTP البريد الصادر
53 TCP/UDP DNS UDP للاستعلام، TCP للردود الكبيرة
67/68 UDP DHCP 67 للخادم، 68 للعميل
80 TCP HTTP نص صريح
110 TCP POP3 نص صريح
143 TCP IMAP نص صريح
161 UDP SNMP v1/v2 بلا تشفير
389 TCP LDAP نص صريح — دليل المستخدمين
443 TCP HTTPS مشفّر
445 TCP SMB هدف تاريخي لأشهر الديدان
3306 TCP MySQL قاعدة بيانات
3389 TCP RDP سطح مكتب بعيد — هدف شائع
8080 TCP HTTP بديل

قاعدة أمنية: كل منفذ مفتوح = خدمة = سطح هجوم. أفضل دفاع هو إغلاق ما لا تحتاجه، وليس ترقيعه فقط.

ملاحظة عن المنافذ المؤقتة: في لينكس الحديث يبدأ المدى الديناميكي من 32768 حتى 60999 افتراضياً. هذا مهم عند قراءة نتائج أدوات المسح: منفذ مستخدم مثل 47132 هو على الأغلب منفذ عميل، وليس خدمة.

DNS — دفتر هاتف الإنترنت

المشكلة: البشر يحفظون الأسماء، والحواسيب تحتاج الأرقام. DNS هو الجسر.

هرمية الأسماء — تُقرأ من اليمين إلى اليسار:

www . wikipedia . org .
 │         │        │   └── الجذر (نقطة ضمنية)
 │         │        └────── النطاق الأعلى (TLD)
 │         └─────────────── النطاق المسجَّل
 └───────────────────────── اسم المضيف (Subdomain)

نوعا الاستعلام:

النوع المعنى من يقوم بالعمل
Recursive "أعطني الجواب النهائي" الخادم يتحمل المسؤولية كاملة
Iterative "أعطني أفضل جواب تعرفه" قد يكون إحالة لخادم آخر

سير الاستعلام الكامل:

  1. جهازك يسأل Recursive Resolver (مثل 1.1.1.1) سؤالاً تعاودياً.
  2. المحلّل يسأل خادم الجذر سؤالاً تكراريّاً → يرد: "لا أعرف، اسأل خادم .org".
  3. المحلّل يسأل خادم TLD الخاص بـ .org → يرد: "اسأل الخادم المسؤول عن wikipedia.org".
  4. المحلّل يسأل الخادم المسؤول (Authoritative) → يرد بالعنوان النهائي.
  5. المحلّل يُخزّن النتيجة مؤقتاً حسب TTL ويرد عليك.

أنواع السجلات (Record Types):

النوع المعنى مثال
A عنوان IPv4 wikipedia.org → 208.80.154.224
AAAA عنوان IPv6
CNAME اسم بديل (Alias) www → wikipedia.org
MX خادم البريد gmail.com → gmail-smtp-in...
NS خوادم الأسماء المسؤولة من يدير النطاق
TXT نص حر التحقق من الملكية، SPF، ونفق البيانات
SOA بداية الصلاحية معلومات إدارة النطاق
PTR عكسي من IP إلى اسم

TXT و CNAME هما نجما الهجمات: لأن كليهما يمكن أن يحمل نصاً حراً، استُخدما في أنفاق DNS (DNS Tunneling) لتهريب البيانات خارج الشبكة. العلامة المميزة: استعلامات كثيرة لنفس النطاق، بأسماء فرعية طويلة وعشوائية، على فترات منتظمة.

DHCP — كيف تحصل على عنوانك (DORA)

DORA = أربع رسائل:

الحرف الرسالة الاتجاه المحتوى
D Discover العميل → بث "هل يوجد خادم DHCP؟ أحتاج عنواناً"
O Offer الخادم → العميل "أستطيع إعطاءك 192.168.1.50"
R Request العميل → بث "أريد 192.168.1.50 فعلاً"
A Ack الخادم → العميل "تم، العنوان لك لمدة كذا"

لماذا Discover و Request بث (Broadcast)؟ لأن العميل لا يملك عنوان IP بعد — فلا يستطيع إرسال شيء موجّه. يبثّ للجميع أملاً في أن يسمعه خادم.

خيارات DHCP المهمة: 3 = البوابة · 6 = خوادم DNS · 51 = مدة الإيجار · 1 = قناع الشبكة.

لماذا يهمنا أمنياً؟

  • تجويع DHCP (Starvation): المهاجم يطلب عناوين بآلاف عناوين MAC وهمية حتى ينفد مخزون الخادم، فلا يستطيع أي جهاز جديد الدخول. حرمان خدمة من الطبقة الثانية.
  • خادم DHCP مزيّف (Rogue): مهاجم يشغّل خادمه الخاص ويرد أسرع من الخادم الحقيقي، فيمنح الضحايا بوابة وخادم DNS يملكه المهاجم. بعدها يمر كل شيء عبره. هذا هو أساس الرجل في المنتصف محلياً.

NAT/PAT — كيف يشارك بيت كامل عنواناً واحداً

المشكلة: عناوين IPv4 انتهت. لديك في البيت عشرون جهازاً وعنوان عام واحد من مزوّد الخدمة.

الحل — NAT/PAT: الموجّه يستبدل العنوان الخاص والمنفذ المؤقت بعنوانه العام ومنفذ جديد يميّز كل اتصال:

قبل بعد
192.168.1.10:51000 203.0.113.5:40001
192.168.1.11:51000 203.0.113.5:40002
192.168.1.12:51000 203.0.113.5:40003

الموجّه يحتفظ بـجدول ترجمة، وعندما يعود الرد يقلبه للخلف. لهذا لا يستطيع أحد من الخارج بدء اتصال بجهازك — لا يوجد مسار في الجدول حتى الآن. هذه فائدة أمنية جانبية ضخمة، وهي السبب في أن كل أجهزة المنزل مخفية خلف عنوان واحد.

تحذير: NAT ليس جداراً نارياً وليس حماية حقيقية — إنه أثر جانبي لنقص العناوين. عندما تسمح بتمرير منفذ (Port Forwarding) تُبطل هذه الحماية لذلك المنفذ تماماً.
