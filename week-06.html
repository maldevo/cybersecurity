Lab 6.1 — Firewalls with ufw, and reading the blocks (2h)

Goal: Write firewall rules, verify them from the outside, and find the denied traffic in the logs.

Setup: Ubuntu VM on labnet (Week 4). Kali as the client. Snapshot Ubuntu first — a badly ordered ufw rule can lock you out of your own SSH.

Steps:

  1. Baseline: sudo ufw status verbose. If inactive, note that.

  2. Block SSH from Kali only — leave everything else working: 

    sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.50.10 to any port 22 proto tcp   # allow Kali
sudo ufw enable

  3. Verify from the outside, not the inside. From Kali: nc -vz 192.168.50.20 22. Now change the rule to deny Kali's address and re-test: sudo ufw delete allow from 192.168.50.10 to any port 22 proto tcp, then nc -vz again. What changed — a RST, or nothing at all?

  4. Read the block. On Ubuntu: 

    sudo grep "UFW BLOCK" /var/log/ufw.log /var/log/syslog 2>/dev/null | tail -20
    Identify: source IP, destination port, protocol, and the interface. This is what a defender sees when you scan them.

  5. Add an allow rule for a web service and prove it works end to end: sudo ufw allow 8080/tcp, then run the Python server from Week 5 Lab 5.2 and browse to it from Kali.

  6. Rule ordering drill. ufw is order-sensitive. Create a rule that allows port 80, then a deny for the same port, then inspect sudo ufw status numbered. Which wins, and why? Delete the wrong one.
  7. Compare to raw iptables. Run sudo iptables -L -v -n and find the rules ufw created for you. ufw is a friendly front end over the same kernel machinery.

Deliverable: Your final rule set (sudo ufw status numbered), plus the log line showing a blocked connection from Kali with every field explained.

If you see this → it means:

Symptom Cause
You locked yourself out of SSH default deny incoming with no allow rule for your management address. Fix via the VM console, or restore your snapshot
nc -vz hangs instead of failing fast ufw drops silently by default — no RST comes back. This is the filtered state you'll meet in Nmap
No UFW BLOCK lines in the log sudo ufw logging on, then retry. Also check both ufw.log and syslog
Rules exist but don't take effect Forgot sudo ufw enable, or an earlier allow rule is shadowing your deny

Lab 6.2 — TLS: inspect a real certificate (1h)

Goal: See the trust chain, not just the padlock.

Steps:

  1. Pull a live certificate: 

    openssl s_client -connect example.com:443 -servername example.com </dev/null | openssl x509 -noout -text

  2. Record from the output: Subject, Issuer, Validity (notBefore / notAfter), Subject Alternative Names, public key algorithm and size, and signature algorithm.

  3. Who signed it? The Issuer is a Certificate Authority. Now find the root: openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null and read the chain — leaf → intermediate → root.
  4. Break it deliberately. Run openssl s_client -connect <your-ubuntu-ip>:443 </dev/null against nothing, and see the failure. Then, if you have time, generate a self-signed certificate on Ubuntu, serve it, and watch the browser refuse it with NET::ERR_CERT_AUTHORITY_INVALID. Why does the browser refuse? Because the signer is not in its trust store.
  5. What TLS does not do. Visit a site over HTTPS and log in with a throwaway account. Capture on Kali. You already know from Week 5 that the payload is unreadable — verify it. Now answer the harder question: the destination IP and the hostname you connected to are still visible even over HTTPS. What does that tell you about what TLS protects, and what it leaves exposed?

Deliverable: The certificate chain annotated by hand (leaf / intermediate / root), plus a written answer to step 5 distinguishing content confidentiality from metadata confidentiality.

Lab 6.3 — Nmap: from discovery to service identification (2.5h)

Goal: Scan your own lab every way Nmap allows, and understand what each scan type actually sends.

Setup: Kali (192.168.50.10) scanning Ubuntu (192.168.50.20) on labnet. Add a couple of services to Ubuntu so there is something to find: SSH (already running), the Python HTTP server on 8080, and sudo apt install vsftpd -y for FTP on 21 (then stop it later — and remember it speaks plaintext).

⚠️ Only scan labnet. Every command below is an intrusion attempt against anything you do not own. The authorization rule from Week 1 has no exceptions.

Steps:

  1. Confirm the target is alive without scanning ports: 

    nmap -sn 192.168.50.0/24
    Note: on a local network this uses ARP, so it is fast and reliable. Compare to Week 4's arp-scan.

  2. Fast port scan: 

    nmap 192.168.50.20
    Nmap scans the top 1000 TCP ports by default. Which are open?

  3. Compare the scan types. Run each and record the results side by side: 

    sudo nmap -sS 192.168.50.20        # SYN "half-open" scan — needs root
nmap -sT 192.168.50.20            # full TCP connect — no root needed
sudo nmap -sU --top-ports 20 192.168.50.20   # UDP — slow, expect filtered
sudo nmap -sA 192.168.50.20       # ACK scan — maps firewall rules, not open ports
    Questions to answer: Which scan completed fastest? Which one appears in Ubuntu's logs, and which does not? (-sT completes the handshake, so the application sees a connection; -sS never completes it, so it often never reaches the application layer.) This is the difference between stealthy and loud.

  4. Port states. With ufw enabled on Ubuntu from Lab 6.1, scan again. Record which ports report open, closed, and filtered, and explain each in terms of what packet came back (or didn't).

  5. Scan a range and save it: 
    sudo nmap -sS -p 1-1000 -oA ~/lab/week6/scan-tcp 192.168.50.20
    -oA writes three formats at once (.nmap, .xml, .gnmap). You will want the XML in Week 10 when you script against scan results.

Deliverable: A comparison table: scan type → command → time taken → ports found → visible in target logs (yes/no) → why.

Lab 6.4 — Services, versions, NSE, and the defender's view (1.5h)

Goal: Go from "port 22 is open" to "this is OpenSSH version X on Ubuntu" — then watch yourself get caught.

Steps:

  1. Version detection: 

    sudo nmap -sV 192.168.50.20
    Record the exact service and version string for each open port. Then find it on the host: ssh -V and dpkg -l | grep openssh-server on Ubuntu. Does the banner match the installed package? Why might it not? (Banners can be edited, and package versions differ from protocol banners.)

  2. Operating system detection: 

    sudo nmap -O 192.168.50.20
    Read the OS CPE and OS details lines. Nmap guesses the OS from TCP/IP stack behaviour, not from banners. How confident is it?

  3. Scripts. NSE scripts turn Nmap from a port scanner into a light vulnerability checker. 

    nmap -sV -sC 192.168.50.20                          # default scripts (-sC == --script=default)
nmap --script http-title -p 8080 192.168.50.20      # grab the page title
nmap --script ssh-hostkey -p 22 192.168.50.20       # collect host keys
nmap --script-help http-title                      # read what a script does BEFORE running it
    Browse the NSE Script Index and note the categories: safe, default, discovery, version, auth, brute, vuln, exploit, intrusive.

  4. Reconnaissance value. Look at your scan output as an attacker would. Given only 22/tcp open OpenSSH 9.x, 21/tcp open vsftpd 3.0.x, 8080/tcp open Python http.server, what are the three most promising next steps? Write them down.

  5. Now be the defender. On Ubuntu, while re-running the scan from Kali, watch it arrive: 

    sudo tcpdump -i enp0s8 -nn 'tcp[tcpflags] & tcp-syn != 0'   # SYN packets only
sudo tail -f /var/log/syslog /var/log/ufw.log
sudo ss -tn state syn-recv                                  # half-open connections
ip n                                                        # who is this, at layer 2?
    Record: how many SYN packets arrived. Which ports. Which source IP and MAC. Whether auth.log recorded anything (it will not, for -sS).

  6. Close the loop. Write a one-paragraph detection rule a defender could implement in plain language: "alert when a single source IP sends SYN packets to more than N distinct destination ports within T seconds." You have just written the core signature of every network IDS in existence. Next week you will use it from the other side.

Deliverable: Full -sV output, the NSE script results, and the defender's capture showing your own scan arriving — with the detection rule written in your own words.

If you see this → it means:

Symptom Cause
-sS says "requires root" SYN scans craft raw packets. Use sudo, or fall back to -sT
-sU reports open\|filtered for everything Normal. UDP gives no response when open and when filtered, so Nmap cannot distinguish. This ambiguity is a real property of UDP, not a bug
-O says "no exact matches" Nmap needs at least one open and one closed port to fingerprint the stack. Open more ports, or accept the guess
-sV reports a wildly wrong service Version detection guesses from banner text. A service on an unusual port confuses it — -sV --version-intensity 9 helps
Your scan is invisible in auth.log Expected for -sS. The connection never reached the application. Check the kernel level instead: ufw.log, tcpdump, conntrack

المختبر 6.1 — الجدران النارية مع ufw وقراءة الحظر (2 ساعة)

الهدف: اكتب قواعد جدار ناري، وتحقق منها من الخارج، وجد الحركة المرفوضة في السجلات.

التهيئة: آلة Ubuntu الوهمية على labnet (الأسبوع 4). و Kali كعميل. خُذ لقطة (snapshot) لـ Ubuntu أولاً — فقاعدة ufw بترتيب خاطئ قد تحجب عنك SSH الخاص بك.

الخطوات:

  1. خط الأساس: sudo ufw status verbose. إن كانت غير مفعّلة، فسجّل ذلك.

  2. احجب SSH من Kali وحدها — واترك كل شيء آخر يعمل: 

    sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.50.10 to any port 22 proto tcp   # allow Kali
sudo ufw enable

  3. تحقق من الخارج، لا من الداخل. من Kali: nc -vz 192.168.50.20 22. الآن غيّر القاعدة لترفض عنوان Kali وأعد الاختبار: sudo ufw delete allow from 192.168.50.10 to any port 22 proto tcp، ثم شغّل nc -vz مرة أخرى. ما الذي تغيّر — هل وصل RST، أم لا شيء على الإطلاق؟

  4. اقرأ الحظر. على Ubuntu: 

    sudo grep "UFW BLOCK" /var/log/ufw.log /var/log/syslog 2>/dev/null | tail -20
    حدّد: عنوان IP المصدر، ومنفذ الوجهة، والبروتوكول، والواجهة. هذا ما يراه المدافع عندما تمسحه.

  5. أضف قاعدة سماح لخدمة ويب وأثبت أنها تعمل من الطرف إلى الطرف: sudo ufw allow 8080/tcp، ثم شغّل خادم Python من المختبر 5.2 في الأسبوع 5 وتصفّحه من Kali.

  6. تدريب على ترتيب القواعد. ufw حسّاس للترتيب. أنشئ قاعدة تسمح بالمنفذ 80، ثم قاعدة deny للمنفذ نفسه، ثم افحص sudo ufw status numbered. أي القاعدتين تفوز، ولماذا؟ احذف القاعدة الخاطئة.
  7. قارن مع iptables الخام. شغّل sudo iptables -L -v -n وجد القواعد التي أنشأها ufw نيابة عنك. ufw مجرد واجهة ودّية فوق نفس آليات النواة (kernel).

المخرج المطلوب: مجموعة قواعدك النهائية (sudo ufw status numbered)، بالإضافة إلى سطر السجل الذي يُظهر اتصالاً محجوباً من Kali مع شرح كل حقل فيه.

إذا رأيت هذا → فهذا معناه:

العَرَض السبب
حَجبت عن نفسك SSH default deny incoming بلا قاعدة سماح لعنوان الإدارة لديك. أصلح الأمر من وحدة تحكم الآلة الوهمية، أو استعد اللقطة
nc -vz يتعلّق بدل أن يفشل سريعاً ufw يُسقط الحزم بصمت افتراضياً — فلا يعود أي RST. هذه هي حالة filtered التي ستلتقي بها في Nmap
لا توجد أسطر UFW BLOCK في السجل شغّل sudo ufw logging on ثم أعد المحاولة. وتحقق أيضاً من ufw.log و syslog معاً
القواعد موجودة لكنها لا تنفّذ نسيت sudo ufw enable، أو أن قاعدة allow أسبق تُظلّل قاعدة deny لديك

المختبر 6.2 — TLS: افحص شهادة حقيقية (1 ساعة)

الهدف: أن ترى سلسلة الثقة، لا مجرد القفل في شريط العنوان.

الخطوات:

  1. اسحب شهادة حيّة: 

    openssl s_client -connect example.com:443 -servername example.com </dev/null | openssl x509 -noout -text

  2. سجّل من المخرجات: Subject، و Issuer، و الصلاحية (notBefore / notAfter)، و Subject Alternative Names، وخوارزمية المفتاح العام وحجمه، وخوارزمية التوقيع.

  3. من وقّعها؟ حقل Issuer هو جهة إصدار الشهادات. الآن جد الجذر: openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null واقرأ السلسلة — الورقة (leaf) ← الوسيط (intermediate) ← الجذر (root).
  4. اكسرها عمداً. شغّل openssl s_client -connect <your-ubuntu-ip>:443 </dev/null على لا شيء، وشاهد الفشل. ثم إن كان لديك وقت، أنشئ شهادة موقّعة ذاتياً على Ubuntu، وقدّمها، وراقب المتصفح يرفضها بالخطأ NET::ERR_CERT_AUTHORITY_INVALID. لماذا يرفض المتصفح؟ لأن الجهة الموقّعة ليست في مخزن الثقة لديه.
  5. ما لا يفعله TLS. زُر موقعاً عبر HTTPS وسجّل الدخول بحساب مؤقت لا قيمة له. والتقط الحزم على Kali. أنت تعرف من الأسبوع 5 أن الحمولة غير مقروءة — فأثبت ذلك بنفسك. الآن أجب عن السؤال الأصعب: عنوان IP الوجهة واسم المضيف الذي اتصلت به يبقيان مرئيين حتى مع HTTPS. ماذا يقول لك ذلك عمّا يحميه TLS، وعمّا يتركه مكشوفاً؟

المخرج المطلوب: سلسلة الشهادة معلَّقاً عليها يدوياً (leaf / intermediate / root)، بالإضافة إلى إجابة مكتوبة عن الخطوة 5 تفرّق بين سرّية المحتوى وسرّية البيانات الوصفية (metadata).

المختبر 6.3 — Nmap: من الاكتشاف إلى تحديد الخدمات (2.5 ساعة)

الهدف: امسح مختبرك أنت بكل الطرق التي يتيحها Nmap، وافهم ما يرسله كل نوع مسح فعلياً.

التهيئة: Kali (192.168.50.10) يمسح Ubuntu (192.168.50.20) على labnet. أضف خدمتين أو ثلاثاً إلى Ubuntu ليكون هناك ما يمكن إيجاده: SSH (يعمل بالفعل)، وخادم HTTP بلغة Python على المنفذ 8080، والأمر sudo apt install vsftpd -y لخدمة FTP على المنفذ 21 (ثم أوقفها لاحقاً — وتذكّر أنها تتحدث بالنص الصريح).

⚠️ امسح labnet فقط. كل أمر بالأسفل هو محاولة اختراق لأي شيء لا تملكه. وقاعدة التصريح من الأسبوع 1 لا استثناءات فيها.

الخطوات:

  1. تأكّد أن الهدف حيّ دون مسح المنافذ: 

    nmap -sn 192.168.50.0/24
    ملاحظة: على شبكة محلية يستخدم هذا ARP، لذا فهو سريع وموثوق. قارنه بـ arp-scan من الأسبوع 4.

  2. مسح منافذ سريع: 

    nmap 192.168.50.20
    يمسح Nmap أعلى 1000 منفذ TCP افتراضياً. أيها مفتوح؟

  3. قارن أنواع المسح. شغّل كل نوع وسجّل النتائج جنباً إلى جنب: 

    sudo nmap -sS 192.168.50.20        # SYN "half-open" scan — needs root
nmap -sT 192.168.50.20            # full TCP connect — no root needed
sudo nmap -sU --top-ports 20 192.168.50.20   # UDP — slow, expect filtered
sudo nmap -sA 192.168.50.20       # ACK scan — maps firewall rules, not open ports
    أسئلة يجب أن تجيب عنها: أي مسح انتهى أسرع؟ وأيها يظهر في سجلات Ubuntu، وأيها لا يظهر؟ (-sT يُكمل المصافحة، فيرى التطبيق اتصالاً؛ أما -sS فلا يُكملها أبداً، لذا كثيراً ما لا يصل إلى طبقة التطبيق أصلاً.) هذا هو الفرق بين التخفّي و الضجيج.

  4. حالات المنفذ. بعد تفعيل ufw على Ubuntu من المختبر 6.1، امسح مرة أخرى. سجّل أي المنافذ يُبلَّغ عنها بـ open و closed و filtered، واشرح كل حالة بدلالة الحزمة التي عادت (أو لم تعد).

  5. امسح نطاقاً واحفظه: 
    sudo nmap -sS -p 1-1000 -oA ~/lab/week6/scan-tcp 192.168.50.20
    -oA يكتب ثلاث صيغ في وقت واحد (.nmap و .xml و .gnmap). وستريد ملف XML في الأسبوع 10 عندما تكتب سكربتات تتعامل مع نتائج المسح.

المخرج المطلوب: جدول مقارنة: نوع المسح → الأمر → الزمن المستغرق → المنافذ المكتشفة → مرئي في سجلات الهدف (نعم/لا) → لماذا.

المختبر 6.4 — الخدمات والإصدارات و NSE ومنظور المدافع (1.5 ساعة)

الهدف: انتقل من "المنفذ 22 مفتوح" إلى "هذا OpenSSH الإصدار X على Ubuntu" — ثم راقب نفسك وأنت تُكتشف.

الخطوات:

  1. كشف الإصدار: 

    sudo nmap -sV 192.168.50.20
    سجّل نص الخدمة والإصدار بالضبط لكل منفذ مفتوح. ثم جدها على المضيف: ssh -V و dpkg -l | grep openssh-server على Ubuntu. هل يطابق البانر الحزمة المثبَّتة؟ ولماذا قد لا يطابق؟ (يمكن تعديل البانرات، وإصدارات الحزم تختلف عن بانرات البروتوكول.)

  2. كشف نظام التشغيل: 

    sudo nmap -O 192.168.50.20
    اقرأ سطري OS CPE و OS details. يخمّن Nmap نظام التشغيل من سلوك حزمة TCP/IP، لا من البانرات. فما مدى ثقته؟

  3. السكربتات. سكربتات NSE تحوّل Nmap من ماسح منافذ إلى مدقّق ثغرات خفيف. 

    nmap -sV -sC 192.168.50.20                          # default scripts (-sC == --script=default)
nmap --script http-title -p 8080 192.168.50.20      # grab the page title
nmap --script ssh-hostkey -p 22 192.168.50.20       # collect host keys
nmap --script-help http-title                      # read what a script does BEFORE running it
    تصفّح NSE Script Index وسجّل الفئات: safe و default و discovery و version و auth و brute و vuln و exploit و intrusive.

  4. القيمة الاستخباراتية. انظر إلى مخرجات مسحك بعين المهاجم. بمعطى 22/tcp open OpenSSH 9.x و 21/tcp open vsftpd 3.0.x و 8080/tcp open Python http.server فقط، ما الخطوات الثلاث التالية الأكثر جدوى؟ اكتبها.

  5. كن المدافع الآن. على Ubuntu، وأثناء إعادة تشغيل المسح من Kali، راقبه وهو يصل: 

    sudo tcpdump -i enp0s8 -nn 'tcp[tcpflags] & tcp-syn != 0'   # SYN packets only
sudo tail -f /var/log/syslog /var/log/ufw.log
sudo ss -tn state syn-recv                                  # half-open connections
ip n                                                        # who is this, at layer 2?
    سجّل: كم حزمة SYN وصلت. وأي المنافذ. وما عنوان IP و MAC المصدر. وهل سجّل auth.log أي شيء (لن يفعل، مع -sS).

  6. أغلق الحلقة. اكتب في فقرة واحدة قاعدة كشف يستطيع مدافع تنفيذها بلغة بسيطة: "نبّه عندما يرسل عنوان IP مصدر واحد حزماً من نوع SYN إلى أكثر من N منفذ وجهة مختلف خلال T ثانية." لقد كتبت للتو التوقيع الجوهري لكل نظام كشف تسلل شبكي موجود. وفي الأسبوع القادم ستستخدمه من الجهة الأخرى.

المخرج المطلوب: مخرجات -sV كاملة، ونتائج سكربت NSE، والتقاط المدافع الذي يُظهر مسحك أنت وهو يصل — مع قاعدة الكشف مكتوبة بكلماتك.

إذا رأيت هذا → فهذا معناه:

العَرَض السبب
-sS يقول "requires root" مسحات SYN تصنع حزماً خاماً (raw). استخدم sudo، أو ارجع إلى -sT
-sU يُبلّغ open\|filtered عن كل شيء هذا طبيعي. فـ UDP لا يعطي أي رد سواء كان المنفذ مفتوحاً أو مُرشَّحاً، فلا يستطيع Nmap التمييز. هذا الغموض خاصية حقيقية في UDP، وليس خللاً

-sV يُبلّغ عن خدمة خاطئة تماماً كشف الإصدار يخمّن من نص البانر. وخدمة على منفذ غير معتاد تربكه — و-sV --version-intensity 9 يساعد

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

This week you crossed a line: you stopped watching traffic and started sending it.

Three things worth internalizing:

  1. A port scan is not an attack — it is a question. And it is astonishing how much the answer reveals. With one nmap -sV an attacker learns which services are running, which versions, which operating system family, and often which specific distribution. From there, the reasoning is mechanical: an outdated version has published vulnerabilities; an FTP service means credentials may cross the wire in plaintext (Week 5 taught you exactly what that looks like); an exposed database port means the database itself is the perimeter now. The scan does not break anything — it tells the attacker where to aim. This is why reducing the attack surface is a defence in its own right: every service you switch off is a question the attacker no longer gets to ask.

  2. Firewalls are evadable, and you need to know that before you trust one. Firewalls make decisions from packet headers: source address, destination port, flags. Every one of those fields can be manipulated. Fragmentation can split a header across packets so a simple filter cannot reassemble it. Source-port manipulation exploits lazy rules ("allow anything from port 53" reasoning). Decoy scans mix the attacker's packets with fake source addresses so the log shows a crowd, not a person. Slow scans spread probes over hours so no threshold is tripped. None of this means firewalls are useless — it means a firewall is a policy enforcement point, not a wall. The correct mental model: firewalls reduce noise and enforce intent; they do not stop a determined adversary. That is why defence in depth exists.

  3. A VPN is not anonymity, and this is the single most misunderstood tool in security. A VPN moves your trust from your internet provider to your VPN provider. That is all it does. The VPN operator sees your traffic exactly as your ISP did — same metadata, same everything, minus the encryption you already had. If you are logged into an account, you are identified regardless of your IP. Browser fingerprinting, TLS metadata such as SNI, timing patterns, and simple behavioural consistency all survive a VPN change. And commercially, "no logs" is a policy claim, not a technical guarantee — you cannot audit a black box you do not control. VPNs are excellent for one specific thing: making an untrusted network (café Wi-Fi, hotel, airport) as safe as a trusted one. They are not a cloak. Anyone selling you the second thing is selling you a feeling.

The closing idea of Month 1. Line up the four weeks you have just finished: Week 3 taught you that systems keep records. Week 4 taught you that the network's foundations trust blindly. Week 5 showed you that unencrypted protocols hand over credentials to anyone watching. Week 6 showed you how an attacker asks questions, how a defender answers them, and where each defence actually fails.

That is the full loop: offence, defence, and evidence. You have now done all three. Everything from Week 7 onward is depth on this same shape.

ثلاثة أمور تستحق أن تستوعبها جيداً:

  1. مسح المنافذ ليس هجوماً — إنه سؤال. والمذهل هو كم يكشف الجواب. بأمر واحد nmap -sV يعرف المهاجم أي الخدمات تعمل، وأي الإصدارات، وأي عائلة أنظمة التشغيل، وغالباً أي توزيعة بالتحديد. ومن هناك يصبح الاستدلال آلياً: فالإصدار القديم له ثغرات منشورة؛ وخدمة FTP تعني أن بيانات الاعتماد قد تعبر السلك بالنص الصريح (وعلّمك الأسبوع 5 بالضبط كيف يبدو ذلك)؛ ومنفذ قاعدة بيانات مكشوف يعني أن قاعدة البيانات نفسها هي المحيط الآن. المسح لا يكسر شيئاً — بل يدلّ المهاجم على أين يصوّب. ولهذا فإن تقليص سطح الهجوم دفاع قائم بذاته: فكل خدمة تطفئها هي سؤال لم يعد المهاجم قادراً على طرحه.

  2. الجدران النارية قابلة للتجاوز، وعليك أن تعرف ذلك قبل أن تثق بأحدها. الجدار الناري يتخذ قراراته من ترويسات الحزم: عنوان المصدر، ومنفذ الوجهة، والأعلام. وكل حقل من هذه يمكن التلاعب به. فالتجزئة (Fragmentation) تستطيع تقسيم ترويسة على عدة حزم بحيث لا يستطيع فلتر بسيط إعادة تجميعها. والتلاعب بمنفذ المصدر يستغل القواعد المتكاسلة (منطق "اسمح بأي شيء من المنفذ 53"). ومسحات الطُّعم (Decoy) تخلط حزم المهاجم بعناوين مصدر مزيفة فيُظهر السجل حشداً لا شخصاً. والمسحات البطيئة توزّع السبر على ساعات فلا يُطلَق أي حد. لا شيء من هذا يعني أن الجدران النارية عديمة الفائدة — بل يعني أن الجدار الناري نقطة إنفاذ سياسة، لا جدار. والنموذج الذهني الصحيح هو: الجدران النارية تقلّل الضجيج وتنفّذ النية؛ لكنها لا توقف خصماً مصمماً. ولهذا يوجد الدفاع في العمق.

  3. VPN ليس إخفاءً للهوية، وهو الأداة الأكثر إساءةً في الفهم في مجال الأمن كله. الـ VPN ينقل ثقتك من مزوّد الإنترنت إلى مزوّد VPN. هذا كل ما يفعله. فمشغّل VPN يرى حركتك كما كان يراها مزوّد الإنترنت تماماً — نفس البيانات الوصفية، ونفس كل شيء، ناقصاً التشفير الذي كان لديك أصلاً. وإن كنت مسجِّلاً دخولك في حساب، فأنت معروف بهويتك مهما تغيّر عنوان IP. وبصمة المتصفح، وبيانات TLS الوصفية مثل SNI، وأنماط التوقيت، والاتساق السلوكي البسيط — كلها تبقى كما هي بعد تغيير VPN. وعلى المستوى التجاري، "لا سجلات" ادّعاء سياسة، لا ضمان تقني — فلا يمكنك تدقيق صندوق أسود لا تتحكم به. الـ VPN ممتاز لشيء واحد محدد: أن يجعل شبكة غير موثوقة (واي فاي مقهى، فندق، مطار) بسلامة شبكة موثوقة. وهو ليس عباءة. ومن يبيعك الأمر الثاني إنما يبيعك شعوراً.

TLS — الطبقة التي أنقذت الإنترنت

تذكّر درس الأسبوع الخامس: قرأت كلمة المرور من الحزم لأن HTTP لا يشفّر شيئاً. TLS هو الحل، وهو نفس البروتوكول الذي تراه في HTTPS (حيث الحرف S يعني Secure).

TLS يحقّق ثلاثة أهداف:

الهدف المعنى ماذا يمنع
السرّية (Confidentiality) لا أحد يقرأ المحتوى التنصّت (Sniffing)
السلامة (Integrity) لا أحد يعدّل المحتوى دون اكتشاف التعديل في الطريق (Tampering)
المصادقة (Authentication) أنت تتصل بالخادم الحقيقي انتحال الخادم (Impersonation)

الهدف الثالث هو الأهم والأكثر إساءة في الفهم. السرّية وحدها لا تكفي: بدون مصادقة، قد تُنشئ اتصالاً مشفّراً تماماً — مع المهاجم. تشفير ممتاز مع شخص خاطئ.

المصافحة في TLS — ببساطة

العميل  ──── ClientHello ─────────────────►  الخادم
        (الإصدارات المدعومة، طرق التشفير، رقم عشوائي)

العميل  ◄─── ServerHello ──────────────────  الخادم
        (الإصدار المختار، طريقة التشفير، رقم عشوائي)
العميل  ◄─── الشهادة + سلسلة الثقة ────────  الخادم

   ← هنا يتحقق العميل: هل الشهادة موقّعة من جهة موثوقة؟
   ← وهل الاسم في الشهادة يطابق الموقع المطلوب؟
   ← وهل ما زالت سارية؟

العميل  ──── تبادل المفاتيح ──────────────►  الخادم
   ← يُشتق مفتاح الجلسة من الرقمين العشوائيين

الطرفان ─── Finished (مشفّر) ─────────────  الطرفان
   ← كل ما بعده مشفّر بالمفتاح المتفق عليه

لاحظ: في TLS 1.3 تم تقليص المصافحة إلى ذهاب وإياب واحد (1-RTT) بدلاً من اثنين، وحُذفت طرق التشفير الضعيفة القديمة تماماً. هذا تحسين في السرعة والأمان معاً.

شهادة الجذر (Root CA)
    └── موقّعة ذاتياً، ومضمّنة مسبقاً في نظامك ومتصفحك
        └── شهادة وسيطة (Intermediate CA)
            └── موقّعة من الجذر
                └── شهادة الموقع (Leaf / End-entity)
                    └── موقّعة من الوسيطة

عندما تزور موقعاً، يتحقق متصفحك من:

  1. هل التوقيع سليم؟ (السلسلة تصل إلى جذر موثوق)
  2. هل الاسم في الشهادة يطابق الموقع؟ (SAN — Subject Alternative Name)
  3. هل الشهادة سارية؟ (لم تنتهِ ولم تبدأ بعد)
  4. هل أُبطلت؟ (Revocation)

إذا فشل أي شرط → تحذير المتصفح. لهذا لا يستطيع المهاجم ببساطة انتحال موقع: لا يملك مفتاحه الخاص ولا يستطيع الحصول على شهادة موقّعة باسمه.

ما لا يحميه TLS — نقطة يغفل عنها الجميع

TLS يحمي TLS لا يحمي
محتوى الطلب والرد عنوان IP الوجهة
كلمة المرور داخل الطلب اسم الموقع (عبر SNI)
الكوكيز في الطريق حجم البيانات وتوقيتها
أن الخادم نفسه خبيث
جهازك أنت (لو مصاب)

الخلاصة: TLS يحمي المحتوى لا البيانات الوصفية (Metadata). لهذا يعرف مزوّد الإنترنت أنك تزور موقعاً معيناً حتى لو لم يعرف ماذا فعلت فيه. إنترنت مشفّر ليس إنترنت مجهول.

الجدران النارية (Firewalls)

الجدار الناري = فلتر يقرر: هل تمر هذه الحزمة أم لا؟ قراره مبني على قواعد مكتوبة مسبقاً.

النوعان الأساسيان:

النوع كيف يعمل الميزة العيب
بلا حالة (Stateless) يفحص كل حزمة بمعزل عن غيرها سريع وبسيط لا يعرف إن كانت الحزمة جزءاً من اتصال شرعي
مع حالة (Stateful) يتذكّر الاتصالات القائمة في جدول تتبّع يمنع حزماً مزوّرة تنتمي لاتصال غير موجود أثقل في الذاكرة

مثال يوضّح الفرق: لو سمحت بحركة قادمة على المنفذ 22 (SSH) فقط، فالجدار بلا حالة سيسمح بأي حزمة ذاهبة إلى 22 حتى لو لم يبدأ أحد الاتصال. أما مع حالة فيعرف أنك بدأت الاتصال من الداخل، فيسمح بالردود المطابقة فقط.

مفاهيم iptables: يعمل بثلاث سلاسل رئيسية:

السلسلة متى تُطبَّق
INPUT حزم قادمة إلى جهازك
OUTPUT حزم صادرة من جهازك
FORWARD حزم تعبر جهازك (عندما يكون موجّهاً)

القرارات (Targets): ACCEPT (مرّر) · DROP (أسقط بصمت) · REJECT (أسقط مع إشعار) · LOG (سجّل).

DROP مقابل REJECT: DROP لا يرد شيئاً، فيبدو المنفذ مُرشَّحاً (filtered) وينتظر المهاجم حتى انتهاء المهلة. REJECT يرد برسالة رفض، فيبدو مغلقاً (closed). هذا الفرق بالذات هو ما يقيسه Nmap.

IDS و IPS — الفرق الذي يربك المبتدئين

IDS IPS
الدور يكتشف وينبّه يكتشف ويمنع
الموضع خارج المسار (Passive) داخل المسار (Inline)
التأثير لا يعطّل الشبكة قد يعطّل حركة شرعية
الخطر لا يوقف الهجوم إنذار كاذب = انقطاع خدمة

طريقتان في الكشف:

الطريقة الأساس الميزة العيب
قائمة على التوقيع (Signature-based) أنماط معروفة للهجمات دقيقة وسريعة تفشل مع الهجمات الجديدة
قائمة على الشذوذ (Anomaly-based) الانحراف عن السلوك الطبيعي تكتشف الجديد إنذارات كاذبة كثيرة

الربط مع الأسبوع الثالث: تذكّر مصطلح خط الأساس (Baseline). الكشف القائم على الشذوذ هو تطبيقه على الشبكة حرفياً: تعرف الشكل الطبيعي لحركة شبكتك، فيلفت نظرك أي انحراف.

الشبكات الخاصة الافتراضية (VPN)

المشكلة: أنت على شبكة واي فاي عامة، وكل شيء تمر به يمكن اعتراضه.

الحل: نفق مشفّر بين جهازك وخادم VPN. كل ما يخرج من جهازك يُشفَّر داخل النفق، فلا يفهمه من على الشبكة المحلية.

الأنواع:

النوع الاستخدام ملاحظة
Site-to-Site ربط فرعين لشركة شفّاف للمستخدمين
Remote Access موظف يتصل من المنزل الأكثر شيوعاً
Split Tunnel جزء من الحركة في النفق أسرع، لكن جزءاً يبقى مكشوفاً
Full Tunnel كل الحركة في النفق أكثر أماناً، أبطأ

البروتوكولات: WireGuard (حديث، خفيف، سريع) · OpenVPN (ناضج ومرن) · IPsec/IKEv2 (قوي، مدمج في الأنظمة) · PPTP (مكسور أمنياً — لا تستخدمه أبداً).

⚠️ أهم تصحيح مفهومي: VPN ليس إخفاء هوية (Anonymity).

VPN ينقل ثقتك من مزوّد الإنترنت إلى مزوّد VPN — لا أكثر. مزوّد VPN يرى حركتك كما كان يراها مزوّد الإنترنت. ولو كنت مسجِّلاً دخولك في حساب، فأنت معروف بهويتك مهما تغيّر عنوان IP. وبصمة المتصفح وتوقيت الحركة يبقيان كما هما.

الاستخدام الصحيح لـ VPN: تأمين شبكة غير موثوقة. الاستخدام الخاطئ: توقّع أن تصبح مجهولاً. من يبيعك الثاني يبيعك وهماً.

Nmap — كيف ترى الشبكة بعين المهاجم

Nmap أشهر أداة لمسح الشبكات. وظيفته: إرسال حزم مصمّمة بعناية وقراءة الردود.

مراحل المسح:

المرحلة الأمر السؤال المطروح
اكتشاف المضيفين nmap -sn من موجود على الشبكة؟
مسح المنافذ nmap -sS أي الأبواب مفتوحة؟
كشف الخدمات nmap -sV ما البرنامج وأي إصدار؟
كشف النظام nmap -O ما نظام التشغيل؟
السكربتات nmap --script هل توجد ثغرات معروفة؟

حالات المنفذ — المفهوم الأهم:

الحالة ماذا حدث المعنى
open وصل SYN-ACK خدمة تعمل وتستقبل
closed وصل RST لا خدمة، لكن الجهاز موجود ولم يُفلتر
filtered لا شيء جدار ناري أسقط الحزم
unfiltered وصل RST لمسح ACK يمكن الوصول لكن الحالة مجهولة
open\|filtered لا رد (في UDP) غموض حقيقي — لا يمكن التمييز

open مقابل filtered هو أهم تمييز عملي. كلاهما لا يعطي خدمة، لكن الأول يعني "لا يوجد خادم هنا" والثاني يعني "هناك حاجز يمنعني". المعلومات الاستخباراتية في الثاني أكبر بكثير: معرفة أن جداراً نارياً موجود وفعّال تخبر المهاجم عن مستوى نضج الدفاع.

أنواع المسح — لماذا يوجد أكثر من نوع؟

النوع الاسم الفكرة يحتاج root؟
-sS SYN Scan يبدأ المصافحة ولا يكملها — نصف اتصال نعم
-sT Connect Scan يُكمل المصافحة كاملة لا
-sU UDP Scan لمنافذ UDP نعم
-sA ACK Scan لا يكتشف المنافذ — يرسم قواعد الجدار الناري نعم
-sN/-sF/-sX Null/FIN/Xmas حزم شاذة تتجاوز بعض الفلاتر القديمة نعم

لماذا -sS أ stealth؟ لأنه لا يُكمل المصافحة، فلا يُنشئ اتصالاً كاملاً. هذا مهم عملياً: البرنامج (مثل SSH) لا يرى شيئاً ولا يسجّله، لأن الاتصال لم يصل لطبقة التطبيق أصلاً. أما -sT فيُكمل المصافحة، فيظهر في سجلات التطبيق.

وهنا الدرس المزدوج: نفس الفرق الذي يجعلك invisible كمهاجم هو بالضبط ما يجب أن يدفعك كمحلل دفاعي إلى مراقبة طبقة الشبكة (جدار ناري، tcpdump، تتبّع الاتصالات)، لا الاعتماد على سجلات التطبيقات وحدها. من يراقب التطبيق فقط لا يرى المسح الخفي.

محرّك سكربتات NSE: يحوّل Nmap من ماسح إلى مدقّق أمني مبدئي. اعرف الفئات: safe · default · discovery · version · auth · brute · intrusive · vuln · exploit.

⚠️ قاعدة إلزامية: اقرأ nmap --script-help <اسم> قبل التشغيل. فئة intrusive قد تُسقط الخدمة أو تُقفل الحسابات. المسح غير المُصرّح به جريمة، والمسح غير المُصرّح به العدواني جريمة أثقل.
