Guided Labالمختبر الموجَّه

≈7h · Step by step, with expected results≈7ساعات · خطوة بخطوة مع النتائج المتوقعة

Lab 3.1 — Services and systemd (2h)

  1. List all running services: systemctl list-units --type=service --state=running
  2. Pick SSH (ssh.service). Inspect it: systemctl status ssh. Explain every line of output.
  3. Stop it. Try to SSH in from Kali — confirm it fails. Start it again — confirm it works.
  4. The important distinction: systemctl stop ssh vs systemctl disable ssh. Stop one, disable the other, reboot, and observe the difference. Write down what each actually does.
  5. Write your own systemd unit file for a trivial script. Place it in /etc/systemd/system/, daemon-reload, enable, start it, and verify with systemctl status and journalctl -u.

Deliverable: Your working unit file plus an explanation of the difference between stop/disable and start/enable.

If you see this → it means:

Symptom Cause
systemctl says "Unit not found" Forgot systemctl daemon-reload after creating the unit file
Service starts then immediately dies Check journalctl -u <name> -n 50 — usually a bad path or missing execute permission
Service won't start at boot You enabled it but the unit has no [Install] section with WantedBy=

Lab 3.2 — Reading the logs (2h)

  1. Open /var/log/auth.log (Ubuntu) or /var/log/secure (RHEL-family). Find your own successful SSH login. What fields identify you?
  2. Deliberately fail 5 SSH logins from Kali (wrong password). Find those failures in the log. This is exactly what a brute-force attack looks like.
  3. Use journalctl to view logs since last boot, then only for one service, then within a time window (--since "1 hour ago").

  4. Count failed SSH attempts by IP: 

    grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn

  5. Explain each stage of that pipeline in your notes. This one-liner is the seed of every log-analysis tool you'll ever use.

Deliverable: The output of step 4 (you'll need to generate failures from at least two different source IPs, or simulate it), plus a written explanation of the pipeline.

Lab 3.3 — Bash scripting (3h)

Write four scripts. Each must have a shebang, be executable, and handle bad input.

  1. sysinfo.sh — prints hostname, current user, uptime, disk usage, top 3 memory-consuming processes. Uses variables and command substitution.
  2. backup.sh — takes a directory as $1, tars it to ~/backups/<name>-<date>.tar.gz. Checks that $1 exists and exits with a helpful error if not.
  3. logscan.sh — takes a log file, counts occurrences of a keyword (default: "Failed"), and prints a summary. Uses a for loop over arguments and an if for the default.
  4. portcheck.sh — takes a host and a list of ports, checks each with nc or /dev/tcp, and reports open/closed. Uses a loop and a conditional.

Requirements checklist (all four):

  • #!/bin/bash shebang
  • A usage message when run with no arguments
  • set -euo pipefail (look it up — and understand why it matters)
  • Meaningful exit codes (exit 0 / exit 1)

Then: schedule backup.sh with cron to run daily at 02:00. Verify with grep CRON /var/log/syslog.

Why set -euo pipefail matters: without it, a script that fails halfway keeps running and can do real damage. A backup script that silently fails is worse than one that crashes loudly. This is a professional habit.

المختبر 3.1 — الخدمات و systemd (ساعتان)

  1. اعرض كل الخدمات العاملة: systemctl list-units --type=service --state=running
  2. اختر SSH (ssh.service). افحصها: systemctl status ssh. اشرح كل سطر في المخرجات.
  3. أوقفها. حاول الاتصال عبر SSH من Kali — تأكد أن المحاولة تفشل. شغّلها من جديد — تأكد أنها تعمل.
  4. التمييز المهم: systemctl stop ssh مقابل systemctl disable ssh. أوقف واحدة، وألغِ تفعيل الأخرى، ثم أعد الإقلاع ولاحظ الفرق. اكتب ما يفعله كل أمر فعلياً.
  5. اكتب ملف unit خاصاً بك لسكربت بسيط. ضعه في /etc/systemd/system/، ونفّذ daemon-reload، ثم enable، ثم start، وتحقق بـ systemctl status و journalctl -u.

المخرَج المطلوب: ملف الـ unit العامل عندك، مع شرح الفرق بين stop/disable و start/enable.

إذا رأيت هذا → فهذا معناه:

العَرَض السبب
systemctl يقول "Unit not found" نسيت systemctl daemon-reload بعد إنشاء ملف الـ unit
الخدمة تبدأ ثم تموت فوراً افحص journalctl -u <name> -n 50 — غالباً مسار خاطئ أو صلاحية تنفيذ ناقصة
الخدمة لا تبدأ عند الإقلاع فعّلتها (enable) لكن ملف الـ unit لا يحتوي قسم [Install] مع WantedBy=

المختبر 3.2 — قراءة السجلات (ساعتان)

  1. افتح /var/log/auth.log (على Ubuntu) أو /var/log/secure (على توزيعات RHEL). ابحث عن تسجيل دخولك الناجح عبر SSH. ما الحقول التي تدل عليك؟
  2. افشل عمداً في 5 محاولات دخول SSH من Kali (كلمة مرور خاطئة). ابحث عن هذه الإخفاقات في السجل. هذا بالضبط شكل هجوم التخمين (brute-force).
  3. استخدم journalctl لعرض السجلات منذ آخر إقلاع، ثم لخدمة واحدة فقط، ثم ضمن نافذة زمنية (--since "1 hour ago").

  4. احسب محاولات SSH الفاشلة حسب عنوان IP: 

    grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn

  5. اشرح كل مرحلة من هذه السلسلة في ملاحظاتك. هذا السطر الواحد هو بذرة كل أداة تحليل سجلات ستستخدمها في حياتك.

المخرَج المطلوب: مخرجات الخطوة 4 (ستحتاج توليد إخفاقات من عنوانَي IP مصدر مختلفين على الأقل، أو محاكاتها)، مع شرح مكتوب لسلسلة الأوامر.

المختبر 3.3 — كتابة سكربتات Bash (3 ساعات)

اكتب أربعة سكربتات. كل سكربت يجب أن يحتوي على shebang، وأن يكون قابلاً للتنفيذ، وأن يتعامل مع المدخلات الخاطئة.

  1. sysinfo.sh — يطبع اسم المضيف، والمستخدم الحالي، ومدة التشغيل (uptime)، واستخدام القرص، وأكثر 3 عمليات استهلاكاً للذاكرة. يستخدم متغيرات واستبدال الأوامر (command substitution).
  2. backup.sh — يأخذ مجلداً كـ $1، ويضغطه بـ tar إلى ~/backups/<name>-<date>.tar.gz. يتحقق من وجود $1 ويخرج برسالة خطأ مفيدة إن لم يوجد.
  3. logscan.sh — يأخذ ملف سجل، ويحسب تكرار كلمة مفتاحية (الافتراضي: "Failed")، ويطبع ملخصاً. يستخدم حلقة for على المعاملات و if للقيمة الافتراضية.
  4. portcheck.sh — يأخذ مضيفاً وقائمة منافذ، ويفحص كل منفذ باستخدام nc أو /dev/tcp، ويبلّغ عن المفتوح والمغلق. يستخدم حلقة وشرطاً.

قائمة المتطلبات (الأربعة كلها):

  • shebang بصيغة #!/bin/bash
  • رسالة استخدام (usage) عند التشغيل بدون معاملات
  • set -euo pipefail (ابحث عنها — وافهم لماذا تهم)
  • رموز خروج ذات معنى (exit 0 / exit 1)

ثم: جدول backup.sh باستخدام cron ليعمل يومياً في الساعة 02:00. تحقق بـ grep CRON /var/log/syslog.

لماذا يهم set -euo pipefail: بدونه، السكربت الذي يفشل في المنتصف يستمر في العمل ويمكن أن يسبب ضرراً حقيقياً. سكربت نسخ احتياطي يفشل بصمت أسوأ من سكربت ينهار بصوت عالٍ. هذه عادة احترافية.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

Logs are where security actually lives.

This week answers the question every beginner eventually asks: "how does anyone ever get caught?" The answer is almost always a log nobody was reading — until someone finally read it.

Three things worth internalizing:

  1. Attackers leave traces in predictable places. Failed logins → auth.log. New services → systemd journal. New users → /etc/passwd. Cron jobs → /var/log/syslog. Knowing the normal shape of these files is what makes the abnormal jump out. That skill is called baselining, and it's the foundation of detection.

  2. Persistence is an attacker's goal, and services are how they get it. A malicious systemd unit or cron job survives reboots. When you learn to create services this week, you're simultaneously learning the #1 way intruders stay on a box.

  3. Automation is leverage — in both directions. A script that scans logs for brute-force patterns is a defensive tool. The identical skills build the offensive tooling. There is no separate "blue team scripting."

السجلات هي المكان الذي يعيش فيه الأمن فعلاً.

يجيب هذا الأسبوع عن السؤال الذي يطرحه كل مبتدئ في النهاية: "كيف يُقبض على أحدهم أصلاً؟" الجواب دائماً سجل لم يكن أحد يقرأه — إلى أن قرأه أحدهم أخيراً.

ثلاثة أمور تستحق أن تستوعبها:

  1. المهاجمون يتركون آثاراً في أماكن متوقعة. تسجيلات الدخول الفاشلة → auth.log. الخدمات الجديدة → سجل systemd. المستخدمون الجدد → /etc/passwd. مهام cron → /var/log/syslog. معرفة الشكل الطبيعي لهذه الملفات هي ما يجعل الشاذ يقفز إلى العين. هذه المهارة تُسمى خط الأساس (baselining)، وهي أساس الكشف.

  2. الاستمرارية هدف المهاجم، والخدمات هي وسيلته إليها. ملف unit خبيث في systemd أو مهمة cron خبيثة يبقى بعد إعادة الإقلاع. عندما تتعلم هذا الأسبوع إنشاء الخدمات، فأنت تتعلم في الوقت نفسه الطريقة الأولى التي يبقى بها المتسللون داخل الجهاز.

  3. الأتمتة قوة مضاعفة — في الاتجاهين. السكربت الذي يفحص السجلات بحثاً عن أنماط التخمين أداة دفاعية. المهارات نفسها هي التي تبني الأدوات الهجومية. لا وجود لشيء منفصل اسمه "كتابة سكربتات الفريق الأزرق".

الخدمات (Services / Daemons)

الخدمة هي برنامج يعمل في الخلفية باستمرار، دون أن تتفاعل معه مباشرة. تُسمى أيضاً Daemon (وتُختصر أحياناً بحرف d في نهاية الاسم مثل sshd).

أمثلة: خدمة SSH (تسمح بالاتصال عن بعد) · خدمة الويب (Apache/Nginx) · خدمة قواعد البيانات · خدمة الطباعة.

لماذا تهمنا أمنياً؟

  • كل خدمة تعمل = منفذ مفتوح = سطح هجوم محتمل (attack surface).
  • المهاجم يسأل دائماً: ما الخدمات التي تعمل على هذا الجهاز؟ لأن كل خدمة قد تحتوي ثغرة.
  • قاعدة ذهبية: أوقف كل خدمة لا تحتاجها. كل خدمة إضافية هي باب إضافي قد يُنسى مفتوحاً.

systemctl — أداة إدارة الخدمات

الأمر الوظيفة
systemctl status ssh عرض حالة الخدمة
systemctl start ssh تشغيل الخدمة الآن
systemctl stop ssh إيقاف الخدمة الآن
systemctl enable ssh تفعيل التشغيل التلقائي عند الإقلاع
systemctl disable ssh إلغاء التشغيل التلقائي
systemctl restart ssh إعادة تشغيل
systemctl list-units --type=service عرض كل الخدمات

أهم تمييز في هذا الأسبوع:

  • start / stop → يتحكم في الوقت الحالي فقط (حتى إعادة التشغيل).
  • enable / disable → يتحكم في ما يحدث عند الإقلاع.

الخدمة قد تكون enabled لكنها stopped في هذه اللحظة. هذان بُعدان مستقلان تماماً — وهذا يربك المبتدئين كثيراً. من الناحية الأمنية: إذا وجدت خدمة enabled لا يعرفها أحد، فهذا مؤشر اختراق محتمل (persistence).

السجلات (Logs) — عيون النظام

السجل هو ملف يسجّل كل ما يحدث في النظام. بدون سجلات، لا يوجد أمان — لا يمكنك اكتشاف هجوم لا تعرف بوجوده.

أهم ملفات السجلات في /var/log:

الملف ماذا يسجّل الأهمية الأمنية
auth.log تسجيلات الدخول، sudo، المصادقة الأهم — تسجيل الدخول الناجح والفاشل
syslog رسائل النظام العامة تشغيل/إيقاف الخدمات، مهام cron
kern.log رسائل النواة أخطاء العتاد، أحداث الشبكة
dpkg.log تثبيت وإزالة الحزم كشف تثبيت أدوات مشبوهة
wtmp / btmp سجل الدخول الناجح / الفاشل يُقرأ بأمر last و lastb

قراءة السجلات زمنياً: 

journalctl --since "1 hour ago"     # آخر ساعة
journalctl -u ssh                   # خدمة محددة
journalctl -p err                   # الأخطاء فقط
journalctl -b                       # منذ آخر إقلاع

تحليل السجلات — المهارة العملية الأهم

grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn

تحليل الأمر خطوة بخطوة:

المرحلة الأمر الوظيفة
1 grep "Failed password" استخرج فقط أسطر فشل تسجيل الدخول
2 awk '{print $(NF-3)}' اطبع الحقل الرابع من النهاية (عنوان IP المهاجم)
3 sort رتّب العناوين أبجدياً لتجميع المتشابه
4 uniq -c احسب عدد مرات تكرار كل عنوان
5 sort -rn رتّب تنازلياً حسب العدد

النتيجة: قائمة بأكثر عناوين IP فشلاً في تسجيل الدخول. هذا بالضبط ما يفعله محلل مركز العمليات الأمنية (SOC Analyst) يومياً.

جميع أدوات كشف التسلل (IDS) و إدارة معلومات الأمن (SIEM) الكبيرة — Splunk، ELK، Wazuh — هي في جوهرها تنفيذ مؤتمت وموسّع لهذا الأمر بالذات. أتقن الأساس، وستفهم كل شيء بعده.

أساسيات Bash Scripting

السكربت (Script) = ملف يحتوي أوامر تُنفَّذ بالتتابع. يحوّل الأوامر اليدوية المتكررة إلى أمر واحد.

البنية الأساسية:

#!/bin/bash                    # السطر الأول: أي مفسّر يستخدم
set -euo pipefail              # أوقف عند أي خطأ — إلزامي في السكربتات الجدية

name="Ahmed"                   # متغير (لا مسافات حول =)
echo "Hello $name"             # استخدام المتغير بـ $

if [ -f "$1" ]; then           # شرط: هل الملف موجود؟
    echo "Found"
else
    echo "Not found" >&2       # >&2 = رسالة خطأ
    exit 1                     # رمز خروج يدل على الفشل
fi

for ip in 192.168.1.1 192.168.1.2; do   # حلقة تكرار
    ping -c1 "$ip"
done

set -euo pipefail — لماذا هي مهمة؟

الخيار المعنى
-e أوقف السكربت فوراً عند أي أمر يفشل
-u اعتبر استخدام متغير غير معرّف خطأً
-o pipefail إذا فشل أي أمر في سلسلة أنابيب، اعتبر السلسلة كلها فاشلة

بدونها: سكربت النسخ الاحتياطي يفشل في المنتصف ويكمل بصمت — فتظن أن لديك نسخة احتياطية ولا تملك. الفشل الصاخب أفضل ألف مرة من النجاح الكاذب.
