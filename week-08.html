Guided Labالمختبر الموجَّه

≈7h · Step by step, with expected results≈7ساعات · خطوة بخطوة مع النتائج المتوقعة

All VMs stay on the NAT Network. The deliberately vulnerable applications you install this week are hostile by design and must never be exposed beyond that network.

Lab 8.1 — Stand up a deliberately vulnerable app (1.5h)

Goal: A target you are unambiguously authorized to attack, running in your own lab.

Setup: Ubuntu VM. You will run DVWA and, if RAM allows, the OWASP Juice Shop.

Steps:

  1. Install the pieces DVWA needs: 

    sudo apt update
sudo apt install -y apache2 mariadb-server php php-mysqli php-gd git
sudo systemctl enable --now apache2 mariadb

  2. Get DVWA from its official repository: github.com/digininja/DVWA. 

    cd /var/www/html
sudo git clone https://github.com/digininja/DVWA.git dvwa
sudo chown -R www-data:www-data /var/www/html/dvwa

  3. Configure it: copy config/config.inc.php.dist to config/config.inc.php, set the database credentials, then create the database and the user in MariaDB.

  4. Fix the two settings the official setup page will complain about — allow_url_include and allow_url_fopen in php.ini — restart Apache, then browse to http://localhost/dvwa/setup.php and click Create / Reset Database.
  5. Log in (default admin / password — change it), then set DVWA Security to Low. You will raise it deliberately in the challenge block.
  6. Isolate it. Confirm DVWA is reachable only from the NAT Network. Verify from your host machine that it is not reachable.
  7. Optional, if you have 8GB+ free: OWASP Juice Shop, which is a modern single-page app and a better model of a real target — owasp.org/www-project-juice-shop · github.com/juice-shop/juice-shop.

Expected output: DVWA's setup page showing all green, a working login, and a security level of Low.

If you see this → it means:

Symptom Cause
Setup page shows red on allow_url_include Edit the right php.ini (php -i \| grep "Loaded Configuration File" tells you which) and restart Apache
"Could not connect to the database" MariaDB not running, or config.inc.php has the wrong credentials
403 Forbidden on /dvwa File ownership — chown -R www-data:www-data on the DVWA directory
Juice Shop needs more RAM than you have Skip it this week; DVWA alone is enough for the labs

Lab 8.2 — SQL by hand, on your own data (1.5h)

Goal: Understand injection by first understanding the language being injected into.

Setup: Ubuntu VM, MariaDB running.

Steps:

  1. Open the client: sudo mysql. Create a practice database and one table: 

    CREATE DATABASE shop;
USE shop;
CREATE TABLE users (id INT PRIMARY KEY AUTO_INCREMENT,
                    username VARCHAR(50), role VARCHAR(20), city VARCHAR(50));
INSERT INTO users (username, role, city) VALUES
  ('ali','admin','Cairo'), ('sara','user','Alexandria'), ('omar','user','Cairo');

  2. SELECT — retrieve everything, then only Cairo users, then only the admin, then only two columns, ordered: 

    SELECT * FROM users;
SELECT * FROM users WHERE city = 'Cairo';
SELECT username, role FROM users WHERE role = 'admin';
SELECT * FROM users ORDER BY username;

  3. UPDATE, then read back the change. Then DELETE a row and read back. Do this deliberately — you are learning to modify data, which is what an attacker does after a successful injection.

  4. JOIN at the basic level — add an orders table with a user_id column, then join it: 

    CREATE TABLE orders (id INT PRIMARY KEY AUTO_INCREMENT, user_id INT, total INT);
INSERT INTO orders (user_id, total) VALUES (1, 250), (1, 90), (2, 400);
SELECT users.username, orders.total
FROM users JOIN orders ON users.id = orders.user_id;
    Explain in your notes what the ON clause is doing.

  5. The key observation: write down, in your own words, what separates the code (SELECT ... WHERE) from the data ('Cairo'). Notice the quotes. Everything about injection lives in that distinction. Do not move on until you can state it clearly.

Expected output: A working shop database, plus a written paragraph distinguishing SQL structure from SQL data.

Lab 8.3 — PortSwigger Academy: SQL injection (2h)

Goal: Your first real exploitation, on a target that is built to be exploited.

Setup: Browser only. Go to the SQL injection topic. You do not need Burp for the first two labs, but the Academy integrates with it when you do.

Steps:

  1. Read the topic page fully — What is SQL injection? — and the cheat sheet. Note the two sub-types on the page: retrieving hidden data, and subverting application logic.
  2. Complete SQL injection vulnerability in WHERE clause allowing retrieval of hidden data. Before you touch it, write down what query the application probably runs for a category filter, and what you would need to inject to make it return everything.
  3. Complete SQL injection vulnerability allowing login bypass. Same discipline: predict the query first, then confirm your prediction.
  4. For each lab, write in your notes: the exact input you used, the query you think the server built, and what the application should have done differently.
  5. Read Union attacks — do not attempt the union labs yet. Just understand why UNION escalates "read my data" into "read your data."
  6. Read Blind SQL injection — again, concept only. Note why an application that shows no errors is still injectable.

Expected output: Two solved labs (the Academy marks them green), plus written predictions for each.

If you see this → it means:

Symptom Cause
The lab says "Not solved" after a promising response You got data back but not the specific thing the lab asks for — reread the lab's exact objective
Input returns a 500 Usually a syntax error in your injection — the query broke. That error is information; a well-built app would not have shown it to you
Nothing at all changes Try -- vs -- (comment syntax needs a trailing space in MySQL) and check -- vs #
Lab resets every few minutes Normal — Academy instances are short-lived. That is deliberate

Lab 8.4 — Access control, and finding the attack in the log (2h)

Goal: The second root-cause pattern, then close the loop back to Week 3's logs.

Setup: Browser for the Academy, Ubuntu VM for the log, DVWA for the local attack.

Steps:

  1. Read the Access control topic and the IDOR section. Write down, in one sentence, the difference between "the request never reached the code that checks permissions" and "the check exists but trusts something the client controls."
  2. Complete Unprotected admin functionality — the vulnerability is literally a missing check plus a guessable path.
  3. Complete Insecure direct object references — the application checks that you are logged in, but not that the object is yours. This is IDOR, and it is one of the most common real-world web bugs in existence.
  4. Complete User role controlled by request parameter — authorization decided by a value the client sends. Say out loud why that can never be secure.

  5. Close the loop. In DVWA (Security = Low), use the SQL Injection page with a detection-friendly payload — something that will appear verbatim in the log. Then: 

    sudo tail -50 /var/log/apache2/access.log
grep -n "UNION\|SELECT\|OR%201" /var/log/apache2/access.log

  6. Identify the request line in the log. Note that the whole attack is right there in plain text — URL, method, user-agent, payload. Now answer: what would you grep for in a real log to find this? What would it look like if the attacker encoded it?

  7. Raise DVWA Security to Medium and repeat step 5 on the same page. Note what changed in how your input had to be written. Do not chase it further — the point is that defenses change the shape of the attack.

⚠️ DVWA is deliberately vulnerable software, installed on your own VM, for the purpose of being attacked. That is its entire design. The identical action against any system you do not own is unauthorized access and a crime.

Expected output: Three solved Academy access-control labs, plus a grep result showing your own SQLi payload sitting in /var/log/apache2/access.log.

المختبر 8.2 — SQL بيدك، على بياناتك أنت (1.5 ساعة)

الهدف: افهم الحقن بفهم اللغة التي نُحقن فيها أولاً.

التهيئة: جهاز Ubuntu وهمي، و MariaDB يعمل.

الخطوات:

  1. افتح العميل: sudo mysql. أنشئ قاعدة بيانات تدريب وجدولاً واحداً: 

    CREATE DATABASE shop;
USE shop;
CREATE TABLE users (id INT PRIMARY KEY AUTO_INCREMENT,
                    username VARCHAR(50), role VARCHAR(20), city VARCHAR(50));
INSERT INTO users (username, role, city) VALUES
  ('ali','admin','Cairo'), ('sara','user','Alexandria'), ('omar','user','Cairo');

  2. SELECT — استرجع كل شيء، ثم مستخدمي Cairo فقط، ثم المدير فقط، ثم عمودين فقط، مرتَّبين: 

    SELECT * FROM users;
SELECT * FROM users WHERE city = 'Cairo';
SELECT username, role FROM users WHERE role = 'admin';
SELECT * FROM users ORDER BY username;

  3. UPDATE، ثم اقرأ التغيير. ثم DELETE صفاً واقرأ النتيجة. افعل هذا عمداً — أنت تتعلم تعديل البيانات، وهذا ما يفعله المهاجم بعد حقن ناجح.

  4. JOIN على المستوى الأساسي — أضف جدول orders فيه عمود user_id، ثم اربطه: 

    CREATE TABLE orders (id INT PRIMARY KEY AUTO_INCREMENT, user_id INT, total INT);
INSERT INTO orders (user_id, total) VALUES (1, 250), (1, 90), (2, 400);
SELECT users.username, orders.total
FROM users JOIN orders ON users.id = orders.user_id;
    اشرح في ملاحظاتك ما الذي يفعله شرط ON.

  5. الملاحظة المفتاحية: اكتب بكلماتك أنت ما الذي يفصل الشيفرة (SELECT ... WHERE) عن البيانات ('Cairo'). لاحظ علامات الاقتباس. كل شيء عن الحقن يعيش في هذا التمييز. لا تنتقل إلى ما بعده قبل أن تستطيع قوله بوضوح.

المخرج المطلوب: قاعدة بيانات shop تعمل، بالإضافة إلى فقرة مكتوبة تفرّق بين بنية SQL وبيانات SQL.

المختبر 8.3 — PortSwigger Academy: حقن SQL (2 ساعة)

الهدف: أول استغلال حقيقي لك، على هدف مبني ليُستغَل.

التهيئة: المتصفح فقط. اذهب إلى موضوع حقن SQL. لا تحتاج Burp في المختبرين الأولين، لكن الأكاديمية تتكامل معه عندما تحتاجه.

الخطوات:

  1. اقرأ صفحة الموضوع كاملة — What is SQL injection? — وورقة الغش (cheat sheet). لاحظ النوعين الفرعيين في الصفحة: استرجاع بيانات مخفية، وإفساد منطق التطبيق.
  2. أكمل SQL injection vulnerability in WHERE clause allowing retrieval of hidden data. قبل أن تلمسه، اكتب الاستعلام الذي يُرجَّح أن التطبيق يشغّله لفلتر التصنيف، وما ستحتاج حقنه ليعيد كل شيء.
  3. أكمل SQL injection vulnerability allowing login bypass. الانضباط نفسه: تنبّأ بالاستعلام أولاً، ثم أكّد تنبؤك.
  4. لكل مختبر، اكتب في ملاحظاتك: المدخل الدقيق الذي استخدمته، والاستعلام الذي تظن أن السيرفر بناه، وما كان ينبغي للتطبيق أن يفعله بشكل مختلف.
  5. اقرأ Union attacks — لا تحاول مختبرات UNION بعد. فقط افهم لماذا يرقّي UNION الأمر من "اقرأ بياناتي" إلى "اقرأ بياناتك".
  6. اقرأ Blind SQL injection — مرة أخرى، المفهوم فقط. لاحظ لماذا يظل تطبيق لا يُظهر أي أخطاء قابلاً للحقن.

المخرج المطلوب: مختبران محلولان (تعلّمهما الأكاديمية بالأخضر)، بالإضافة إلى تنبؤات مكتوبة لكل منهما.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

The OWASP Top 10 is a map, not a checklist. Read the category names carefully and you will notice something: almost none of them name a bug. "Broken Access Control," "Identification and Authentication Failures," "Security Misconfiguration" — these are descriptions of classes of design failure. That is the single most important thing to take from this week. Web vulnerabilities are rarely clever. They are the same two mistakes, made over and over, in a thousand different technologies.

Root-cause pattern #1: trusting user input.

An application builds a string out of your input and hands it to an interpreter — the SQL engine, the shell, the filesystem, an XML parser. The interpreter cannot tell which parts of that string were the developer's code and which parts were yours. So if your input contains the interpreter's own syntax, you have just written code inside their program.

That is all SQL injection is:

// The vulnerable pattern — the user's text becomes part of the QUERY
$q = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'";

If the user sends admin'--, the database receives:

SELECT * FROM users WHERE username = 'admin'-- ' AND password = 'anything'

The -- comments out the password check. There was never a password check to defeat; there was only a string that no longer meant what the developer assumed it meant. The fix is not to filter bad characters — filtering is a losing arms race. The fix is to stop building strings:

// The safe pattern — the query STRUCTURE is fixed before the data arrives
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);

With a parameterized query, the database is told "here is the query, and separately, here is a value." The value can never become grammar. Design, not filtering. Every injection class in the Top 10 — SQL, command, LDAP, XPath — is the same mistake with a different interpreter.

Root-cause pattern #2: failing to check authorization on the server.

Broken Access Control sits at A01 — the top of the 2021 list — because it is the most common serious web vulnerability and the one that most often exposes real user data. The pattern is always the same: the application checks something other than "is this user allowed to do this?"

  • It checks you are logged in, but not that the record is yours → IDOR. Change ?invoice_id=1042 to 1043 and you are reading a stranger's invoice.
  • It hides the admin button but leaves the admin endpoint reachable → security through obscurity. The page is hidden; the API is not.
  • It decides your role from a value you send → the client is now the authorization server. role=admin and you are done.

Notice what all three have in common: the browser was doing the enforcement, and the browser belongs to the attacker. Which brings back the sentence from last week, now with a body count: the same-origin policy, hidden buttons, disabled form fields, and client-side validation are usability features. They are not security controls. The only authorization check that exists is the one the server performs, on every request, against the identity it established — not against anything the client told it.

And the third thread, tying both weeks together: the highest-value target in any web application is not the database. It is the session. Injection reads data; a stolen session is the user, with all their permissions, and it looks completely legitimate in the logs. This is why the flags from Week 7 exist, and why "the app is secure because it uses HTTPS" is not an answer to anything.

⚠️ Legal boundary — repeated deliberately, because this is the week learners feel tempted. DVWA, OWASP Juice Shop, and the PortSwigger Academy labs are deliberately vulnerable systems, built for exactly this purpose. PortSwigger runs its labs on its own servers and invites you to attack them. That invitation is the authorization. OverTheWire's Natas servers exist to be broken. That is the authorization. Everything else requires written permission. Testing a live website — even one request, even adding a single quote to a URL parameter to "see what happens" — without a signed scope, a bug bounty program's published policy, or a CTF's rules, is unauthorized access and is a criminal offence in essentially every jurisdiction. There is no small version of this. The difference between a penetration tester and a criminal is not skill and it is not intent — it is a document. In Week 12 you will learn to read that document. Until then: your VMs, your lab, and the sanctioned platforms. Nothing else.

"Broken Access Control" و"Identification and Authentication Failures" و"Security Misconfiguration" — هذه أوصاف لفئات فشل تصميمي. وهذا هو أهم شيء واحد تأخذه من هذا الأسبوع. ثغرات الويب نادراً ما تكون بارعة. إنها الخطأان نفسهما، يُرتكبان مراراً وتكراراً، في ألف تقنية مختلفة.

نمط السبب الجذري #1: الثقة بمدخلات المستخدم.

يبني التطبيق نصاً من مدخلك ويسلّمه إلى مفسّر (interpreter) — محرّك SQL، أو الـ shell، أو نظام الملفات، أو محلّل XML. لا يستطيع المفسّر التمييز بين الأجزاء التي كانت شيفرة المطوّر والأجزاء التي كانت مدخلك. فإن احتوى مدخلك على صياغة المفسّر نفسه، فقد كتبت للتو شيفرة داخل برنامجه.

هذا كل ما في حقن SQL:

// The vulnerable pattern — the user's text becomes part of the QUERY
$q = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'";

إن أرسل المستخدم admin'--، تستقبل قاعدة البيانات:

SELECT * FROM users WHERE username = 'admin'-- ' AND password = 'anything'

الـ -- تعلّق فحص كلمة المرور. لم يكن هناك قط فحص كلمة مرور لنهزمه؛ كان هناك فقط نص لم يعد يعني ما افترض المطوّر أنه يعنيه. والحل ليس تصفية الأحرف السيئة — فالتصفية سباق تسلح خاسر. الحل هو التوقف عن بناء النصوص:

// The safe pattern — the query STRUCTURE is fixed before the data arrives
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);

مع استعلام ذي معاملات (parameterized query)، تُخبَر قاعدة البيانات: "هذا هو الاستعلام، وبشكل منفصل، هذه قيمة." ولا يمكن للقيمة أن تصبح قواعد أبداً. تصميم، لا تصفية. كل فئات الحقن في Top 10 — SQL، والأوامر، و LDAP، و XPath — هي الخطأ نفسه بمفسّر مختلف.

نمط السبب الجذري #2: الفشل في فحص التخويل على السيرفر.

يجلس ضعف التحكم بالوصول في A01 — قمة قائمة 2021 — لأنه أشهر ثغرة ويب خطيرة، وأكثرها كشفاً لبيانات مستخدمين حقيقية. والنمط واحد دائماً: التطبيق يفحص شيئاً غير "هل يُسمح لهذا المستخدم بفعل هذا؟"

  • يفحص أنك مسجّل الدخول، لا أن السجل يخصّك → IDOR. غيّر ?invoice_id=1042 إلى 1043 وستقرأ فاتورة شخص غريب.
  • يخفي زر المدير لكنه يترك نقطة نهاية المدير قابلة للوصول → الأمن بالإخفاء (security through obscurity). الصفحة مخفية؛ والـ API ليس كذلك.
  • يقرّر دورك من قيمة ترسلها أنت → العميل الآن هو سيرفر التخويل. role=admin وانتهيت.

لاحظ القاسم المشترك بين الثلاثة: المتصفح كان ينفّذ الإنفاذ، والمتصفح ملك المهاجم. وهذا يعيد جملة الأسبوع الماضي، الآن مع حصيلة ضحايا: سياسة الأصل الواحد، والأزرار المخفية، وحقول النماذج المعطّلة، والتحقق في جهة العميل — كلها ميزات استخدام. وليست ضوابط أمنية. التحقق الوحيد من التخويل الموجود هو الذي ينفّذه السيرفر، على كل طلب، مقابل الهوية التي أنشأها هو — لا مقابل أي شيء أخبره به العميل.

والخيط الثالث، الرابط بين الأسبوعين: أعلى هدف قيمةً في أي تطبيق ويب ليس قاعدة البيانات. إنه الجلسة. فالحقن يقرأ بيانات؛ أما الجلسة المسروقة فهي المستخدم، بكل صلاحياته، وتبدو مشروعة تماماً في السجلات. ولهذا توجد الأعلام (flags) في الأسبوع 7، ولهذا فإن "التطبيق آمن لأنه يستخدم HTTPS" ليس جواباً على أي شيء.

⚠️ الحد القانوني — مُكرَّر عمداً، لأن هذا هو الأسبوع الذي يشعر فيه المتعلمون بالإغراء. DVWA و OWASP Juice Shop ومختبرات PortSwigger Academy هي أنظمة مثبَّت بها ثغرات عمداً، مبنية لهذا الغرض بالضبط. و PortSwigger يشغّل مختبراته على خوادمه الخاصة ويدعوك لمهاجمتها. تلك الدعوة هي التخويل. وخوادم Natas الخاصة بـ OverTheWire موجودة لتُكسَر. وهذا هو التخويل. كل ما عدا ذلك يتطلب إذناً مكتوباً. اختبار موقع حيّ — حتى طلب واحد، حتى إضافة علامة اقتباس واحدة إلى معامل URL لـ "ترى ما يحدث" — بدون نطاق موقَّع (scope)، أو سياسة منشورة لبرنامج bug bounty، أو قواعد CTF، هو وصول غير مصرَّح به وجريمة جنائية في كل نطاق قضائي تقريباً. ولا توجد نسخة صغيرة من هذا. الفرق بين مختبر اختراق ومجرم ليس المهارة وليس النية — إنه مستند. في الأسبوع 12 ستتعلم قراءة ذلك المستند. وحتى ذلك الحين: أجهزتك الوهمية، ومختبرك، والمنصات المصرَّح بها. لا شيء غيرها.

ملاحظات مفاهيمية موسّعة

شرح إضافي موسّع

معمارية تطبيق الويب — من ثلاثة طبقات

أي تطبيق ويب حقيقي يتكون من ثلاث طبقات، وبين كل طبقتين حدود ثقة (Trust Boundary) — وهي أهم مفهوم في هذا الأسبوع:

[ المتصفح ]  ──►  [ السيرفر ]  ──►  [ قاعدة البيانات ]
 العميل            منطق التطبيق        تخزين البيانات
الطبقة من يتحكم بها هل نثق بها؟
المتصفح (Client) المهاجم ❌ لا. إطلاقاً. ملك المستخدم، ويمكن تعديله بالكامل
السيرفر (Server) المطوّر ✅ نعم — هنا يجب أن يكون كل التحقق
قاعدة البيانات المطوّر ✅ نعم — لكنها تنفّذ ما يُقال لها حرفياً

القاعدة الذهبية: كل ما يأتي من المتصفح هو مدخلات غير موثوقة — حتى لو جاء من نموذج كتبته أنت، وحتى لو كان في حقل مخفي (hidden)، وحتى لو منعته جافاسكربت. المهاجم لا يستخدم متصفحك؛ يستخدم curl أو Burp ويرسل ما يريد.

قواعد البيانات و SQL — اللغة التي نُخترق من خلالها

قاعدة البيانات منظّمة في جداول (Tables): صفوف (Records) وأعمدة (Columns). وSQL هي لغة التحدث معها.

الأوامر الأربعة الأساسية:

الأمر الوظيفة مثال
SELECT اقرأ بيانات SELECT * FROM users;
INSERT أضف صفاً INSERT INTO users (username) VALUES ('ali');
UPDATE عدّل صفاً UPDATE users SET role='admin' WHERE id=3;
DELETE احذف صفاً DELETE FROM users WHERE id=3;

WHERE تحدّد أي الصفوف. بدونها، الأمر يطبّق على الجدول كله — وهذه معلومة أمنية خطيرة: UPDATE users SET role='admin' بدون WHERE تمنح كل المستخدمين صلاحيات المدير.

JOIN يربط جدولين ببعضهما عبر عمود مشترك:

SELECT users.username, orders.total
FROM users JOIN orders ON users.id = orders.user_id;

ON تقول: اربط الصف الذي users.id فيه يساوي orders.user_id. تخيّل أن لك صفاً في جدول المستخدمين وصفاً في جدول الطلبات — هذا الأمر يعيدهما معاً كسطر واحد.

الوعد (IN) و الخروج منه: SQL له UNION (يجمع نتائج استعلامين)، و; (ينهي الأمر ويبدأ آخر)، و-- (تعليق يلغي بقية السطر). هذه كلها أدوات مشروعة تماماً — لكنها في يد مهاجم تصبح أسلحة. الخطأ ليس في اللغة، بل في التطبيق الذي سمح لك بكلماتها داخل جملته.

كيف يتحدث التطبيق مع قاعدة البيانات — وهنا يولد الثقب

الكود الساذج يبني نص الاستعلام بدمج مدخلاتك مباشرة:

// ❌ خطير — مدخلات المستخدم تُدمج في نص الاستعلام
$username = $_POST['username'];
$query = "SELECT * FROM users WHERE username = '" . $username . "'";

ما الذي يحدث ذهنياً في هذه اللحظة؟ المطوّر يرى: "جملة استعلام + قيمة". لكن قاعدة البيانات لا ترى هذا التمييز. هي ترى نصاً واحداً وتنفّذه حرفياً. الفرق بين "الشيفرة" و"البيانات" كان موجوداً في ذهن المطوّر فقط — ولم يُخبر قاعدة البيانات به أبداً.

الحل — الاستعلامات المُعدّة مسبقاً (Prepared Statements):

// ✅ آمن — هيكل الاستعلام ثابت، والقيمة تُرسل منفصلة
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);

هنا يقول المطوّر لقاعدة البيانات صراحةً: "هذا هو الاستعلام. وهذه قيمة." القيمة تُرسل في قناة منفصلة، فلا يمكن أن تصبح جزءاً من القواعد مهما احتوت من علامات اقتباس أو شرطات.

لماذا التصفية (Filtering) ليست حلاً؟ لا يمكنك حصر كل الحالات: الترميز (encoding)، اختلاف حالة الأحرف، تعليقات SQL، الصيغ البديلة. التصفية سباق تسلح تخسره دائماً. التصميم الصحيح لا سباق فيه. لا تُنقِّح المدخلات — افصل الشيفرة عن البيانات.

جوهر ثغرة SQL Injection — الشرح الكامل

الفكرة في جملة: إذا استطعت إدخال قواعد SQL داخل قيمة، فقد تحوّلت من مستخدم إلى مبرمج — تستطيع تعديل الاستعلام نفسه.

مثال تسجيل الدخول. التطبيق يبني هذا الاستعلام:

SELECT * FROM users WHERE username = 'ali' AND password = 'secret';

قاعدة البيانات تنفّذه هكذا: "هات لي صفاً اسم المستخدم فيه ali و كلمة المرور secret". سليم.

الآن ماذا لو كان اسم المستخدم المدخل هو admin'--؟ يصبح نص الاستعلام:

SELECT * FROM users WHERE username = 'admin'-- ' AND password = 'anything';

انظر ماذا حدث: -- في SQL تعني تعليق — ألغِ كل ما بعدها. الجزء ' AND password = 'anything' كله أصبح تعليقاً لا وجود له. الاستعلام الفعلي صار:

SELECT * FROM users WHERE username = 'admin';

كلمة المرور لم تُفحص إطلاقاً. لم نتجاوزها — بل حذفناها من الجملة. ولهذا يعمل هذا الهجوم بغض النظر عن كلمة المرور.

صيغة ثانية — ' OR 1=1-- كاسم مستخدم:

SELECT * FROM users WHERE username = '' OR 1=1-- ' AND password = 'x';

1=1 صحيحة دائماً، فيعيد الاستعلام كل المستخدمين. التطبيق يأخذ أول صف (عادةً المدير) ويظنك أنت.

لماذا كان هذا ممكناً؟

ما ظنّ المطوّر أنه حدث ما حدث فعلاً
قيمة نصية في حقل قواعد SQL جديدة داخل الجملة
المدخل "بيانات" المدخل صار "شيفرة"
الاستعلام ثابت الاستعلام أعاد المهاجم كتابته

هذا هو النمط الجذري الأول في هذا الأسبوع: الثقة بالمدخلات. كل أنواع الحقن — SQL، أوامر النظام، LDAP، XPath — هي نفس الخطأ مع مفسّر مختلف. تعلّم النمط مرة واحدة، وستفهم العائلة كلها.

UNION — من "اقرأ بياناتي" إلى "اقرأ بياناتك":

' UNION SELECT username, password FROM users--

هذه لا تتلاعب بمنطق الاستعلام فحسب — بل تضيف استعلاماً ثانياً نتائجه تُدمج مع الأول. هكذا تُسرَّب جداول كاملة (بيانات اعتماد، بطاقات، كل شيء) عبر حقل بحث واحد بريء.

APIs و REST — واجهة التطبيق الحديثة

الـ API هي الواجهة التي يتحدث بها برنامج مع برنامج آخر، بدلاً من إنسان مع موقع.

REST أسلوب في تصميمها، ملخّصه:

المفهوم المعنى مثال
Endpoint عنوان المورد /api/users/42
Verb الفعل على المورد GET اقرأ · POST أنشئ · PUT استبدل · DELETE احذف
JSON صيغة تبادل البيانات {"id":42,"user":"ali"}
Status Code نتيجة العملية 200, 201, 401, 403, 404, 500
Auth Header كيف تُثبت هويتك Authorization: Bearer eyJhbGci...

لماذا الـ APIs سطح هجوم ضخم؟

  1. لا واجهة رسومية تخفي شيئاً. في الموقع قد يكون الزر مخفياً — في الـ API يُنفَّذ الأمر مباشرة.
  2. يوثّق المطوّرون افتراضهم الخاطئ: "من يستدعي الـ API هو تطبيقنا". المهاجم يستدعيها مباشرة بـ curl.
  3. التحقق من التخويل غائب أكثر مما تتوقع — لأن المطوّر اختبر الـ API عبر التطبيق الرسمي، ولم يجرّب أبداً استدعاء /api/users/43 بمعرّف جلسة شخص آخر.
  4. معرّفات متسلسلة (/api/orders/1001, 1002, 1003) = IDOR جاهز.

مشروع OWASP Top 10 هو أشهر مرجع لتصنيف مخاطر تطبيقات الويب. النسخة الحالية (2021):

# الفئة المعنى بالعربية
A01 Broken Access Control ضعف التحكم بالوصول — الأول في القائمة
A02 Cryptographic Failures إخفاقات التشفير
A03 Injection الحقن — ويشمل SQL Injection
A04 Insecure Design تصميم غير آمن

A06 Vulnerable and Outdated Components مكونات قديمة أو مثبّت بها ثغرات

الملاحظة الأهم: لاحظ أن معظم الفئات لا تُسمّي ثغرة، بل نمط فشل. "ضعف التحكم بالوصول" ليست ثغرة واحدة، بل عائلة كاملة. من يحفظ أسماء الفئات يفشل في الاختبارات العملية؛ من يفهم الأنماط يجدها في أي تطبيق.

النمط الجذري الثاني: غياب التحقق من التخويل — IDOR

هذا هو الفرق الذي يجب أن يثبت:

السؤال النظام متى
من أنت؟ المصادقة (Authentication) مرة عند الدخول
هل يُسمح لك بهذا؟ التخويل (Authorization) مع كل طلب

IDOR (الإشارة المباشرة غير الآمنة للكائن) تعني: التطبيق تحقّق أنك مسجّل الدخول، لكنه لم يتحقق أن السجل يخصّك.

GET /api/invoice?id=1042      ← فاتورتك، تعمل بشكل طبيعي
GET /api/invoice?id=1043      ← فاتورة شخص آخر — وتعمل أيضاً!

الخطأ ليس في الصياغة، بل في سؤال لم يُطرح أبداً: "هل المستخدم الحالي له حق في السجل رقم 1043؟"

الأنماط الثلاثة التي يجب أن تعرفها:

النمط الشكل لماذا يفشل
الفحص غائب مسار /admin يستجيب للجميع لا يوجد تحقق أصلاً
الفحص معطّل الزر مخفي لكن الـ API مفتوح الواجهة ليست أماناً
الفحص معتمد على العميل role=admin يُرسله المتصفح العميل ملك المهاجم

الجملة التي تلخّص الأسبوعين: سياسة الأصل الواحد، والزر المخفي، والحقل المعطّل، والتحقق في الجافاسكربت — كلها ميزات استخدام، وليست ضوابط أمنية. التحقق الوحيد الموجود هو الذي ينفّذه السيرفر، على كل طلب، بناءً على هوية هو من أنشأها — لا على شيء أخبره به العميل.
