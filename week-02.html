Guided Labالمختبر الموجَّه

≈7h · Step by step, with expected results≈7ساعات · خطوة بخطوة مع النتائج المتوقعة

Lab 2.1 — The permission model by hand (2h)

Goal: Build intuition for permissions by creating every combination.

  1. Create ~/lab/week2/permtest/ and three files. Set them to 644, 755, 777.
  2. Create a second user tester with useradd. Try to read each file as tester. Record what happens.
  3. Change the owner with chown. Re-test.
  4. Create a group, add tester, set a file to 660 owned by that group. Verify tester can now write to it.
  5. Run umask and explain the default in your notes. Change it to 077 and create a file — what permissions did it get? Why?

Deliverable: A table in your notes showing, for each of 5 test cases, the permissions set, whether tester could read/write/execute, and why.

If you see this → it means:

Symptom Cause
Permission denied on a file you own You're in the wrong directory, or it's a directory-traversal issue — check x on every parent dir
Can't cd into a directory you can read Directories need x (execute) to be entered, not r
chown fails with "Operation not permitted" Only root can change ownership (even your own files)

Lab 2.2 — Users, groups, and sudo (1.5h)

  1. Create user analyst with a home directory and bash shell.
  2. Set a password. Inspect the entry in /etc/passwd and /etc/shadow — explain every field.
  3. Add analyst to a new group soc. Verify with id analyst.
  4. Give analyst sudo access without full root — edit /etc/sudoers via visudo, grant only /usr/bin/apt and /usr/bin/systemctl status.
  5. Switch to analyst (su - analyst) and verify: sudo apt update works, sudo cat /etc/shadow does not.

Deliverable: Notes explaining why limited sudo is better than full sudo, with reference to a real-world scenario.

Never edit /etc/sudoers directly with nano. Always visudo — it validates syntax before saving. A broken sudoers file can lock you out of root entirely. This is a real outage cause in production.

Lab 2.3 — Processes and signals (1.5h)

  1. Start a long-running process: sleep 600 &
  2. Find it with ps aux | grep sleep, note its PID.
  3. Send SIGTERM (kill PID) — it dies gracefully.
  4. Start another sleep 600, send SIGKILL (kill -9 PID). Explain the difference.
  5. Use top and htop — identify the top 3 CPU consumers, sort by memory.
  6. Find which process is listening on port 22: sudo ss -tlnp | grep 22.
  7. Explain in your notes: what is a zombie process? What is PID 1?

Lab 2.4 — Finding SUID binaries (2h)

Goal: The first genuinely security-flavored lab.

  1. Find all SUID binaries on your Ubuntu VM: find / -perm -4000 -type f 2>/dev/null

  2. For each, note what it does and whether it's expected.

  3. Read about GTFOBins (gtfobins.github.io) — a catalogue of standard binaries that can be abused to escalate privileges.
  4. Check: are any binaries on your system listed in GTFOBins with a SUID technique?
  5. Do not exploit anything. Just answer: why does an SUID binary that calls a shell, or that can read arbitrary files, hand an attacker root?

Deliverable: A list of your system's SUID binaries with a risk assessment for each: expected / suspicious / dangerous, and one sentence of reasoning.

المختبر 2.1 — نموذج الصلاحيات يدوياً (ساعتان)

الهدف: بناء حدس بالصلاحيات عبر إنشاء كل تركيبة ممكنة بيدك.

  1. أنشئ المجلد ~/lab/week2/permtest/ وثلاثة ملفات. اضبط صلاحياتها على 644 و755 و777.
  2. أنشئ مستخدماً ثانياً باسم tester بالأمر useradd. جرّب قراءة كل ملف بصفة tester. سجّل ما يحدث.
  3. غيّر المالك بـ chown. ثم أعد الاختبار.
  4. أنشئ مجموعة، وأضف tester إليها، واضبط ملفاً على 660 مملوكاً لتلك المجموعة. تحقق أن tester يستطيع الكتابة فيه الآن.

المختبر 2.2 — المستخدمون والمجموعات وsudo (ساعة ونصف)

  1. أنشئ المستخدم analyst مع مجلد منزلي وصدفة bash.
  2. اضبط له كلمة مرور. افحص مدخله في /etc/passwd و/etc/shadow — واشرح كل حقل.
  3. أضف analyst إلى مجموعة جديدة باسم soc. تحقق بالأمر id analyst.
  4. امنح analyst صلاحية sudo دون root كامل — عدّل /etc/sudoers عبر visudo، وامنحه فقط /usr/bin/apt و/usr/bin/systemctl status.
  5. انتقل إلى analyst (su - analyst) وتحقق: sudo apt update يعمل، وsudo cat /etc/shadow لا يعمل.

المخرجات: ملاحظات تشرح لماذا sudo المحدود أفضل من sudo الكامل، بالإشارة إلى سيناريو من الواقع.

لا تعدّل /etc/sudoers مباشرة بـ nano أبداً. استخدم visudo دائماً — فهو يتحقق من الصياغة قبل الحفظ. ملف sudoers معطوب قد يحرمك من root تماماً. هذا سبب انقطاع حقيقي في بيئات الإنتاج.

المختبر 2.3 — العمليات والإشارات (ساعة ونصف)

  1. شغّل عملية طويلة الأمد: sleep 600 &
  2. اعثر عليها بـ ps aux | grep sleep، وسجّل رقم PID الخاص بها.
  3. أرسل SIGTERM (kill PID) — فتموت بسلاسة.
  4. شغّل sleep 600 آخر، وأرسل SIGKILL (kill -9 PID). واشرح الفرق.
  5. استخدم top وhtop — حدّد أكثر 3 عمليات استهلاكاً للمعالج، ثم رتّب حسب الذاكرة.
  6. اعرف أي عملية تستمع على المنفذ 22: sudo ss -tlnp | grep 22.
  7. اشرح في ملاحظاتك: ما هي العملية الزومبي (zombie)؟ وما هو PID 1؟

المختبر 2.4 — العثور على ملفات SUID (ساعتان)

الهدف: أول مختبر بطابع أمني حقيقي.

  1. اعثر على كل ملفات SUID التنفيذية في جهاز Ubuntu الوهمي: find / -perm -4000 -type f 2>/dev/null

  2. لكل ملف، سجّل ما يفعله وهل وجوده متوقع.

  3. اقرأ عن GTFOBins (gtfobins.github.io) — فهرس للأدوات القياسية التي يمكن استغلالها لتصعيد الصلاحيات.
  4. تحقق: هل يوجد أي ملف تنفيذي في نظامك مُدرج في GTFOBins مع تقنية SUID؟
  5. لا تستغل أي شيء. أجب فقط: لماذا يمنح ملف SUID يستدعي صدفة، أو يستطيع قراءة أي ملفات، المهاجم صلاحيات root؟

المخرجات: قائمة بملفات SUID في نظامك مع تقييم مخاطر لكل واحد: expected (متوقع) / suspicious (مشبوه) / dangerous (خطير)، وجملة تبرير واحدة.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

This is the week Linux becomes a security topic.

The permission model is the access control system. Every "privilege escalation" vulnerability you will ever read about is, at its core, one of these:

  • SUID misconfiguration — a binary runs as root; if you can make it run your code, you are root. This is the #1 Linux privesc technique in the real world.
  • World-writable files (777) — anyone can modify a script that root executes on a schedule. Instant root.
  • Weak sudo rules — sudo apt sounds harmless until you learn apt can install a package that runs arbitrary code as root.
  • Group membership leaks — being in the docker group is equivalent to root. Almost nobody knows this until they're being tested on it.

The lesson to internalize: on Linux, privilege escalation is almost never an exploit. It's a misconfiguration someone wrote off as "fine."

هذا هو الأسبوع الذي يتحول فيه لينكس إلى موضوع أمني.

نموذج الصلاحيات هو نظام التحكم بالوصول. وكل ثغرة "تصعيد صلاحيات" ستقرأ عنها يوماً ما هي، في جوهرها، واحدة من هذه:

  • سوء إعداد SUID — ملف يعمل بصلاحيات root؛ وإن استطعت جعله ينفّذ كودك أنت، صرت root. هذا هو أسلوب تصعيد الصلاحيات رقم 1 في لينكس في العالم الحقيقي.
  • ملفات قابلة للكتابة من الجميع (777) — أي شخص يستطيع تعديل سكربت ينفّذه root وفق جدول زمني. root فوراً.
  • قواعد sudo ضعيفة — sudo apt يبدو غير مؤذٍ، حتى تعلم أن apt يستطيع تثبيت حزمة تنفّذ كوداً عشوائياً بصلاحيات root.
  • تسريبات عضوية المجموعات — أن تكون في مجموعة docker يعادل أن تكون root. لا أحد تقريباً يعرف هذا حتى يُختبر عليه.

الدرس الذي يجب أن تستوعبه: في لينكس، تصعيد الصلاحيات ليس استغلالاً (exploit) في الغالبية العظمى من الحالات. إنه سوء إعداد مرّ عليه أحدهم قائلاً "لا بأس".

ملاحظات مفاهيمية موسّعة

شرح إضافي موسّع

نموذج الصلاحيات في لينكس — قلب الأمان

في لينكس، كل ملف له مالك، ومجموعة، وصلاحيات محددة. هذا هو أساس نظام الحماية كله.

قراءة الصلاحيات: -rwxr-xr--

عند تشغيل ls -l، أول 10 أحرف تخبرك بكل شيء:

-  rwx  r-x  r--
│   │    │    │
│   │    │    └── الآخرون (others) — أي مستخدم آخر
│   │    └─────── المجموعة (group) — أعضاء مجموعة الملف
│   └──────────── المالك (owner) — من يملك الملف
└──────────────── نوع الملف: - ملف عادي، d مجلد، l رابط رمزي

معنى الأحرف:

الحرف المعنى للملف المعنى للمجلد
r (read) قراءة المحتوى عرض قائمة الملفات
w (write) تعديل المحتوى إنشاء/حذف ملفات داخله
x (execute) تنفيذ الملف كبرنامج الدخول إليه بـ cd
- لا يوجد هذا الإذن لا يوجد هذا الإذن

نقطة يخطئ فيها الجميع: المجلد يحتاج x للدخول إليه، وليس r. إذا كان لديك r بدون x، ترى أسماء الملفات لكن لا تستطيع فتحها أو الدخول.

النظام الرقمي (Octal)

كل إذن له قيمة: r=4 · w=2 · x=1. اجمعها لكل فئة:

الرقم المجموع المعنى
7 4+2+1 قراءة + كتابة + تنفيذ (كل شيء)
6 4+2 قراءة + كتابة
5 4+1 قراءة + تنفيذ
4 4 قراءة فقط
0 — لا شيء

أمثلة شائعة:

  • 644 = المالك يقرأ ويكتب · الآخرون يقرؤون فقط → الملفات العادية
  • 755 = المالك كل شيء · الآخرون يقرؤون وينفذون → البرامج والمجلدات
  • 600 = المالك فقط → الملفات الحساسة مثل مفاتيح SSH
  • 777 = الجميع كل شيء — خطر أمني! لا تستخدمه أبداً

الصلاحيات الخاصة: SUID — أخطر مفهوم هذا الأسبوع

عندما تضع SUID على ملف تنفيذي، فإنه يعمل بصلاحيات مالكه وليس صلاحياتك.

-rwsr-xr-x  root  root  /usr/bin/passwd
   ↑
   s بدلاً من x = SUID مُفعّل

مثال عملي: أمر passwd يعدّل ملف /etc/shadow — وهو ملف لا يملك أي مستخدم عادي صلاحية الوصول إليه. لكن passwd عليه SUID ومالكه root، فيعمل بصلاحيات root ويستطيع التعديل.

لماذا هذا خطير أمنياً؟

لأنه إذا استطاع المهاجم إجبار برنامج SUID على تنفيذ أوامره — مثلاً عبر قراءة ملف أو فتح shell — فإن تلك الأوامر ستعمل بصلاحيات root. هذا هو أشهر أسلوب لتصعيد الصلاحيات في لينكس.

كيف تبحث عنها: 

find / -perm -4000 -type f 2>/dev/null

هذا الأمر يبحث عن كل ملف عليه SUID. الرقم 4 في البداية في 4000 هو SUID.

المستخدمون والصلاحيات — مبدأ أقل صلاحية

root هو المستخدم الخارق: يستطيع فعل أي شيء. العمل الدائم بـ root خطأ فادح:

  • أي خطأ بسيط (مثل rm -rf /) يدمر النظام بالكامل — لا يوجد "تراجع".
  • أي برنامج خبيث تشغّله يعمل بصلاحيات كاملة.
  • لا يوجد أثر جنائي (audit trail) — لا نعرف من فعل ماذا.

الحل: sudo — يمنحك صلاحيات root لأمر واحد فقط، ثم يعود بك مستخدماً عادياً. يُسجّل كل استخدام في السجلات.

مبدأ أقل صلاحية (Least Privilege): امنح كل مستخدم وكل برنامج أقل صلاحيات ممكنة لأداء مهمته فقط. هذا المبدأ هو أساس الأمان في كل الأنظمة — من لينكس إلى السحابة.

العمليات والإشارات (Processes & Signals)

العملية (Process) = برنامج قيد التشغيل. لكل عملية PID (معرّف رقمي).

الإشارات (Signals) = رسائل تُرسل للعملية:

الإشارة الرقم المعنى
SIGTERM 15 "من فضلك توقف" — إنهاء لطيف، يسمح للبرنامج بحفظ عمله
SIGKILL 9 "توقف الآن" — قتل فوري، لا يمكن للبرنامج تجاهله
SIGHUP 1 إعادة تحميل الإعدادات عادةً

القاعدة: جرّب SIGTERM أولاً. استخدم SIGKILL فقط عندما يرفض البرنامج التوقف — لأنه لا يمنحه فرصة لحفظ البيانات أو تنظيف الموارد.
